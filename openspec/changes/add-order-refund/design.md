## 全额退款：把约束放进接口形状，而不是校验里

PRD §7.7：「一期只支持原路全额退款，任何部分退款请求必须拒绝且不创建退款记录。」

有两种落法：

```js
refundOrder(id, amount, reason)   // 然后校验 amount === o.total
refundOrder(id, reason)           // 采纳
```

第一种能工作，但它把「可以部分退款」写进了接口形状。半年后有人要加部分退款时，只需删掉一行校验 —— 而这恰恰是需要范围授权的事（§3.2 排除项、§14「后续若需实施必须分别获得范围授权」）。第二种让部分退款**表达不出来**：调用方没有地方放金额。

门禁因此断言的是接口形状而非校验逻辑：`refundOrder.length <= 2`，且函数体里不出现 `amount` 作为入参。这比断言「金额校验存在」更难绕过。

同理，契约层不再导出 `partial` 标记。一个恒为假的布尔字段只会让读代码的人以为部分退款是可能的，而页面里那句「部分退款 / 实付 ¥38.00」永远不会被渲染 —— 死分支比没有分支更有害。

## 只推进到「退款中」

§7.7：只有微信确认退款成功才是 `已退款`；「受理成功、客户端提示或调用成功均不等于退款完成」。

所以 PC 端的退款动作到 `退款中` 为止，没有「确认退款成功」按钮。加这个按钮会让主账号能凭手感把订单标成已退款 —— 那是伪造到账。`退款中 → 已退款` 由微信支付回调驱动，属后端。

这也解释了财务页那个「N 笔未到账」：净额已经扣了它们，钱还没退出去。这两个数字之间的差就是当前的在途风险，主账号需要看得到。

## 幂等：拒绝，而不是"返回第一次的结果"

§7.1 要求「相同幂等键重复请求返回第一次最终结果，不重复产生副作用」。

严格照做的话，重复调用应当**静默返回第一次的退款记录**。但在 PC 后台这个上下文里，重复点击「发起退款」几乎总是误操作 —— 主账号以为第一次没生效。静默成功会让他以为退了两次，或者以为什么都没发生。

因此这里的做法是：**拒绝并说明当前状态**（「『0118』当前为 退款中，不能再次发起退款。退款结果以微信为准。」），同时保证既有退款记录一个字节都不改。副作用的幂等性得到满足，且用户拿到了他真正需要的信息 —— 第一次已经生效了。

门禁两条都验：重复调用被拒，且事后该订单仍只有一条退款记录、退款单号不变。

## 「未取餐」为什么必须是筛选而不是状态

§6.7 写得很直白：「作为一个筛选条件提供，**不是订单状态**」。而 §7.1 又规定状态「必须且只能为」六个。

如果做成第七个状态，就需要一个把 `待取餐` 转成 `未取餐` 的转换 —— 而这个转换的触发条件是**时间流逝**，不是任何人的动作。时间驱动的状态转换意味着：订单的状态取决于你什么时候去看它，同一笔单在营业日结束前后是两个状态，而 §7.1 要求「每次转换必须由服务端校验前置状态、资源权限和幂等键，并记录审计」—— 没有动作也就没有操作人可审计。

做成筛选就没有这些问题：状态永远是 `待取餐`，「未取餐」只是 `status === '待取餐' && pickupDate < 当前营业日` 这个查询的名字。门禁正向断言筛选结果正确，反向断言它没有泄漏进 `LANES` 或 `ACT`。

有一个实现上的坑：这个筛选是挂在 `待取餐` 泳道上的条件。切到别的泳道时若不清掉，交集必然为空，列表会莫名其妙变空 —— 这个 bug 在浏览器里实际出现过一次（退款成功后跳到 `退款中`，列表空白、详情停在旧单）。因此门禁额外断言「切泳道」和「退款后跳转」两处都清了它。

## 营业日与登录账号各归一处

之前 `pages/finance.js` 里硬编了 `const TODAY = '2026-08-21'`，而「未取餐」也需要同一个日期。两处各写一份，跨零点时会各说各话。

登录账号同理：页面头部原本读的是 `Seed.MANAGER = { name: '高特', role: '店长' }` —— 一个与 `MERCHANT_ACCOUNTS` 无关的装饰常量。退款要记操作人，必须取自真正的登录账号（§4.4：PC 后台仅主账号可登录），否则财务对账上的追责链是断的。

两者都收进契约层：`Api.today()` 与 `Api.currentAccount()`。门禁断言页面源码里不再出现形如 `'20xx-xx-xx'` 的字面日期。
