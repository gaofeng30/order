## Context

当前 PRD §1–§14 同时保留一期目标、P0 阶段说明、V1 增强和大量“需要讨论”条目，§15 又精确记录了允许使用 mock、假支付、独立订单集合、简化状态和可撤销交互的 P0 原型。P0 本身已经完成其演示目标，问题不是原型不够“真实”，而是后续身份、库存、订单、支付、退款、履约、核销和权限 changes 缺少一个共同且无歧义的正式产品输入。

本 change 只通过一次 PRD 基线更新解决这个问题。它不实施任一业务能力，不修改客户确认清单、合同、技术文档或源码，也不把尚未取得的外部账号与经营配置伪装成已就绪事实。

## Goals / Non-Goals

**Goals:**

- 把用户已裁决的一期范围和十二组行为规则写入 PRD §1–§14，并消除同层级冲突和行为 TODO。
- 让后续 changes 能从 PRD 得到唯一库存维度、订单状态机、身份价格、预约、退款和权限契约，无需读取 mock 猜业务。
- 建立需求—页面—状态—角色—外部依赖追踪矩阵和可执行 PRD 验收检查。
- 保留 P0 §15 的 as-built 价值，同时明确其低于正式产品基线且不能成为生产契约。
- 把外部 12 Gate 和 UAT 配置值放在正确阶段，不阻塞本地 OpenSpec 规划。

**Non-Goals:**

- 不设计或实现业务 API、数据库 schema、支付 SDK、定时任务、前端页面、权限中间件、部署或监控。
- 不修改 `docs/product/微信点单小程序客户资料与业务规则确认清单.md`、合同、`online-ordering-system-technical.md` 或业务代码。
- 不判断现实合同是否已经签署，不替客户完成认证、收款、退款、隐私确认或发布授权。
- 不记录真实商品值、库存值、时段、截单、取餐点、员工名单、价格、密钥、证书、账号标识或个人数据。
- 不把会员等级、优惠券、积分、储值、部分退款、配送、多门店、POS、打印机或叫号屏带回一期。

## Decisions

### D1. 正式产品规则只落在现有 PRD §1–§14

批准后的实现直接更新 `docs/product/online-ordering-system-prd.md`，不另建“正式基线”文档。各章节职责固定为：

- §2–§3：目标、一期包含/排除范围、文档优先级和仓库合同证据边界；
- §4：用户身份与后台四角色；
- §5：固定预约、首次结算身份、服务端算价和微信支付用户流程；
- §6：逐商品员工价、按日按餐段库存、营业时段、订单、核销、财务与后台权限；
- §7：九态状态机、软预占、支付确认、超时/迟到支付、履约、取消和退款；
- §8：把全部一期规则放入 MVP，移除与一期冲突的 V1/二期表述；
- §9：幂等、事实源、资源权限、审计和敏感数据边界；
- §12：集中列出正式业务不变量；
- §13：改为“生产配置与外部依赖”，不得继续承载行为讨论；
- §14：验收标准与需求—页面—状态—角色—外部依赖追踪矩阵；
- §15：保留 P0 as-built 描述，在章首及冲突处明确“仅原型、不得覆盖 §1–§14”。

另建文档会产生第二个产品事实源，因此被拒绝；只在 §15 追加说明也不能消除 §1–§14 内部冲突，因此同样被拒绝。

### D2. 一期范围按一条闭环冻结

一期是单门店固定预约自提闭环：员工/访客识别 → 服务端价格与库存 → 15 分钟支付软预占 → 微信支付 → 商户接单/制作/备好 → 单取餐点核销 → 完成或全额退款 → 基础后台。员工价是逐商品固定价格，不是会员等级。

所有排除项直接从一期验收和 MVP 必做移出，不提供“可选启用”或“先预留”双轨。需要这些能力时必须另起 change 和范围授权。

### D3. 库存、支付和状态用一个服务端事实模型表达

库存池固定为 `(service_date, meal_period, product_id)`；午餐和晚餐独立，同餐段所有时段共享。订单提交原子生成 15 分钟软预占，支付成功才实扣；超时释放；迟到支付先重占，失败自动全额退款并进入异常。客户端库存、支付跳转和 mock 状态都不是事实源。

订单公开状态固定九态，且只允许服务端单向转换。支付状态、退款事实、库存流水和操作审计将由后续 changes 设计内部模型，本 change 只冻结它们必须呈现的产品结果和不变量。

继续使用原型六态或 PC 三态会遗漏支付、退款和异常；把支付、退款、履约完全拆成用户不可理解的多套公开状态又会改变已裁决的九态，因此均被拒绝。

### D4. 身份与价格在首次结算时由服务端确定

浏览不要求手机号；首次结算需要微信会话、手机号和姓名。服务端标准化手机号并匹配启用员工名单，命中为员工，否则为访客。商品使用整数分正常价和可选整数分 `employee_price`，服务端算价并在订单固化身份、名单版本与价格快照。

客户端自选员工、手工手机号作为可信认证、百分比折扣、等级和优惠券都会引入绕过或叠加语义，均不进入一期。

### D5. 所有一期订单都使用固定预约和单取餐点

门店时区固定 `Asia/Shanghai`，可选营业日期仅今天和明天，餐段仅午餐和晚餐，每个固定时段拥有独立截单时间。一期没有“尽快取餐”，也没有多取餐点路由；订单固化营业日期、餐段、时段、截单和取餐点快照。

真实时段、截单和取餐点内容是 UAT 前生产配置。它们改变可售日历和展示值，但不改变日期范围、餐段、固定时段或单取餐点模型。

### D6. 后台权限固定四角色并由服务端执行

一期只存在店管、后厨、核销和财务只读四个业务角色。角色权限按 spec 的最小动作集合执行；用户端身份选择不能授予商户权限，开发方也不拥有默认常驻业务角色。生产排障只能使用客户限时授权并留审计。

原 PRD 的平台/超级管理员会把多商户平台责任带入一期，因此不保留为产品角色；开发运维责任通过外部授权表达。

### D7. 外部依赖归并为十二个有序 Gate

外部台账使用固定 12 Gate：主体一致性；小程序注册与认证；餐饮类目；备案；项目/体验成员；云资源/域名实名/ICP；HTTPS/服务器域名；商户号/AppID 绑定；API 安全状态；交易结算管理；隐私/手机号；体验版真机→审核→客户发布确认。

每个 Gate 只记录责任方、非敏感证据引用、状态、阻塞阶段和更新时间。未取得完成证据时统一使用 `BLOCKED_EXTERNAL`，证据通过后变为 `READY`，不使用空值或行为 TODO。合同适用性作为商业/上线依赖记录；它与其他外部 Gate 都不阻塞本地 PRD 和技术 OpenSpec，只阻塞明确对应的联调、UAT、提审或发布阶段。

最后三步归在第 12 Gate 内并保持严格顺序，从而既满足十二项台账结构，也不会把真机、审核和客户发布确认误当成一个可并行动作。

### D8. 真实经营值是 UAT 配置，不是行为 TODO

商品、库存数量、固定时段、逐时段截单、取餐点、员工名单和正常/员工价格值统一列为 UAT 前生产配置。PRD 定义字段用途、责任方、最晚阶段和验收方法，不填示例个人数据或真实账号标识。

配置尚未提供时，后续 change 仍可完成模型、API、本地测试和严格 OpenSpec；对应能力进入 UAT 时才检查配置完成。这样避免把普通经营配置变成全局研发 Gate。

### D10. PRD 验收使用严格校验、结构检查与敏感词边界

writer 先对未修改 PRD 运行目标检查并记录 Red，再修改 PRD 转 Green。检查只扫描 §1–§14 的正式目标内容，§15 的 P0 as-built 可以保留“后天”“尽快”或简化状态，但必须明确为原型差异。

自动检查至少验证：九态、四角色、库存三维键、15 分钟软预占、迟到支付、今天/明天、午晚餐、单取餐点、`Asia/Shanghai`、逐商品 `employee_price`、12 Gate、来源优先级、追踪矩阵和排除项全部出现；§1–§14 不存在 `TODO`、`TBD`、`A/B`、`待确认`、`需要和客户讨论`或与本 spec 相反的正式规则。

只做关键词存在检查不足以证明语义一致，因此 reviewer 还必须逐行对照 spec 和矩阵。任何 PRD、spec、tasks、owned paths 或候选 SHA 变化都会使旧验证失效。

## Risks / Trade-offs

- [仓库缺少已签署合同证据] → 只记录仓库证据边界和现实未知；合同适用性留在商业/上线 Gate，不阻断本地产品与技术基线。
- [§15 与正式规则仍会看起来不同] → 保留 as-built 是为了可复现 P0；在章首、状态、预约、身份、支付等冲突处明确目标规则以 §1–§14 为准。
- [一个 PRD change 横跨多个未来业务模块] → 本 change 只冻结不可拆分的共同产品输入，不实现任何模块；后续能力仍按独立 OpenSpec、owned paths 和依赖拆分。
- [真实经营配置未提供] → 规格固定模型和字段，UAT Gate 检查值；禁止在规划文档使用真实个人数据或账号标识。
- [关键词检查可能误报或漏报] → 检查限定 §1–§14 并与严格 OpenSpec、追踪矩阵人工逐项核对组合使用。
- [并行 worker 修改 PRD] → 当前 DRAFT 只写 change 目录；批准实施前重新检查 PRD HEAD 和 ownership，出现并行 writer 时先协调串行所有权，不覆盖他人改动。

## Migration Plan

1. 本规划提交保持 `DRAFT`，只包含 change artifacts。
2. 用户批准后，writer 重新读取四类 artifacts、确认 PRD 无并行 writer，并把状态转为 `APPROVED`/`IMPLEMENTING`。
3. 对当前 PRD 运行 §1–§14 结构和规则检查，记录因冲突、缺失矩阵和行为待确认产生的 Red。
4. 仅修改 `online-ordering-system-prd.md`，按 D1 的章节落点写入唯一规则并保留 §15 原型边界。
5. 重跑相同规则检查、追踪矩阵核对、`openspec validate formalize-mvp-product-baseline --strict` 和 owned-path diff，全部通过后产生候选 SHA。
6. 在另一个干净 detached worktree 对精确候选 SHA 只读重跑全部验收；任一变化后重新验证。

回滚只需整体撤销该候选对 PRD 的修改及本 change 的实现状态记录；不涉及数据迁移、业务代码或外部系统回滚。
