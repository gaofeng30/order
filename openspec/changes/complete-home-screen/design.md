## 选定方案

### 公告与营业状态都读配置，首页不持有事实

首页从 `globalData.store` 读 `notice` 与 `status`，不在页面里写死任何一句。`STORE` 种子补 `notice`，取值与 PC `SETTINGS.notice` 一致 —— 两端演示数据说同一句话，接后端时它们本来就会是同一条记录。

营业状态直接取 `store.status` 的三个取值，**不再从截单时刻派生**。§6.9 明写「主账号可手动切换，覆盖营业时间规则」：既然人工可以覆盖，派生值就不是事实，只是默认值。首页要展示的是事实。

### 提示条的三个状态

```
无进行中订单            → 不渲染
有进行中、无 待取餐     → 「你有 N 单进行中 · 今天 18:30 取餐」，常规样式
有任一 待取餐           → 「已备好，可取餐」，高亮
```

「最近一单」按取餐时刻排序取第一条，点击进入该单。不是按下单时间 —— 用户关心的是下一顿什么时候能拿，不是他什么时候付的钱。

`待取餐` 优先于单数展示，因为此刻用户需要的动作是**现在就去窗口**，而不是知道自己有几单。文案里不再重复单数，避免「已备好，可取餐 · 2 单进行中」这种把行动号召稀释掉的写法。

### 为什么提示条不能省

§5.10 的两类订阅消息都需要用户主动授权，且餐饮类目只能一次性订阅。用户拒绝授权时，PRD 指定的兜底正是「§5.1 的首页进行中订单提示条与 §5.8 的订单状态展示」。没有提示条，拒绝订阅的用户在餐做好时不会收到任何信号 —— 他要么一直等，要么反复进小程序刷订单页。

## 边界

- 不引入开屏图层：它依赖服务端下发接口，本地实现已按 `remove-retired-entry-screens` 的结论移除，重新引入会退回那个「只会渲染无法清除的陈旧图片」的状态。
- 不改三个入口（预约点餐 / 我的订单 / 取餐码），§5.1 就是三个。
- 提示条只读订单，不写订单。

## 会使旧验证失效的变更面

- `store.notice` 或 `store.status` 改由首页自行推导。
- 进行中口径从 `已预约` / `制作中` / `待取餐` 三态变化。
- 首页重新出现占位或「即将上线」一类角标。
