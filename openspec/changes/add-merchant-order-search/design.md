## 选定方案

### 营业日：一个常量，两处消费

`utils/data.js` 导出 `BUSINESS_DAY = '2026-08-21'`，与 PC 后台 `apps/web-admin/data/api.js` 的同名常量取值一致。商户端订单新增 `pickupDate` 字段。

不引入「从系统时间推导今天」。种子数据是固定的演示数据，若按真实时钟推导，明天跑测试整套断言就会翻转。营业日必须是**数据里的一个事实**，不是运行时环境的函数。后端就位后这个常量由服务端下发，届时替换的是取值来源，不是消费方。

### 取餐号：格式与解析分离

格式（4 位数字、按取餐日期累计）是**数据事实**，由种子保证并由门禁按正则校验。
解析（一个 4 位串指向哪张单）是**查询规则**，由 `utils/util.js` 新增的 `findByCode(code)` 单点实现，搜索与手工核销共用。

分离的理由：§6.6 的「只匹配当前营业日」如果分别写在搜索和核销两处，两处会漂移 —— 这正是 PC 端 `fold-verify-into-orders` 踩过的坑。放在一处，门禁可以断言「解析取餐号的实现只有一份」。

### 搜索：查询，不是状态

`kw` 是页面局部状态，不写入 `globalData`，不参与订单模型。搜索态与泳道互斥：
- `kw` 非空 → 忽略 `lane`，在全部订单上匹配；
- 点泳道 → 清空 `kw`。

不做「在当前泳道内搜索」。商户使用搜索的场景是顾客站在窗口报一个号，此时商户并不知道这张单处于哪个状态 —— 把结果限制在当前泳道，等于要求使用者先猜对答案。

匹配规则（与 PC `_search` 同构）：

| 输入 | 匹配 |
| --- | --- |
| 4 位纯数字 | 当前营业日的取餐号，**或**手机号包含该串 |
| 其他 | 订单号 / 手机号 / 联系人 / 取餐号 包含 |

4 位数字同时匹配手机号，是因为跨营业日歧义只是取餐号的属性，手机尾号没有这个问题；若只按取餐号解释，商户输入手机尾号会得到空列表。

### 跨营业日：报事实，不报空

4 位数字在当前营业日无果、但存在于其他营业日时，`codeHint(code)` 返回一句话，指出该号属于哪个营业日以及可用的替代定位方式（订单号 / 手机号）。搜索列表在其上方渲染该提示；手工核销用同一文案 toast。

空列表是最差的反馈：它和「这个号不存在」不可区分，而两者的处置完全不同。

## 边界

- 只改小程序。PC 后台的搜索与营业日逻辑已在 `fold-verify-into-orders` 落地，本 change 不触碰，也不抽取两端共享模块 —— 两端没有构建链路，共享只能靠复制，复制比各自实现更难维持一致。
- 不改 `NEXT` / `ACT` / 泳道数组，因此不与 `order-lifecycle-ui1.test.js` 的既有断言冲突。
- 用户端只改 `code` 字面值，不改任何渲染或交互代码。

## 会使旧验证失效的变更面

- 任何对 `ADMIN_ORDERS` / `USER_ORDERS` 条目数或状态分布的改动。
- `BUSINESS_DAY` 取值变化。
- `findByCode` 从单点实现被拆散。
