## Context

用户要求「商户自己上传 Excel，自动解析，存数据库」。我先核查 PRD 是否已有该能力，结论是基本没有——只有一段继承自已删除会员名单的 CSV 表述，客户从未表态。用户随后确认：先补 PRD，再开发。

## Decisions

### 收 `.xlsx`，不收 CSV

原设计要求商户把 Excel 另存为 CSV UTF-8，并为 GBK 编码准备了中止提示。那条提示本身就是失败率的证据——让食堂管理员分清「CSV」和「CSV UTF-8」不现实。

直接收 `.xlsx` 的代价是服务端要引 Excel 解析库，收益是绕开整个编码坑。经用户 2026-08-21 确认。

### 解析放服务端

两个理由，都不是偏好：解析结果要写数据库，校验必须在服务端做，否则客户端校验只是装饰；`apps/web-admin` 是零构建静态站点，浏览器内解析要往仓库塞几百 KB 的 SheetJS。

因此前端只负责选文件、上传、渲染预览、提交确认。

### 菜品只新增不更新，员工按手机号覆盖

两套规则不同，因为主键性质不同。

员工白名单的手机号是天然唯一识别键，覆盖语义清楚，PRD §6.4 原本就是这么写的，保留。

菜品**没有天然唯一键**。名称可以重复也可以改，用名称做覆盖键意味着：商户传一份旧表就能把全部价格改回去，且没有撤销。因此定为只新增——命中同名即标记异常跳过。批量改价继续走菜品管理页已有的批量调价功能，那条路径有明确的目标价格与确认步骤。

经用户确认选 A（只新增）。

### 分类不存在则自动新建，但要有去重规则

用户要求分类不必预先存在。直接新建的风险是长出垃圾分类：「今日套餐 」带尾空格、同一批里同名重复。

因此补三条规则：去首尾空格后精确匹配；同一文件内同名新分类只建一次；预览单独列出本次将新建的分类，让商户在提交前看见。

### 图片不进模板

Excel 塞不进图片。硬做只能在表里写图片 URL 或文件名，两者都要求商户先把图传到别处，比逐个上传更麻烦。

因此模板只覆盖文字字段，导入的商品先以占位图上架，商户随后逐个补图。导入页必须明写这一点，否则商户会以为图也一起进来了。

### 先补 §6.3 的表单字段集合，再定模板列

「Excel 字段与前端页面一一对应」是用户提的约束。要执行它，必须先有一个确定的「前端页面字段集合」——而当前 PC 菜品表单缺 `餐段可售`，PRD §6.3 却要求它。

因此本 change 先在 §6.3 把表单字段集合固定下来（五项必填加一项选填），再让 §6.13.2 的模板列对齐它。门禁对这两处做交叉检查。

规格与口味选项经用户确认一期不在表单内维护，记为已知偏差而非静默省略——评审 §11 确实要求过逐商品口味配置。

### 商户账号名单不做导入

用户只提了菜品与员工两项。商户账号名单本就只有几个人，而它直接决定谁能进商户端和 PC 后台，批量写入的误操作后果远大于收益。明确写成不做，避免后续被当作遗漏补上。

## Risks / Trade-offs

| 风险 | 处置 |
| --- | --- |
| §6.13 全节不在客户已确认范围内 | 已在节首与 §16.4 C4 双处标注为「开发方提出的范围新增，待客户确认」，并明写取得确认前不得表述为已含在已付款范围内 |
| 只新增不更新意味着改价仍需逐个操作 | 批量调价功能已存在于菜品管理页，路径更安全 |
| 导入后一批无图商品直接可售 | 已列为 §16.3 P7 待拍板：直接可售显示占位图，还是先置售罄待补图 |
| 单文件行数上限未定 | 已列为 §16.3 P6，需按真实规模给具体值 |

## Invalidation conditions

- 客户对批量导入作出正式确认或否决；
- §6.3 的表单字段集合变化，届时 §6.13.2 的模板列需同步；
- 决定引入商户账号名单的批量导入。
