## 选定方案

### 名称是快照，不是外键

`items` 元组变为 `[id, name, qty, price, discountedPrice, flavors?, note?]`。

`id` 保留：退款、对账、销量统计都需要指回商品。但**显示用的名称不再经由 id 解析**。理由是订单的语义：§5.6 要求订单固化原价、折扣率、折后价、身份与价格版本，目的正是让订单在目录变化后仍然复述得出下单当时的事实。名称属于同一类事实，把它留成外键等于给这份历史记录开了一个会随时间变化的洞。

反过来说，如果名称必须实时解析才正确，那价格也必须实时解析 —— 而那显然是错的。两者不能采用不同的存储策略。

### 为什么插在 index 1 而不是追加到末尾

追加到末尾（`[id, qty, price, discountedPrice, flavors?, note?, name?]`）可以避开所有既有位置索引，改动更小。不这么做，是因为 `flavors` 与 `note` 是**可选尾项**，把一个必填字段排在可选项之后，元组就再没有稳定的 arity 可言：`it[6]` 到底是名称还是备注，取决于前面有没有填口味。这类形状会在第一次「没填口味的单」上出错，而且错得安静。

代价是 PC 的归档门禁按位置断言会整体右移一位，需要走接管流程。这个代价是一次性的、可见的、在门禁里会红给我们看的；末尾追加的代价则是长期的、隐蔽的。

### 回查路径整体移除，兜底一并移除

PC 的 `itemsSummary` 现在写作：

```js
items.map(([id, q]) => (Seed.itemById(id) || { name: '已删除菜品' }).name + '×' + q)
```

`|| { name: '已删除菜品' }` 是回查方案的补丁。名称改为快照后它不再有触发条件，继续留着会让人以为「商品删除后订单会显示已删除菜品」仍是当前行为。一并删除。

小程序侧同理：`itemsSummary`、`order-detail`、`admin-order-detail`、`admin-verify` 四处的 `data.itemById(id)` 调用中，凡是**只为取名称**的整体删除；`order-detail` 还用它取图片，那一处保留但允许返回空 —— 订单没有固化图片，商品不在本地目录时回落占位图，这是诚实的降级，不是缺陷。

### 门禁断言形状而非位置

新门禁按 arity 与语义断言：每行至少 5 项、`it[1]` 是非空字符串、`it[2]` 与 `it[3]` 是整数。结算恒等式改用具名解构而非裸下标，这样下一次元组变形时门禁会以「字段缺失」而不是「算错了」的形式失败 —— 后者要花时间才能诊断出根因。

## 边界

- 只改「名称从哪来」。小程序订单的金额单位、遗留字段、整单级口味留给下一个 change，本 change 不碰，因此两个 change 可以分别回滚。
- 不动购物车与目录层：`cart.list()` 已经返回带 `name` 的目录快照，`confirm.pay()` 只是把它写进元组。
- 不动 PC 的订单状态机、财务与支付待处理的金额口径。

## 会使旧验证失效的变更面

- `items` 元组的 arity 或列序再次变化。
- 任何重新引入「按 id 解析名称」的渲染路径。
- `check_order_model.js` 的接管断言集被削减。
