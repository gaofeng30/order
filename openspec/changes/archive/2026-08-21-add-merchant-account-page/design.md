## 关键判断：不变量放在哪一层

「至少有一个启用的主账号」是本页唯一一条真正危险的规则 —— 违反它的后果不是数据难看，而是**没有人能登录 PC 后台**，且 PC 后台是唯一能添加主账号的地方。这构成自锁：一旦触发，产品内部没有任何恢复路径，只能人工改库。

有三种放法：

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| A 页面隐藏按钮 | 最后一个主账号的行不渲染停用 / 删除按钮，编辑抽屉的角色下拉去掉子账号 | 只挡住了 UI 路径。契约方法仍可被直接调用；后端就位后该规则会随页面代码一起消失 |
| B 保存后校验回滚 | 先写，再检查是否还有启用主账号，没有则回滚 | 需要事务语义，本地演示数据层没有；且回滚失败时状态不可知 |
| **C 契约层前置守卫（采纳）** | `guardLastOwner(id, action)` 在三个写方法入口处判定，不通过直接 reject | 三条路径共用一处判定，页面不参与裁决；后端就位时该守卫平移为服务端校验，页面代码不动 |

采纳 C。守卫本身只回答一个问题：**除了这个账号，还有别的启用主账号吗**——

```js
function enabledOwners(exceptId) {
  return g().accounts.filter(a => a.role === 'owner' && a.enabled && a.id !== exceptId);
}
function guardLastOwner(id, action) {
  const target = g().accounts.find(a => a.id === id);
  if (!target || target.role !== 'owner' || !target.enabled) return null;  // 本来就不是启用主账号，随便动
  if (enabledOwners(id).length > 0) return null;                           // 还有别人顶着
  return fail(`「${target.name}」是唯一启用的主账号，不能${action}。请先添加并启用另一个主账号。`);
}
```

`action` 由调用方传入（`删除` / `停用` / `降级为子账号`），使拒绝提示能指出具体动作。三个入口：`deleteMerchantAccount`、`setMerchantAccountEnabled(id, false)`、`saveMerchantAccount` 的编辑分支中 `role` 由 `owner` 变 `staff` 时。

页面仍然渲染这些按钮，不做预先禁用 —— 让管理员点下去看到「为什么不行、怎么才行」，比一个灰掉且无解释的按钮更有用。页面只额外加一条提示条说明当前处于这个状态。

## 为什么这份名单不给批量导入

菜品与员工白名单都做了 `.xlsx` 导入，本页不做，理由不是工作量：

- 账号数量在个位数，导入的收益接近零。
- 它授予的是**登录权限**。一次误导入可以凭空造出一批能进 PC 后台的主账号，而这类错误往往在很久之后才被发现。
- 逐条录入是**有意的摩擦**：每加一个能登录的人，都应该是一次明确的动作。

这条已写进 PRD §6.13.4。门禁上断言的是「页面不具备导入能力」（不装配 `ImportFlow`、无 `type="file"`、导航无对应路由），而不是「批量导入」四个字不出现 —— 页面注释里说明本页为何不提供导入是正当的。

## 与员工折扣白名单的分离

两份名单字段相似、页面相邻，最容易出的管理事故是**认错名单**：把顾客加进商户账号名单（等于给了他后台权限），或把员工加进商户名单却以为是在配折扣。

三处做了区分：字段上多一个「角色」列并展示可用范围；页头文案直接写明两份名单各自决定什么；门禁断言两份数据是不同集合且 id 不重叠。

## 子账号的可用范围文案

评审 §26 写子账号「上架下架菜品、扫码」，§38 又把小程序菜品页收敛为只能切可售 / 售罄。以 §38 为准（它是后来的收敛结论，且已落地为小程序 4 屏），因此本页对子账号的可用范围写作「仅小程序：订单 / 核销 / 菜品」，与 `miniprogram-scope-conformance` 已生效的四屏规格一致，不写「上架下架」。
