## Context

删除类三件套的最后一件。前三个 change 已集成归档，本 change 在其基础上清理商品目录字段。

规划阶段曾把本 change 的范围估得偏大，实测后收窄：用户端的 `menu` 与 `detail` 早已切到 API 目录，既有 UI1 用例的 `UNSUPPORTED_PRODUCT_FIELDS` 已经把 `stock` / `sold` / `tags` 挡在用户端之外。真正还带这些字段的只有商户端页面与两端 mock 种子。

## Goals / Non-Goals

**Goals**

- 让两端商品记录、契约与商户端页面不再出现标签、过敏原、月售与数量库存。
- 保证删除后售罄与上下架链路完好——这是一期唯一的可售性机制。

**Non-Goals**

- 不实现按取餐日期的售罄开关。本 change 只删数量维度，新机制属新增类 change。
- 不把 PC 销量排行改接真实订单数据（PRD §6.12 的待改造项）。
- 不删即时单，不迁商户端配置页。

## Decisions

### 删 `stock` 但保留 `status`

评审 §3 说「商品只有可售和售罄两种销售状态」。`status` 承载的正是这两态（外加 `off` 下架），是一期唯一的可售性机制，必须保留。被删的是数量维度：`stock` 字段、`stock <= 8` 的告急判定、库存输入与校验。

因此断言分两侧写：既断言四类字段消失，也断言 `status` 仍在、售罄切换端到端可用。只写前者会让一次删过头的改动静默通过。

### 顺带删掉「待取超时」待办

PC 工作台待办原有三项：待制作、待取超时、库存告急。本 change 的范围只覆盖库存告急（D2）；待取超时属评审 §21（D6），严格说不在范围内。

仍然一并删除，理由是待办列表是一个整体单元：0818 PRD §6.12 明确规定「待办：待制作数」，只有一项。删掉三项中的一项、留下另一项已废止的，会让这个单元处于一个既不符合旧规则也不符合新规则的中间态，而且下一个碰它的 change 还要再改一次同一个数组。

这是本 change 唯一一处越出字面范围的改动，在此显式记录。

### 状态色阶一并清理

两端的状态语义色阶表里还有 `待取超时: 'warn'` 与 `库存告急: 'warn'`。这两个语义已经不存在，留着会让后续实现者以为还有对应状态。清理属于本次删除的直接尾巴，不是顺手优化。

### PC 后台的 UI1 这次直接跑浏览器

上一个 PC 端 change 我曾把 UI1 记为 `BLOCKED_EXTERNAL`，后来更正为实际运行取得。本 change 直接沿用该做法：本地静态服务器 + 浏览器，验证表格列、编辑抽屉字段、工作台待办、销量排行与售罄切换。仓库仍无可提交的自动化 runner，这一点不变。

## Risks / Trade-offs

| 风险 | 处置 |
| --- | --- |
| 删掉数量库存后，一期没有任何超卖保护 | 这是客户已确认接受的取舍（0818 PRD §16.1 R1）。本 change 只是让代码与该决定一致 |
| PC 销量排行仍读 `Seed.RANK` 的静态数据 | `RANK` 是排行数据源，与商品的 `sold` 字段是两回事，未被本 change 触碰。改接真实订单数据是 PRD §6.12 的独立待改造项 |
| 商品编辑去掉库存后，表单只剩四项 | 符合 PRD §6.3 对商品管理的定义。售罄由列表页的切换控件承担，不在编辑表单里 |

## Invalidation conditions

- 客户对商品字段或可售性机制作出新的正式确认；
- `mvp-product-baseline` 的 `Product availability uses a per-service-date sellout switch` 被修改；
- 按取餐日期的售罄开关实现后，本 change 建立的「商品记录不含数量字段」断言需与新机制的数据结构一并复核。
