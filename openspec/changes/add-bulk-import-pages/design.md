## Context

批量导入四件事的最后两件。前两件补齐了菜品的餐段字段与员工白名单主页面，本件把两个导入页建起来。

## Decisions

### 自己写 xlsx 读取器，不引库

`apps/web-admin` 是零构建静态站点，没有打包工具。引 SheetJS 意味着往仓库塞几百 KB 的 vendor 文件。

`.xlsx` 本质是 ZIP + XML，而 ZIP 的中央目录格式简单，deflate 有浏览器与 Node 都内置的 `DecompressionStream('deflate-raw')`，XML 结构规整到可以用正则扫。整个读取器约 120 行，覆盖 Excel 生成的常规文件（stored 与 deflate、sharedStrings、inlineStr、数值单元格）。

不支持加密、宏与多工作表选择，固定读第一张表。这些限制写在文件头。

### 解析放契约层而不是页面

PRD §6.13.1 规定解析必须在服务端，页面不得自行解析。后端接口未就位，因此走该节标注的 P0 原型例外：解析放在 `data/api.js` 的导入方法内部（经由 `window.Xlsx`），页面只调 `Api.previewXxxImport(file)`。

这不是绕过约束，而是把本地实现放在**后端就位时唯一要替换的那个文件**里。门禁对此有断言：两个页面源码中不得出现 `Xlsx.readRows` 或 `DecompressionStream`。

### 预览与提交分离，令牌幂等

预览把计划存进内存 `_imports[token]`，不碰数据。提交按令牌取计划执行，执行后置 `done`；重复提交返回首次结果并带 `duplicate: true`。

这样「用户连点两次确认」不会导入两遍，也让流程与将来的服务端实现同构 —— 那边令牌会是服务端会话里的一份解析结果。

### 行号从表内 1 起算，含表头

异常提示要让商户能在 Excel 里直接定位。因此行号 = 表头算第 1 行的实际行号，而不是数据行序号。门禁对此有断言，故意把三条异常放在第 4、5、6 行。

### 菜品导入的「只新增」在预览阶段就判定

同名菜品在预览阶段就标为异常，而不是提交时静默跳过。商户在确认前就能看到「哪几行不会进去、为什么」，避免以为全部导入成功。

异常原因里直接给出替代路径：「改价请用菜品管理的批量调价」。

### 员工覆盖只写两个字段

`commitStaffImport` 的更新分支用 `Object.assign({}, 既有, { phone, name })`。这条与 `saveStaff` 是同一处理，理由也相同：全量表重传不能把离职人员重新激活。

门禁专门造了一条已停用记录参与导入，断言提交后 `enabled` 仍为 `false` 且 `joinAt`、`spend` 未变。

### 门禁自己造 .xlsx 夹具

要验证解析器就得有真文件。夹具构造器手写 ZIP（含 CRC32 与中央目录），用 `zlib.deflateRawSync` 产生 deflate 条目，同时能产出 stored 条目 —— 两条压缩路径都被覆盖。夹具只在 `checks/` 下，不进产物。

## Risks / Trade-offs

| 风险 | 处置 |
| --- | --- |
| 自写解析器覆盖面窄于成熟库 | 限制写在文件头。后端就位后该实现整体替换，届时用 Go 的成熟库 |
| 本地解析违反 §6.13.1 的服务端要求 | 该节已标注 P0 原型例外并明确不构成生产契约；解析位于契约层，页面不接触 |
| 导入的菜品无图 | 模板本就不含图片。导入页两处提示，商户随后逐个补图 |
| 单次行数上限 500 是我拍的 | PRD §16.3 P6 已列为待拍板，需按真实规模给值 |

## Invalidation conditions

- 后端导入接口就位，届时契约层实现整体替换，P0 例外应从 PRD 移除；
- 模板列变化，届时 §6.13 与本 change 的校验需同步；
- PRD §16.3 P6 拍板给出真实行数上限。
