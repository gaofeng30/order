## 选定方案

### 删掉 `branch` 而不是把它设成门店名

客户说「门店名就叫绥安食品」。若保留 `branch` 并设为 `'绥安食品'`，就会有两个恒等的字段，而下一个写代码的人仍要在 `name` 和 `branch` 之间挑一个 —— 这正是上一个 change 里 `pickupPoint` 与 `pickupWindow` 分裂的成因，同样的坑不必再挖一次。

一期是单门店（§3.1），分店概念没有对应的现实事实。字段删除，消费点各自改指正确来源。

### 取餐地点取自订单，不取自门店配置

`admin-order-detail.wxml` 把取餐地点渲染成 `{{store.branch}}` 是一处真实错误。§7.2 要求「生成订单时再次固化商品、价格、折扣率、身份、取餐日期与时间、取餐点快照」，§15.6.2 的 `pickupPoint` 就是那个快照。渲染门店当前配置意味着：配置一改，历史订单展示的取餐地点跟着改 —— 与快照的意义直接相反。

用户端订单详情本来就读 `o.pickupPoint`，商户端漏了。改为一致。

### 硬编码只改「错的那几行」

`绥安食品` 在十来处硬编码。这些值**是对的**，不是缺陷，只是耦合。把它们全部改为配置读取是一次独立的重构，会把本 change 的改动面扩大三倍，而收益（将来改门店名时少改几处）在单门店一期里趋近于零。

本 change 只处理两类：值错的（含 `县前直营店` 的三处字面量），以及因为删 `branch` 本来就要改的。其余保持原样并在 non-goals 里说明，不留「改了一半」的错觉。

## 边界

- 只改门店标识（名称、地址）与由此牵出的取餐地点渲染错误。
- 不动 `app.json` 的静态标题：它不经运行时数据层，改它属另一类事。
- 不动订单模型。

## 会使旧验证失效的变更面

- `branch` 字段重新出现。
- 任何页面重新按门店配置渲染订单的取餐地点。
