## 选定方案

### 一个常量，两端同源

```js
const PICKUP_POINT = '党政办公中心后院老食堂北门';
```

小程序 `utils/data.js` 与 PC `data/seed.js` 各自导出同名同值常量，所有写入与展示路径引用它。

不保留 `name` / `addr` 二元结构。客户只给了一个字符串，硬拆成名称与地址就得凭空编一个 —— 而现在的两条写入路径正是因为有两个字段可挑，才各挑了一个，产生了 `confirm.pay()` 写窗口描述、种子写点位名称的分裂。字段少一个，分裂就无处发生。

`PICKUP_POINTS` 数组保留但只作为「配置里可枚举的点位列表」供 PC 营业设置渲染，其唯一元素的 `name` 即该常量。不新增 `addr`。

### 订单详情只展示一次

原模板一行里同时输出 `ptAddr`（地址）与 `o.pickupPoint`（名称）。合并为一个值后，两处会渲染同一串文字。改为只展示取餐点本身。

### 为什么不顺手把门店名地址一起换掉

`STORE.branch` 与 `STORE.addr` 同样是演示值，但客户这次给的是取餐地点。把它们替换成「党政办公中心」一类的推测值，等于把一个明显虚构的值换成一个看起来可信的虚构值 —— 后者更难在 UAT 时被发现。保持原样并单独索取，是更安全的处理。

## 边界

- 只改取餐点。门店名、门店地址、门店公告不动。
- 不改订单模型：`pickupPoint` 仍是订单上的快照字段（§7.2 要求生成订单时固化取餐点）。
- 不动 PC 营业设置页的「取餐点」表单结构，只改它渲染的值来源。

## 会使旧验证失效的变更面

- 取餐点重新变成多值或重新拆成名称 / 地址两个字段。
- 出现第二处硬编码的取餐点字符串。
