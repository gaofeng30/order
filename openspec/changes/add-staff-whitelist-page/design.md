## Context

四件事里的第二件。第一件补齐了商品的餐段可售，本件补建员工折扣白名单——它是全局折扣率的作用对象、附加手机号双要素的数据源，也是员工批量导入的落地页。

## Decisions

### 折扣率定义为「员工实付百分比」而非「折扣」

「折扣率 85」有两种读法：打 85 折（付 85%）或打折 15%。中文语境下「八五折」= 付 85%，但字段名 `discountRate` 容易被读成减免比例。

因此在界面上写成「**员工实付 85 %**」，旁边给一个实时推导的「约 8.5 折」提示。存储与校验都用整数百分比 1–100，100 表示无折扣。这样字段含义在 UI 上无歧义，也避免了小数带来的舍入分歧。

### 状态用行内按钮而非编辑表单里的开关

PRD §6.4 把状态归为非填写字段——它是对已有记录的运营动作（离职停用），不是新建时要填的数据。放进编辑抽屉会让人以为它和姓名手机号同级。

因此列表行内直接给「停用 / 启用」按钮，编辑抽屉里只以只读方式显示当前状态并注明「在列表中切换」。

### 编辑只覆盖两个字段

`saveStaff` 在编辑分支用 `Object.assign({}, 既有记录, { phone, name })`，而不是整条替换。这样加入时间、微信绑定、累计消费与单量不可能被前端传来的字段覆盖。

门禁对此有专门用例：编辑姓名后逐项比对四个系统字段的快照。这类「更新时静默丢字段」的缺陷不写断言基本发现不了。

### 删除与停用在确认文案里区分

停用保留记录与统计，删除不可恢复。商户很容易把「这人离职了」理解成删除，然后丢掉历史消费数据。

因此删除确认文案明写「停用可保留记录，删除不可恢复」，把选择摆在他面前。

## Risks / Trade-offs

| 风险 | 处置 |
| --- | --- |
| 白名单里是真实姓名与手机号 | 种子为 mock 演示数据。真实名单属 §13.3 的 UAT 前配置，由客户授权人员录入 |
| 折扣率改动立即生效，无审批 | PRD §6.4 即如此设计，且只影响新报价。若需审批属独立范围 |
| 该页未接后端 | 项目方选择 B（先 mock 后接）。契约层方法签名即为后端接口契约，后端就位时只替换实现 |

## Invalidation conditions

- 客户对白名单字段或折扣率形态作出新的正式确认；
- PRD §6.4 被修订；
- PC 后台接入真实后端，届时契约层实现替换但方法签名应保持。
