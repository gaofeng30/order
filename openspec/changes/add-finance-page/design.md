## 归集口径是这页唯一的实质问题

其余都是排版。一个财务页要么和微信账单对得上，要么就是个好看的废物。而对不上的原因几乎总是同一类：**用错了日期**。

有四个日期在这套数据里同时存在：

| 日期 | 含义 | 谁在用 |
| --- | --- | --- |
| `paidAt` | 支付成功时间 | 微信交易账单 |
| `pickupDate` | 取餐营业日期 | 商户的排产与备餐 |
| `refund.at` | 退款到账时间 | 微信退款明细 |
| 当前日期 | —— | 页面默认区间 |

前两个在预约单上会分开（今天付、明天取），后两个在跨日退款上会分开（今天退、明天到账）。**只要把任意一对混用，账就对不上**，而且错得很隐蔽 —— 总数看着差不多，只有具体某天差一笔。

因此：

- 收款按 `paidAt` 归集。理由不是「更合理」，而是**微信账单就是这么切的**。我们要和它对，就得用它的刀。
- 退款按 `refund.at` 归集，不跟原单走。

这两条不写进注释就会被下一个人改回去，所以都写在契约层的注释里，并且各配一条用跨日数据构造的门禁：

```
种子里有一笔 08-20 支付、08-21 取餐的预约单
  → 按 08-21 筛选时它必须不出现
种子里有一笔 08-21 支付、08-22 才退到账的退款
  → 按 08-21 筛选退款时它必须不出现，按 08-22 必须出现
```

没有这两笔数据，一个把两处日期都写错的实现照样能通过所有断言 —— 因为其余订单的两个日期恰好相同。**门禁的强度取决于数据能不能把错误实现区分开**，不取决于断言写了多少条。

## 部分退款为什么必须在种子里

净额有两种写法：

```
net = gross - Σ(退款金额)          ← 对
net = gross - Σ(被退订单的实付)     ← 错，但在全额退款下结果相同
```

只有当种子里存在一笔「实付 38.00、只退 12.00」的部分退款时，两种写法才会给出不同的数（462.80 vs 434.80），门禁才能判掉后者。

同理，未到账的退款笔数要单独标出：净额已经扣了它，但钱还没退出去。管理员看到「净额 462.80」时，需要知道其中 36.00 是已扣未付。

## 导出为什么是 CSV 而不是 .xlsx

批量导入用 `.xlsx`，导出用 CSV，看着不对称，但理由具体：

- 我们**没有生成 `.xlsx` 的能力**。`data/xlsx.js` 是只读的 ZIP 解析，写要重新实现 ZIP 打包与 OOXML 组装。
- 导出的用途是拿去和微信账单比对，纯文本更好处理，Excel、Numbers、任何脚本都能开。

但 CSV 有两个会让文件直接变废的坑，都必须防：

1. **无 BOM 的 UTF-8 在 Excel 里是乱码。** 商户拿到的是一屏问号。开头补 `﻿`。
2. **20 位的微信交易号会被 Excel 当数字**，显示成 `4.2E+21`，交易号就此丢失 —— 而交易号正是对账的连接键。用 `="…"` 公式形式钉成文本。

门禁两条都断言了。第二条断言的是「导出行里不出现科学计数法」，也就是断言事实而非断言我用了哪种写法 —— 换成前缀制表符或加引号的其他方案照样能过。

## 页面必须说自己核不了什么

汇总卡给出一个净额，管理员很自然会理解成「系统已经核过了」。实际上本页只是把本系统内的订单加了一遍，微信那一侧根本没读。

自动拉取账单需要后端调支付查询接口，一期没有。因此页面底部固定一段口径说明，明写「自动拉取并比对微信账单一期未实现，本页数字只汇总本系统内的订单，不代表已与微信核平」，并同时记进 PRD §16.5 的缺口清单。

门禁对此断言的是**事实**：页面提到微信账单、给出净额，且 PRD 缺口清单里有对应条目 —— 而不是去匹配某句固定文案。
