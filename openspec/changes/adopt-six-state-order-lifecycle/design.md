## Context

新增阶段的第一件。删除类三件套已经把一期范围外的能力清干净，但订单生命周期本身仍是旧的三态模型。生效 spec 的六态 requirement 从 `realign-mvp-product-baseline` 起就已生效，一直处于被违反的状态。

## Goals / Non-Goals

**Goals**

- 两端订单生命周期与生效 spec 的六态一致。
- 彻底移除撤销能力——这是 spec 里少有的用 `MUST NOT` 写死的约束。
- 移除即时单，使结算恒为预约流程。

**Non-Goals**

- 不实现服务端定时排产、退款触发、取餐时间点新 UI、支付对账兜底。
- 不改后端。

## Decisions

### `已预约 → 制作中` 不进 NEXT 表

这条转换按 spec 由服务端定时任务驱动。原型没有后端，最省事的做法是让商户手点一下"开做"——但那等于把被客户明确删除的「接单」换个名字加回来（评审 §4「不再有接单功能」、§27「不提供商户手动提前开做」）。

因此 `NEXT` 只含两条商户转换，`已预约` 在 `ACT` 里映射为只读标签「待开做」。种子里放一条 `已预约` 订单填充泳道，让这个状态在界面上真实存在。定时推进标注为服务端职责，原型不模拟。

门禁对此有专门断言：尝试推进 `已预约` 必须被拒绝且状态不变。缺了这条，后续实现者很容易"顺手"加上手动开做。

### 撤销要连组件能力一起删，不只是删调用

小程序的撤销挂在 Toast 组件的 `onUndo` 上，PC 的挂在 `Api.revertOrder`。只删调用点，能力还在，下一个人写推进逻辑时会自然地再用一次。

因此两端都删到能力层：Toast 组件去掉 `_onUndo`、`undoable` 与模板里的撤销按钮，PC 契约层删掉 `revertOrder` 导出。断言也写在能力层。

### 即时单的删除范围止于订单模型

首页「到店点单」入口在 `remove-retired-entry-screens` 里被显式列为非目标，理由是它与结算页的取餐方式切换、订单 `type` 字段和状态机入口态同属一件事。本 change 正是那件事，因此一并删除。

但结算页的**日期与时段控件本身不动**——把「时段」改成「取餐时间点」是 `switch-to-pickup-time-selection` 的范围。本 change 只是让预约分支成为唯一分支。

### 修一处被放大的既有文案缺陷

PC 订单页对不可推进的订单渲染 `该订单已${o.status}`。旧模型下 isView 只有 `已完成` / `已取消`，拼出「该订单已已完成」——缺陷一直存在但只在两个状态上出现。六态把 `已预约`、`退款中`、`已退款` 也纳入只读分支，缺陷面扩大三倍且在默认泳道就能看到。

这属于本 change 直接放大的问题，修复在范围内。门禁加了一条断言防回归。

## Risks / Trade-offs

| 风险 | 处置 |
| --- | --- |
| 原型无法演示 `已预约 → 制作中` 的自动流转 | 种子里同时存在两种状态的订单，界面能看到两者。自动流转标注为服务端职责，不用假定时器伪造 |
| `退款中` / `已退款` 在原型中没有触发路径 | 种子里有一条 `已退款` 订单填充泳道。退款发起属 PC 后台独立 change |
| 订单 `minsToPickup` 仍是种子里的静态值 | 该字段驱动取消规则判定，真实值应由服务端按取餐时间计算。原型保持静态，不影响状态机断言 |
| 取餐号改 4 位无前缀后与旧订单号风格不一致 | 旧种子的 `A126` / `B208` 已按新规则改为纯数字或保留为历史数据；生效 spec 要求按取餐日期从 `0001` 累计，真实编号由服务端分配 |

## Invalidation conditions

- 客户对订单状态集合或即时单作出新的正式确认；
- `mvp-product-baseline` 的六态 requirement 被其他 change 修改；
- 后端实现定时排产后，本 change 建立的「客户端不可推进 `已预约`」断言需与真实链路复核。
