## 选定方案

### 闸门落在需要它的一侧

```
启动 → 身份选择页
        ├─ 用户端  → 首页，零索取（§14 不变）
        └─ 商户端  → 微信手机号授权面板
                      ├─ 拒绝 → 留在本页，说明为何需要
                      └─ 允许 → 进商户端 + 明示校验待服务端
```

改动前的版本把这两条反过来了：用户端弹授权、商户端零验证。需要手机号的是商户（要比对商户账号名单），不需要的是浏览用户。

### 用微信的按钮，不画自己的弹窗

`<button open-type="getPhoneNumber" bindgetphonenumber="...">` 是微信提供的唯一手机号授权入口，点击弹出的是微信自己的面板，用户的允许 / 拒绝由微信裁决并回调。

这与被删掉的旧实现有本质区别：旧的是一个 `<view>` 弹层，「允许」按钮的 `bindtap` 直接跳页，全程没有微信参与。生效 spec 的「MUST NOT 保留不调用微信接口的假授权控件」拦的正是后者，本 change 不触碰这条。

代价是按钮样式受微信 `<button>` 限制。用 `class` 覆盖默认边框与背景、`::after { border: none }` 去掉系统描边即可保持卡片外观。

### 授权之后必须说实话

`getPhoneNumber` 回调拿到的是 `encryptedData` / `code`，明文手机号必须由服务端用会话密钥换取，再比对商户账号名单（§4.4）。前端拿不到、也不该拿到明文。

因此「允许」之后的处理只有两种诚实写法：

1. 拦住，提示该能力待服务端 —— 商户端在演示中完全进不去；
2. 放行，同时明示校验待服务端接入。

当前阶段的目标是前端演示，取 2。关键是那句提示不能省 —— 省掉它，演示现场看到的就是一个「验证通过」的假象，而实际上什么都没验。

### 拒绝授权不是错误

用户拒绝时不报错、不拦路，只留在身份选择页并说明「商户端需要验证手机号身份」。拒绝是一个合法选择，把它渲染成失败会诱导用户重复尝试。

## 边界

- 不碰 §14 的浏览链路：用户端一侧仍然零索取。
- 不碰个人中心的「商户登录」入口，它是 §4.4 原有路径。
- 不做任何形式的前端鉴权：`admin-*` 四屏的访问控制在服务端，本 change 不给它任何前端替身。

## 会使旧验证失效的变更面

- 入口页再次变化。
- 商户端入口退回成非 `getPhoneNumber` 的普通跳转，或重新出现自绘的「授权」弹层。
- 授权成功后的提示中不再声明校验尚未发生。
