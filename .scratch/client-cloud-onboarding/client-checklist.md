# Order 上线：甲方一次性准备与授权清单

更新：2026-09-22。适用本项目中国大陆餐饮点单/自提小程序，腾讯云 CloudBase 部署。**这是一份待办理清单，不是已完成回执。** 小程序及支付已由甲方安排，以下只核验、补缺，不重复注册或重置密钥。

目标：集中办完资料、归属和授权，之后技术配置尽量由开发方完成。平台审核、备案短信及部分敏感操作仍需负责人后续配合，不能保证一场会议全部办结。

## 一、可直接转发甲方的准备事项

请先准备以下内容，并安排一次集中线上协作。营业执照、身份证、银行资料直接提交官方平台；**不要在群聊、普通文档或代码仓库发送账号密码、验证码、AppSecret、APIv3 密钥或私钥。**

| 编号 | 请甲方准备什么 | 必要性 / 完成标准 |
| --- | --- | --- |
| P1 | 最新营业执照；确认主体名称、主体类型、注册住所；实际经营所需的有效餐饮资质 | 必需。主体与平台现状一致；餐饮资质按真实经营模式及微信所选类目核验，不统一强索多套证照 |
| P2 | 甲方长期保管账号的人、法定代表人、备案负责人、付款联系人；相关人员手机可实时接收通知 | 必需。允许合规兼任，不要求新增多个岗位；法人/负责人按实际实名与省份要求配合，不让开发者冒用身份 |
| P3 | 已有腾讯云中国站账号是否企业实名；若没有，使用甲方控制的手机/邮箱注册 | 必需。甲方保留主账号；开发方使用独立授权账号 |
| P4 | 已有域名、注册商、到期日、域名实名及 ICP 备案状态；没有域名则确认拟用名称 | 必需核验。现有合规域名优先，一般一个根域名即可，不必为 API/后台分别购买 |
| P5 | 已有小程序管理员能登录；提供 AppID、认证/备案/服务类目通过状态 | 必需核验。注册完成不等于认证、备案与类目均通过；已完成的项目不用再申请 |
| P6 | 已有微信支付超级管理员能登录；提供商户号、JSAPI/小程序支付开通及 AppID 关联状态 | 必需核验。确认实际收款主体、结算信息正确；不更换超级管理员、收款账户或验签模式 |
| P7 | 实际门店/商户负责人手机号、甲方验收人员微信、对外客服/隐私联系渠道；核验小程序名称/头像/介绍、首发门店与取餐地址、商品名称/实际售价/可用图片、营业与取餐时段 | 必需核验。**已有资料直接复用，仅缺项由甲方提供/确认**，不重新讨论已确认规则；开发方录入。负责人信息用于业务授权、体验验收与联系，手机号走受控渠道。平台基本资料要求见 [W1] |
| P8 | 指定费用审批/付款人，确认开发方提交的具体订单、费用提醒人和是否自动续费 | 下单前必需。此前“合理费用甲方承担”不等于批准任意额度；本清单不要求先充值固定金额或开自动续费 |

以上各项可以先回复“已具备 / 缺项 / 需协助”，身份证和密钥不作为回复附件。

## 二、集中协作时需要甲方完成的操作

后台菜单会调整，下表提供功能位置；开发方应会前备好自己的微信号、云子用户联系方式、精确权限和采购草案，避免临场让甲方研究技术。

| 编号 / 必要性 | 甲方操作与后台位置 | 开发方负责 / 如何判定完成 |
| --- | --- | --- |
| A1 必需 | **腾讯云中国站 → 账号中心 → 实名认证**：核验或完成正确主体认证；按所选方式由法人扫码/人脸或财务配合，不要求所有方式都做 | 提前解释材料、核对主体。完成证据是“认证通过”，不是只上传资料；对公验证仅在所选方式需要时办理。[C1] |
| A2 必需 | **访问管理 CAM → 用户 → 新建普通子用户**：给指定开发人员控制台账号，设置其自己的安全手机/邮箱及 MFA；甲方主账号联系方式不变 | 提供项目所需权限清单，开发人员本人首登改密、绑定 MFA 并验证。不给全账号管理员权限；不交主账号密码/API 密钥。后续修改普通子用户安全联系方式可能仍需甲方管理员。[C2] |
| A3 开通时需要 | **CloudBase 控制台 → 首次开通/服务授权**：甲方确认条款及平台实际申请的服务角色 | 解释角色用途并核对必要权限。云服务角色与开发人员账号是两回事，不把服务角色宽权限直接挂给人。按实际功能可能出现多个授权弹窗。[C3] |
| A4 下单前需要 | **费用中心 → 订单/充值/续费**：批准具体资源订单、付款、确认续费与余额/费用提醒接收人 | 提供单一采购清单并核验 CloudBase 与独立 MySQL 的同地域私网兼容。不给开发人员默认全局财务权；本轮没有购买 CVM、SSM 的要求。CloudBase 用作备案资源需专项核验，不能随手买个最便宜套餐即认定可备案。[C4][D1] |
| A5 必需 | **域名注册商 → 域名实名/管理；DNS 控制台 → 域名权限**：确认域名归甲方，按备案要求完成实名；授权开发人员管理该域名解析，或指定可及时操作的域名管理员 | 提供具体 DNS 记录并验证；不交注册商主密码，不要求合规已有域名转移到腾讯云。新购/过户要考虑实名同步等待。[D2] |
| A6 国内正式服务前必需核验 | **腾讯云 ICP 备案系统**：确认主体、按注册省份确定负责人；负责人本人完成所需核身，条件所需的授权文件由甲方签署 | 准备网站/服务、资源及域名信息；核验首次/接入/变更类型。已备案不自动代表已接入腾讯云。甲方证件直传官方系统，不发开发群。[D3] |
| A7 开发必需 | **微信公众平台 → 成员管理 → 项目成员**：添加开发人员自己的微信，授予实际所需开发、后台配置等权限 | 用开发者自己的微信验证登录、AppID、上传及相关配置权限。单纯“体验成员”不够；甲方保留小程序管理员。[W1] |
| A8 上线前必需核验 | **公众平台 → 账号信息/认证/备案/服务类目**：核验正确主体、认证有效、小程序备案通过；按真实经营模式补齐类目资质 | 开发方协助填报。小程序备案和域名 ICP 备案分别办理；不把自营餐饮误选为第三方“点餐平台”。许可材料依实际类目要求，不默认需要增值电信经营许可证。[W2][W3] |
| A9 已用手机号能力，必需 | **公众平台 → 用户隐私保护指引；手机号能力/付费管理**：甲方确认真实信息用途、保存期限、联系渠道；核验手机号能力可用及额度 | 开发方整理与代码一致的隐私内容，核验非个人且认证、额度及真实接口。不能让甲方盲填隐私模板；有可用体验/其他额度时不强买套餐。额度不足再报具体费用。[W4][W5] |
| A10 支付必需 | **微信支付商户平台 → 账户中心 → 员工账号管理**：添加开发方技术操作员、必要查询/技术权限；若确需密钥证书操作，单独明确安全联系人授权范围 | 开发方验证实际权限；甲方保留超级管理员和收款/结算控制权。技术权限不等于批准操作资金、结算账户或任意退款；真实支付/退款联调需明确对象和金额。[W6] |
| A11 支付必需核验 | **商户平台 → 产品中心/商户信息/AppID 账号管理**：确认商户正常、JSAPI/小程序支付开通、目标 AppID 关联成功 | 查当前结果，不重新进件；异主体如已按官方流程关联，不擅自拆除重绑。纯原生小程序不需要 JSAPI 支付授权目录。[W7][W8] |
| A12 运行必需 | **公众平台 → 管理 → 开发管理 → AppID/AppSecret；商户平台 → API 安全**：核验现有密钥材料是否已在安全存储中；只有缺失时由有权限者配合补齐 | 所需：AppSecret；APIv3 密钥；商户私钥及匹配证书序列号；与当前商户验签模式匹配的微信公钥/平台证书材料。先确定受控存储/交接方式，复用有效配置，不在群里传，不盲目重置或切换整个商户验签模式。[W9][W10] |
| A13 视交易管理状态 | **公众平台对应交易/发货管理、商户授权页面**：若被纳入交易管理，完成平台要求的商户确认/授权 | 开发方查询实际管理状态并实现、验证自提履约上报；不是要求甲方写接口。“自提没有快递单号”不代表豁免。[W11] |
| A14 交付验收必需 | **公众平台 → 成员管理 → 体验成员**：添加指定甲方验收微信；确认真实门店负责人和运维联系安排 | 开发方在业务系统授予经确认的负责人身份、准备真实门店/商品/时间配置。业务管理员与微信平台管理员不同，不能因能登录平台就默认有门店管理权；不创建共享默认管理员密码 |

### 四类账号不能混为一个

| 账号/身份 | 甲方保留 | 开发方需要 |
| --- | --- | --- |
| 腾讯云主账号 | 资产、主体、付款和主账号控制 | 自己的 CAM 子用户及项目权限 |
| 小程序管理员 | 主体与管理员身份 | 项目成员；甲方验收人员另加体验成员 |
| 微信支付超级管理员 | 商户、结算账户与经营责任 | 技术操作员；必要时明确授权安全联系人 |
| Order 业务负责人 | 门店运营权限与业务决策 | 经授权初始化/配置，不等同上述平台账号 |

## 三、授权以后开发方做，甲方不用研究

- 准备并确认最终资源订单；创建 CloudBase 服务、独立 MySQL、私有 COS、网络、安全规则、证书、日志告警及备份。具体规格和权限按部署方案核验，不让甲方选端口、VPC 或数据库密码。
- 配置数据库迁移与受限应用账号；运行密钥安全注入，不用云主账号密钥，不将私有 COS 为排障改成公有读。
- 生成 API/后台域名和真实支付/退款回调地址，完成 DNS、HTTPS、域名绑定及微信合法域名。`request/uploadFile/downloadFile` 按实际调用配置，未使用的能力不强行开通；服务端 IP 白名单和 CI 上传 IP 白名单分别核验，不混同。
- 配置订阅消息实际模板与字段；核验手机号调用；完成登录、门店配置、下单、支付、取消/退款、商户履约及所需自提上报的真实流程。**授权清单完成不代表代码已具备全部上线能力。**
- 开发方检查当前 AppID 是否纳入发货管理；若需要且代码缺接入，必须补齐后再验收。不能把缺实现伪装成“等甲方配置”。
- 准备体验版、审核说明、真实可访问的审核路径/所需测试说明、隐私合规检查和上线验收记录；确认公开网页的公安联网备案适用范围并准备申报材料。
- 资源创建后按真实 ID 收敛权限；交付资源清单、到期提醒、备份恢复/故障处理和人员撤权清单。正式发布、付费及资金操作仍按相应明确授权执行。

## 四、即使集中准备，也需预留的后续配合

| 事件 | 甲方需要做什么 | 时间/依赖 |
| --- | --- | --- |
| ICP 工信部短信验证 | 所需联系人收到验证码后本人进入官方核验页完成，不把验证码转发给开发群 | 官方要求收到后 **24 小时内**，可能发生在集中协作之后；超时可能退回。[D4] |
| 平台实名/备案/安全操作核验 | 按平台要求由法人、负责人、管理员本人扫码/刷脸；如果选对公认证由财务配合 | 外部审核及风控不能保证一次授权后免除；无法提前收验证码 |
| DNS/实名同步与材料审核 | 保持负责人联系方式有效，补充被退回的真实材料 | 不承诺当天完成备案或审核；材料齐全不等于已通过 |
| 真机体验与真实支付/退款 | 指定验收人；事先批准小额联调对象/金额，再验收实际资金与订单结果 | 服务部署、密钥配置及平台权限齐备后进行，不能用模拟成功替代 |
| 上线批准及条件备案 | 甲方确认可对外营业、客服/退款责任；按平台提示完成必要发布验证。符合条件的公开网站办理公安联网备案 | 开发方准备材料与执行步骤；公安备案时限/范围按实际服务判定，不能自动把 PC 后台算作“纯 API”豁免。[D5] |
| 到期/费用/安全变更 | 甲方保留可接收认证、域名、证书、余额和安全告警的联系通道 | 开发方监控和提醒；续费及敏感责任仍有明确负责人 |

## 五、完成回执：只记状态，不放秘密

每项 A1–A14 记录：`已完成 / 待补 / 条件不适用（理由）`、责任人、脱敏截图或后台状态、核验日期。其他可记录：主账号/子用户 ID、AppID/商户号、资源 ID、域名、备案号、证书到期日、精确授权范围、密钥存储引用（**不是密钥值**）。

目前没有真实后台核验回执，不能把上述任何一项预勾为完成。下一次集中操作前，开发方需先收敛：**当前主体与域名、现有平台完成状态、指定开发人员、具体资源订单与费用审批、技术权限方案、密钥安全交接方式**。能从后台只读查到的不要重复问甲方；未确认的预算、代付、安全联系人权限、自动续费及业务负责人不能默认批准。
