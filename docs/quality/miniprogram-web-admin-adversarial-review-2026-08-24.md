# 小程序、商家端与 Web Admin 对抗性走查及评审标准

> - 走查日期：2026-08-24
> - 代码快照：`319020dd02f93199a5710711044cca0db2e2d576`
> - 覆盖对象：微信小程序用户端、微信小程序商家端、Web Admin、Go API、数据模型、自动化测试、产品/演示文档
> 总结论：**NO-GO。当前版本只能用于 UI/交互原型演示，不具备正式 UAT、试运营或发布条件。**

## 1. 决策摘要

本轮共记录 **14 项问题：P0 × 3、P1 × 7、P2 × 2、P3 × 2**。

阻断发布的核心原因不是页面完成度，而是系统尚未形成同一个可信业务闭环：

1. 用户端可以在没有微信支付、服务端订单和支付回调的情况下产生“预约成功”、取餐码和“退款处理中”等成功结果。
2. 普通用户可直接进入商家端，Web Admin 也没有真实登录和服务端授权；当前商家操作与个人数据没有权限边界。
3. 用户端、商家端、Web Admin 使用三套相互独立的本地演示数据；后台看到的订单、营业数据和操作结果不是服务端事实。

视觉层面已经具备较好的演示完成度：小程序与桌面后台的设计语言基本统一，主要页面层级清楚，菜单请求失败时也能明确提示并重试。但视觉完成度掩盖了交易、权限和数据真实性的缺失，因此不得把当前演示结果表述为“核心流程已完成”。

## 3. 严重级别与处理规则

| 级别 | 定义 | 当前版本处理规则 |
| --- | --- | --- |
| P0 | 资金、订单真实性、权限、敏感数据或核心业务不变量错误；可产生不可接受的成功假象或越权 | 一票否决；修复并完成独立复验前不得 UAT/发布 |
| P1 | 主流程无法闭环、关键业务规则错误、跨端数据不一致，或必要运营能力缺失 | 阻断对应主流程验收；必须在候选版本前清零 |
| P2 | 用户可见的误导、死控件、明显视觉/交互缺陷，但有明确替代路径且不改变最终业务结果 | UAT 前清零；特殊延期必须有 owner、期限和不影响主流程的证据 |
| P3 | 边界适配、性能告警或低频体验问题 | 可进入已知问题清单，但必须有明确复验条件 |

`BLOCKED_EXTERNAL` 不是 PASS，也不是缺陷豁免；它只表示当前缺少平台账号、支付资产、真机或真实环境，恢复条件满足后必须补验。

## 4. 问题清单

### P0-01 未支付也会生成订单、成功页、取餐码和退款结果

- **复现**：用户端加入购物车 → 提交订单。确认页未调用预支付或 `wx.requestPayment`，直接创建随机本地订单、清空购物车并跳转“预约成功”；订单详情取消后直接显示“退款处理中”。
- **证据**：`apps/wechat-miniprogram/pages/confirm/confirm.js:73-109`、`pages/result/result.js:8-31`、`pages/order-detail/order-detail.js:37-44`；API 路由当前只有菜单、目录、会话和手机号能力，见 `services/api/internal/httpapi/router.go:14-20`；现有 migrations 没有订单、支付、退款和对账表。
- **影响**：形成最严重的资金与履约假成功；用户、商家、客服和财务看到的结果都不可作为事实。
- **关闭标准**：服务端创建 quote/prepay → 微信支付 → 验签回调幂等落单 → 查询订单事实 → 失败不落单；退款与对账也必须以服务端和微信最终状态为准。拒绝授权、401、503、超时、重复回调和状态未知时不得显示成功、清购物车或生成取餐码。

### P0-02 用户端、商家端和 Web Admin 均缺少可执行的授权边界

- **复现**：小程序启动页对所有人同时展示“用户点单”和“商家入口”，普通用户点击后直接进入商家订单；Web Admin 访问任意 hash 页面无需登录，“退出登录”仅显示 toast。
- **证据**：`apps/wechat-miniprogram/pages/launch/launch.wxml:27-43`、`apps/web-admin/app.js:127-130`。后端已有小程序 session 与手机号接口，但前端没有调用 `wx.login`、手机号授权或这些 API；商家身份也未由服务端校验。
- **影响**：一旦把本地操作替换成真实写接口，将直接造成订单、商品、员工和商家账号越权；当前员工页完整手机号也没有受保护的访问前提。
- **关闭标准**：普通用户默认直达用户首页；只有服务端确认的商家成员才展示身份选择。小程序所有商家写操作与 PC 所有管理能力必须服务端鉴权；PC 按既定二维码登录契约实现会话、过期、退出、最后 owner 保护和审计。仅隐藏按钮不算修复。

### P0-03 三端数据彼此隔离，后台经营事实为本地演示值

- **复现**：用户端创建/取消订单不会出现在商家端或 Web Admin；商家端售罄不会影响 Web Admin 或用户菜单；Web Admin 刷新后状态恢复。
- **证据**：小程序 `app.js:5-34`、`utils/data.js:21-110` 使用本地 `orders/aOrders/menu`；Web Admin `data/api.js:9-13` 使用独立内存 Store；Web Admin 商品状态只修改 `product.status`（`data/api.js:84-89`）。
- **影响**：无法接单、履约、核销、对账或追责；页面 KPI 和操作反馈可能被误认为真实经营数据。
- **关闭标准**：订单、商品可售性、员工身份、商家账号、设置、退款和对账必须来自同一服务端事实源；客户端刷新、跨端操作和重登后保持一致。演示 seed 只能在明确隔离的 demo 环境存在，且页面必须显著标识。

### P1-01 当前时间使用固定演示时钟，已过时间仍可选择

- **复现**：设备时间约 21:49，时间选择器仍默认并启用“今天 17:00”，晚餐时段仍显示可选。
- **证据**：`apps/wechat-miniprogram/utils/data.js:130-187` 把当前时间固定为 `16:48`。
- **影响**：用户可选择已经过去或已经截止的时间；即使服务端最终拒绝，也会在主流程末端制造无效操作和错误预期。
- **关闭标准**：可选日期、时段、截止时间和默认值均来自服务端权威时钟/菜单响应；客户端只展示服务端可选项。跨时区、跨日、截止边界和请求返回后时间推进均有测试。

### P1-02 售罄实现为全局商品状态，缺少按服务日期的写链路

- **复现**：小程序商家端或 Web Admin 点击“标记售罄”，只切换本地商品 `status`，无日期选择、服务端写入或跨端同步。
- **证据**：`apps/wechat-miniprogram/pages/admin-products/admin-products.js:29-35`、`apps/web-admin/data/api.js:84-89`。后端已有 `product_sold_out_dates` 的按日读取模型，但没有商家/Admin 写路由。
- **影响**：今日售罄可能错误影响未来日期，或根本不影响用户菜单；商家无法可信管理预约菜单。
- **关闭标准**：售罄唯一键为 `(product_id, service_date)`；商家端和 PC 写同一 API，用户菜单读同一事实，重复操作幂等，并覆盖今天/未来日期与跨端刷新。

### P1-03 核销页是模拟器，不是真实扫码与当日校验

- **复现**：小程序核销页显示静态取景框和 A118/A126/A090 演示按钮，没有 `wx.scanCode`；Web Admin 仍保留独立“扫码核销”页。输入演示码可直接在本地把订单改为完成。
- **证据**：`apps/wechat-miniprogram/pages/admin-verify/admin-verify.js:6-31`、`admin-verify.wxml:5-20`；Web Admin `pages/verify.js`。当前使用字母数字码，与已确认的四位纯数字取餐码不符。
- **影响**：无法证明真机扫码、当前服务日期限制、二维码 token、防重放、幂等核销或最终订单状态；错误日期/错误订单可能被核销。
- **关闭标准**：扫码能力只在商家小程序；PC 人工核销进入订单管理页。二维码使用不可伪造 token，人工码为四位数字，只允许当前服务日期、待取餐订单；重复核销返回同一最终结果并保留审计。必须补真机 UI3。

### P1-04 Web Admin 缺少正式运营必需页面，且保留了已删除页面

- **现状**：导航包含应删除的 PC 扫码核销，但没有财务对账、待支付、退款管理；订单页也没有按既定规则提供当前服务日期人工核销与完整退款处理。
- **证据**：`apps/web-admin/app.js:26-45`；产品基线 `docs/product/online-ordering-system-prd-0818.md:821-832`。
- **影响**：运营无法处理支付异常、退款和账实差异，也无法在正确位置完成人工核销。
- **关闭标准**：按已确认 PC 信息架构删除独立扫码页，补齐订单、待支付、退款、财务与对账闭环；所有统计和动作来自真实 API，并包含权限、审计、错误态和最终状态核对。

### P1-05 手机号、员工身份和员工价没有接入实际下单链路

- **复现**：个人中心默认显示“已认证员工”和三张历史订单；确认页使用手填联系人/手机号，没有微信手机号绑定、附加手机号、员工白名单匹配或服务端报价。
- **证据**：`apps/wechat-miniprogram/utils/data.js:196`、`pages/profile/profile.wxml`、`pages/confirm/confirm.wxml:35,64-70`。后端虽已有 session、绑定和主手机号查询，但小程序没有调用。
- **影响**：匿名、普通员工、优惠员工的身份和价格均不可信；客户端价格可被篡改，客服无法以服务端事实解释订单价格。
- **关闭标准**：浏览菜单不强制手机号；下单前完成微信手机号绑定或已确认的附加手机号流程；员工资格和全局折扣由服务端在 quote/支付前重新计算并固化快照，前端不提交可信价格。

### P1-06 入口、文案和功能仍包含已排除范围

- **实际观察**：普通用户先看到身份页；商家入口写“接单”；首页/个人中心出现“外卖配送暂未开放”“联系客服”“切换身份入口”；商家订单详情有“打印小票/拨打电话”；Web 业务入口层展示洗衣、洗车“即将上线”。Dashboard 标题写“实时接单”。
- **证据**：`apps/wechat-miniprogram/pages/launch/launch.wxml:27-43`、`pages/profile/profile.wxml:31-46`、`pages/admin-order-detail/admin-order-detail.wxml:51-52`；`apps/web-admin/pages/orders.js:123,130`、`pages/layer.js:89-147,282`、`pages/dashboard.js:121`。
- **影响**：错误定义一期产品边界，引导用户进入不可用能力，并与“预约制、无需接单、一期只做餐饮、禁止占位入口”的已确认决策冲突。
- **关闭标准**：一期界面和测试中完全移除配送、打印、电话、接单、洗衣/洗车和其他 placeholder；普通用户直达首页，只有已授权商家显示身份选择。

### P1-07 自动化测试和文档把原型行为当成正确行为

- **现状**：`62/62` 与 `74/74` 虽然通过，但测试明确断言“两张身份入口保留”“mock pay”“本地订单状态推进/退款”；README 和 demo guide 仍指导使用本地假支付、旧商家 Dashboard、PC 扫码等流程。小程序 scope spec 内部也同时存在商品上下架“保留”和“禁止”的矛盾描述。
- **证据**：`apps/wechat-miniprogram/tests/anonymous-entry-ui1.test.js`、`catalog-ui1.test.js`、`order-lifecycle-ui1.test.js`；根 `README.md:54-74,120,133-163`；`apps/wechat-miniprogram/README.md`；`docs/product/online-ordering-system-demo-guide.md`；`openspec/specs/miniprogram-scope-conformance/spec.md:128-167,272-298`。
- **影响**：持续集成全绿仍可能交付错误产品；后续开发者无法区分权威产品契约、原型说明和过期实现。
- **关闭标准**：先统一权威规格并删除冲突，再以正式不变量重写测试；README/demo guide 只能陈述当前真实能力，原型测试不得作为正式验收证据。支付、权限和跨端一致性必须由真实服务端/平台测试覆盖。

### P2-01 多个控件可见但不可用或反馈错误

- **实际观察**：商家订单和商品搜索框只是静态 View；商品显示“上架”但商家端只应有按日售罄；预约单“待开做”按钮点击后 Web Admin 提示“该订单已是终态”；打印/拨号只弹提示；成功页在订单未待取餐时就引导“查看取餐码”。
- **证据**：`apps/wechat-miniprogram/pages/admin-orders/admin-orders.wxml:17-23,63-73`、`pages/admin-products/admin-products.wxml`、`apps/web-admin/data/api.js:153-200`。
- **影响**：造成可操作性误判、错误状态理解和重复点击。
- **关闭标准**：不可用控件直接移除；保留控件必须有真实 handler、loading、成功、失败、幂等和刷新后结果。预约单不允许客户端提前生产。

### P2-02 首页“服务功能”标题对比度不足

- **复现**：iPhone 12/13 Pro 视口下，内容区负 margin 覆盖蓝色 hero，“服务功能”仍使用深色文字，标题与背景对比不足。
- **证据**：`apps/wechat-miniprogram/pages/home/home.wxml:28`、`pages/home/home.wxss:13`。
- **影响**：首屏信息层级断裂，深色背景下可读性差。
- **关闭标准**：在目标机型和系统字体缩放下满足正文/标题可读性与对比度要求；补深浅背景视觉回归截图。

### P3-01 Web Admin 只适配 1280px 以上桌面

- **复现**：`1024 × 768` 下文档宽度仍为 `1280px` 并产生横向裁切；`1366px` 下正常。
- **证据**：`apps/web-admin/index.html:5` 固定 viewport 宽度。当前 README 已声明 `>=1280px`，因此记为已知产品边界而非主流程缺陷。
- **关闭标准**：明确后台最低分辨率和浏览器支持矩阵；若实际运营设备包含 1024px 或分屏，须改为响应式并补浏览器矩阵。

### P3-02 小程序存在全局组件注入性能告警

- **复现**：微信开发者工具提示 9 个全局注册自定义组件影响按需注入；无运行错误。
- **影响**：低端机首屏体积和初始化性能可能受影响，当前尚无量化性能证据。
- **关闭标准**：按页面注册组件或证明全局注册必要；记录包体、首屏耗时和低端机基线后再关闭。

## 5. 流程级评审结果

| 用户/运营流程 | 当前结果 | Verdict | 最低复验标准 |
| --- | --- | --- | --- |
| 匿名进入与浏览 | 页面可用，但普通用户被身份页拦截 | FAIL | 普通用户直达首页；无商家入口泄露；菜单来自服务端 |
| 日期/时段/菜单 | API 失败态清楚；时间选择使用固定演示时钟 | FAIL | 服务端权威时间、截止规则和按日菜单；跨边界测试 |
| 手机号与员工价 | 仅本地假身份，未接 API | FAIL | 微信登录/手机号、员工白名单、服务端 quote 全链路 |
| 下单与支付 | 本地 mock 成功 | **P0 FAIL** | 真实预支付、支付回调、幂等落单、失败不产生成功副作用 |
| 订单查询/取消/退款 | 本地状态推进 | **P0 FAIL** | 服务端状态机、退款最终态、对账与异常恢复 |
| 商家履约 | 普通用户可进入；订单不来自用户端 | **P0 FAIL** | 服务端 RBAC、同一订单事实、合法状态迁移和审计 |
| 扫码/人工核销 | 模拟码、本地完成；PC 页面位置错误 | FAIL | 真机扫码、四位码、当日限制、防重放、幂等与审计 |
| 商品/售罄 | 本地全局状态 | FAIL | 按服务日期写 API，三端读取同一事实 |
| Web Admin 运营 | UI 较完整，但无登录、无真实数据且关键页面缺失 | **P0 FAIL** | PC 登录/RBAC、真实 API、财务/退款/待支付/人工核销闭环 |
| UI 一致性/可用性 | 整体视觉成熟，存在范围残留、死控件和一处对比度问题 | PARTIAL | P1/P2 清零，目标机型和桌面浏览器视觉回归 |

## 6. 修复顺序与发布门禁

必须按以下顺序收敛，前一层未稳定时不得用上层 UI 演示宣称闭环完成。

### Gate A：契约与事实源冻结

- `online-ordering-system-prd-0818-review.md` 的已确认结论与 `mvp-product-baseline` 作为当前业务事实源；消除 miniprogram scope spec 内部矛盾。
- README、demo guide、测试名和页面文案明确区分“演示”与“正式能力”，删除已否决范围。
- 冻结状态机、角色权限、服务日期、取餐码、支付/退款/对账和售罄唯一键。

### Gate B：身份与授权

- 接通小程序 session、手机号和商家成员关系；所有写操作服务端鉴权。
- 实现 PC 二维码登录、会话、退出、角色、最后 owner 保护和审计。
- 401、授权拒绝、身份未知时 fail closed，不导航到商家页、不展示敏感数据。

### Gate C：服务端业务闭环

- 完成订单、quote、预支付、支付事件、退款、对账、设置、员工白名单、商家账号、审计和按日售罄的数据模型/API。
- 对支付回调、重复提交、并发状态迁移、退款重试、核销重放和进程中断建立 Red → Green → Refactor 证据。
- 任何客户端成功页、KPI、价格、订单状态和权限结果只使用服务端事实。

### Gate D：三端接线与 UI 收敛

- 删除本地订单、支付、身份和经营 seed；全部页面接同一 API。
- 移除 P1-06 中的越界入口和 P2-01 的死控件；修复固定时间、按日售罄、真实扫码和首页对比度。
- 每个动作覆盖 loading、失败、重试、重复点击、刷新、重登和跨端同步。

### Gate E：候选版本复验

- W3：订单、资金、退款、权限、核销、幂等、并发、恢复和真实数据库检查全部通过。
- Web Admin：在支持矩阵内用 Chrome 对真实 API 执行主路径与错误路径 E2E。
- 小程序普通 UI 最低 UI2；`wx.login`、手机号、支付、扫码、订阅消息最低 UI3。
- 使用正式 AppID、受控测试账号/商户、真机和公网回调；记录未验证边界，不得用模拟器替代。
- writer 产生完整 candidate SHA 后，由另一 clean detached worktree 对同一 SHA 独立只读验证；源码、规格、测试、环境或 SHA 变化后旧回执立即失效。

## 7. 每个版本必须使用的评审清单

### 产品与范围

- [ ] 页面、入口、文案和埋点只包含已确认一期范围，无“即将上线”或已否决占位功能。
- [ ] 普通用户、员工、商家成员、商家 owner、PC 管理员的入口和责任边界明确。
- [ ] 每个状态、价格、时间、权限和成功结果都有唯一服务端事实源。

### 用户主流程

- [ ] 匿名浏览、登录、手机号授权拒绝/成功、员工价与普通价均有真实场景。
- [ ] 日期、时段、截止时间、跨日、售罄和服务日期由服务端校验。
- [ ] 支付成功、取消、失败、超时、状态未知、重复点击和回调重放均不产生假订单。
- [ ] 取餐码只在合法状态展示；取消、退款和订阅消息与最终订单状态一致。

### 商家与 Admin

- [ ] 未授权用户无法看见或调用商家/Admin 能力；直接 URL/API 访问同样被拒绝。
- [ ] 用户订单、商家履约、Admin 管理和财务对账读取同一订单事实。
- [ ] 预约、生产、待取餐、完成、取消、退款状态迁移由服务端控制且不可越级。
- [ ] 真机扫码、四位人工码、当前服务日期、重复核销和审计全部通过。
- [ ] 按日售罄、员工白名单、商家账号、基础设置、待支付、退款和对账均有真实 API 与错误态。

### UI/UX 与兼容性

- [ ] 目标机型/分辨率下无裁切、遮挡、低对比、不可点击假控件或错误按钮状态。
- [ ] 空、加载、错误、重试、无权限、网络中断和重复操作状态清楚且 fail closed。
- [ ] 页面文案不把本地演示数据、异步处理中状态或未知状态描述为最终成功。

### 工程与证据

- [ ] 测试断言权威业务不变量，而不是固化 mock 行为；默认脚本包含全部应运行测试。
- [ ] API provider、全部 consumer、数据库、微信平台和最终数据均有对应证据。
- [ ] 当前候选 exact SHA、运行环境、账号类型、AppID/商户环境和未验证边界已记录。
- [ ] 独立验证使用 clean detached worktree；候选、规格、测试或环境变化后重新验证。
- [ ] 日志和证据不包含手机号、openid、登录 code、Cookie、支付回调原文、证书/密钥或可重放二维码。

## 8. 当前可保留的设计基础

- 小程序与 Web Admin 的配色、卡片、状态标签和信息层级已经形成一致的视觉语言，可在接入真实业务后继续使用。
- 菜单请求失败页有明确错误说明和重试入口，具备 fail-closed 的展示基础。
- 后端已经存在菜单按服务日期读取、`product_sold_out_dates`、小程序 session 和主手机号能力，可作为后续闭环的已有下层基础；但当前客户端和管理写链路尚未接通。
- Web Admin 的员工导入、商家账号和设置页面具备较完整的表单/展示原型，可保留 UI 结构，不能保留内存数据层作为正式实现。

只有当 P0/P1 清零、P2 清零或获明确延期批准，并且 Gate A-E 全部取得当前候选版本的真实证据后，整体 verdict 才能从 `NO-GO` 改为 `GO`。
