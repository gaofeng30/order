# 企业自营餐饮小程序资料准备精细清单

适用范围：个人开发者为商业机构开发企业自营餐饮小程序。当前首期聚焦餐饮点餐、到店自提、订单管理、在线支付；未来可评估外卖、快递、洗车等服务扩展。

核心原则：

- 机构是经营主体、备案主体、收款主体和数据责任主体。
- 开发者负责技术实现、接入指导、材料核验提醒，不应使用个人主体代替机构收款、备案或持有核心资产。
- 首期业务边界建议写成“企业自营餐饮门店服务”，不要写成“外卖平台、多商户平台、快递服务”等高资质业务。

| --- | --- | --- | --- | --- | --- |
| A01 | 营业执照 | 小程序认证、备案、微信支付、餐饮类目审核、合同主体确认。 | 彩色扫描件或照片；信息完整、清晰、无遮挡。 | 企业名称、统一社会信用代码、经营范围、有效期是否清晰；主体是否与项目合同一致。 |  |
| A02 | 统一社会信用代码 | 多个平台填写主体信息时需要，需与营业执照一致。 | 文字版提供。 | 不要手输错误，建议从营业执照复制核对。 |  |
| A03 | 法定代表人姓名与身份证 | 认证、备案、支付进件、法人授权和必要的人脸核验。 | 身份证正反面彩色照片；必要时法人配合扫码/人脸。 | 身份证有效期是否充足；姓名是否与营业执照法人一致。 |  |

| A05 | 小程序负责人信息 | 小程序备案、平台审核联系、问题通知。 | 姓名、身份证号、手机号、邮箱、微信号。 | 可与主体负责人相同，也可不同；需提前确认谁负责接收通知。 |  |
| A06 | 企业联系人 | 日常项目沟通、材料补充、上线协调。 | 姓名、手机号、微信、邮箱。 | 至少指定 1 名业务负责人和 1 名技术/运营对接人。 |  |
| A07 | 公章配合人 | 承诺函、授权书、补充说明、合同和部分平台材料需要盖章。 | 姓名、联系方式、盖章流程说明。 | 确认盖章周期，避免卡住备案或审核。 |  |

| B06 | 取餐地点 | 到店自提和核销流程需要。 | 文字说明，可附现场照片。 | 是否需要按窗口、楼层、柜台区分。 |  |
| B07 | 门店照片 | 辅助审核、页面展示、门店可信度。 | 门头、店内、后厨/经营场所照片。 | 图片是否清晰；是否与门店名称、地址一致。 |  |
| B08 | 多门店关系说明 | 若后续支持多门店，需要明确主体和权限。 | 门店清单、每店许可证、负责人、地址、营业时间。 | 首期是否单门店；多门店是否同一主体或分支机构。 |  |

| C05 | 是否已有公众号/服务号 | 可能用于复用认证、菜单入口、用户运营。 | 提供公众号名称、主体、管理员。 | 主体是否一致；是否要关联小程序。 |  |
| C06 | 小程序备案材料 | 小程序发布前通常需要备案。 | 主办单位证件、负责人证件、手机号、前置审批材料等。 | 备案负责人需及时完成短信核验；业务描述与类目一致。 |  |

## 四、域名、云服务与备案资料

| 编号 | 机构需提供 | 为什么需要 | 物料提供方式 | 开发者核验点 | 完成状态 |
| --- | --- | --- | --- | --- | --- |
| D01 | 云服务商选择 | 决定服务器、备案接入、域名解析、运维方式。 | 选择腾讯云、阿里云或其他。 | 微信小程序项目可优先考虑腾讯云；已有阿里云资产可沿用。 |  |
| D02 | 企业云账号 | 服务器、数据库、对象存储、备案资源建议归机构所有。 | 机构注册企业账号，开发者用子账号/协作权限。 | 避免使用开发者个人云账号长期承载客户生产系统。 |  |
| D03 | 域名 | 小程序请求后端必须使用 HTTPS 合法域名。 | 机构企业主体购买并实名。 | 域名持有人尽量与备案主体一致。 |  |
| D04 | 域名备案资料 | 中国大陆服务器/API 对外服务通常需要 ICP 备案。 | 营业执照、负责人证件、手机号、域名证书/域名信息。 | 备案主体、云资源、域名主体尽量一致；负责人配合短信核验。 |  |
| D05 | SSL 证书 | 小程序接口必须走 HTTPS。 | 可由云平台申请免费或付费证书。 | 确认证书绑定域名，例如 `api.example.com`。 |  |
| D06 | 服务器预算 | 决定技术部署方案和性能边界。 | 月/年预算、预计订单量、图片量、并发量。 | 低价云资源不等于 24 小时运维保障，需另列维护范围。 |  |
| D07 | 生产/测试环境要求 | 避免测试数据污染生产订单和支付。 | 确认是否需要测试环境。 | 建议至少区分测试配置和生产配置。 |  |

## 五、微信支付与财务资料

| 编号 | 机构需提供 | 为什么需要 | 物料提供方式 | 开发者核验点 | 完成状态 |
| --- | --- | --- | --- | --- | --- |
| E01 | 微信支付商户号 | 小程序在线支付、退款、对账、结算。 | 如已有，提供商户号和管理员；如没有，机构申请。 | 商户主体应与小程序主体或合规授权关系一致。 |  |
| E02 | 对公银行账户 | 微信支付结算和账户验证。 | 开户名、开户行、银行账号。 | 开户名通常需与营业执照主体一致。 |  |
| E03 | 经营类目 | 支付进件和费率判断。 | 按餐饮实际业务填写。 | 不要填写与实际业务不符的类目。 |  |
| E04 | 客服电话 | 支付进件、用户售后、平台要求。 | 可公开电话。 | 必须可接通，建议与门店电话或客服专线一致。 |  |
| E05 | 退款负责人 | 线上支付后需要明确退款审核责任。 | 姓名、手机号、后台角色。 | 谁能审核退款，谁能查看财务数据。 |  |
| E06 | 对账需求 | 后台报表、财务核算、经营分析。 | 说明按日/月、按门店、按菜品还是按订单导出。 | 首期可先支持订单导出，后续再做复杂财务报表。 |  |

## 六、菜品、订单与运营规则

| 编号 | 机构需提供 | 为什么需要 | 物料提供方式 | 开发者核验点 | 完成状态 |
| --- | --- | --- | --- | --- | --- |
| F01 | 菜品分类 | 首页和点餐页展示。 | 表格提供，例如套餐、热销、轻食、汤饮。 | 分类数量不要过多，首期保持清晰。 |  |
| F02 | 菜品清单 | 商品建模、购物车、订单明细。 | 表格：名称、分类、价格、描述、状态。 | 是否有重复菜名、临时菜、每日菜。 |  |
| F03 | 菜品图片 | 商品展示和转化。 | 每个菜品 1 张或多张高清图。 | 图片比例、风格、版权。 |  |
| F04 | 规格和口味 | 影响购物车、价格、库存和订单备注。 | 表格列出规格、加料、口味、默认选项。 | 规格是否影响价格；口味是否只是备注。 |  |
| F05 | 库存规则 | 避免超卖和售罄后继续下单。 | 按菜品每日库存、是否自动重置。 | 是否需要每日自动恢复库存。 |  |
| F06 | 上下架规则 | 商户后台管理菜品。 | 谁可以上架/下架，是否立即生效。 | 订单中已售商品不应因下架丢失历史信息。 |  |
| F07 | 取餐规则 | 到店自提流程核心。 | 取餐时间、取餐号规则、是否扫码核销。 | 是否需要小票打印、二维码核销。 |  |
| F08 | 堂食规则 | 如涉及桌号点餐，需要额外流程。 | 是否支持桌号、扫码点餐、餐后支付。 | 首期若不做，页面不要暗示支持。 |  |
| F09 | 配送规则 | 当前如不做配送，应明确为后续预留。 | 是否自配送、配送范围、配送费、配送时间。 | 如果未来做第三方外卖平台，要重新评估资质。 |  |
| F10 | 订单取消规则 | 支付后用户是否可取消。 | 文字规则：未接单、已出餐、已完成等状态。 | 需要映射成订单状态机。 |  |
| F11 | 退款规则 | 支付退款、售后处理。 | 哪些状态可退款、是否自动退、谁审核。 | 与微信支付退款接口和后台权限匹配。 |  |
| F12 | 发票规则 | 用户咨询和企业财务要求。 | 是否支持发票、开票类型、开票入口。 | 首期不做在线开票时需写清楚线下处理方式。 |  |

## 十一、建议的推进顺序

1. 机构确认业务模式：首期为企业自营餐饮，不做平台型外卖、快递收派、多商户入驻。
2. 机构提供营业执照、法人身份证、食品经营许可证、门店信息。
3. 开发者核对类目和资料缺口，输出风险清单。
4. 机构注册或确认小程序账号，并完成企业认证。
5. 机构申请或确认微信支付商户号。
6. 机构购买企业主体域名和云资源，开发者协助配置。
7. 完成域名 ICP 备案和小程序备案。
8. 开发者完成小程序端、商户后台、支付接入、部署配置。
9. 机构提供菜品、图片、价格、营业时间、退款售后规则。
10. 双方按验收标准测试，提交小程序审核并上线。

## 十二、首期边界建议

首期建议包含：

- 用户浏览菜品、加入购物车、提交订单。
- 在线支付。
- 到店自提和取餐核销。
- 商户后台查看订单、管理菜品、管理分类、设置营业状态。
- 基础数据看板。
- 退款/售后流程的基础支持。

首期建议暂不包含：

- 多商户入驻。
- 平台型外卖。
- 快递收件/派件。
- 洗车服务。
- 储值卡/预付卡。
- 复杂财务结算和分账。
- UGC 社区、评论广场、直播、营销裂变等高审核风险功能。
