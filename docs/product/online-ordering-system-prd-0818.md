## 1. 项目背景

本系统用于企业承包政府或企业单位餐饮服务后的在线点单场景。用户通过微信小程序浏览菜品、加入购物车、提交订单，并在线下窗口自提。商户通过小程序商户端或 PC 网页后台维护菜品、价格、图片、库存、上下架状态、订单履约和经营数据。

系统首期目标不是做完整外卖平台，而是先稳定解决"单位内部/访客点餐、自提、商户后台管理、基础经营统计"这几个核心问题。

## 2. 产品目标

- 降低用户排队和人工点单成本，让用户提前完成选餐和下单。
- 让商户可自主维护每日供应菜品、价格、图片、份数和上下架状态。
- 让取餐窗口可以通过取餐号或二维码快速核销，减少错餐和漏单。
- 让经营方可以查看每日与每月营收、订单量和单品销售数据。
- 在 500 人以内使用规模下，优先保证稳定、清晰、易维护。

## 3. 交付范围与形态

### 3.1 范围基线

> 本节含 §16 需人工复查条目（预约点餐、PC 网页后台、品牌多业务首屏、外卖占位），对外沟通合同范围时需先复查，不宜整节直接表述为"已确认范围"。

- 用户入口：微信小程序。
- 用户范围：单位员工 + 外部访客。
- 履约方式：线下自提，支持**即时单**与**预约单**两种取餐方式。
- 取餐凭证：取餐号 + 订单二维码。
- 商户入口：**小程序商户端**（现场高频操作）+ **PC 网页后台**（批量与配置操作）。
- 支付：微信支付，资金进入餐饮企业的微信支付商户号。
- 外卖配送：首期不开发，仅在 UI 中保留"暂未开放"占位入口。
- 视觉方向：商务蓝 + 绿色。

### 3.2 一期交付形态

系统由三个前端形态构成，共用同一套业务数据：

| 形态 | 载体 | 使用者 | 主要任务 |
| --- | --- | --- | --- |
| 用户端 | 微信小程序 | 单位员工、访客 | 浏览、点单、支付、凭码自提 |
| 商户端 | 同一微信小程序，启动时分流 | 窗口、后厨 | 出餐推进、核销、临时改售罄 |
| PC 网页后台 | 浏览器 | 店长、管理员 | 菜品与分类维护、订单查询与退款、营业设置、名单批量导入 |

小程序冷启动首屏为**品牌选择页**（绥安食品 / 绥安洗衣 / 绥安洗车，后两个标注"即将上线"），选定后进入身份选择页，再分流到用户端或商户端。

### 3.3 页面清单

**用户端（11 屏）**：品牌选择、启动选择、首页、菜单点单、菜品详情、确认订单、支付/预约结果、取餐码与订单详情、我的订单、个人中心、我的优惠券（二期）。

**小程序商户端（16 屏）**：工作台、订单管理、订单详情、扫码核销、菜品管理、菜品编辑、分类管理、商户中心、营业设置、开屏图层、会员等级（二期）、会员名单（二期）、名单导入（二期）、会员编辑（二期）、优惠券列表（二期）、优惠券编辑（二期）。

**PC 网页后台（11 页）**：工作台、订单管理、扫码核销、菜品管理、分类管理、营业设置、开屏图层、会员等级（二期）、会员名单（二期）、批量导入名单（二期）、优惠券（二期）。

> 标注"二期"的页面属于会员等级 / 会员名单 / 优惠券能力，不在一期合同范围。界面与接口契约先行落地，实际上线需先签补充协议或需求变更单。

## 4. 角色与权限

### 4.1 普通用户

包括单位员工和外部访客。能力：微信授权登录；浏览菜品、分类、价格、图片、售罄与上下架状态；加入购物车；提交即时单或预约单；查看取餐号、二维码、订单状态与历史订单；凭码自提；在规则允许范围内取消订单。

员工与访客的差异：员工可绑定手机号、姓名、部门、工号；访客可用手机号、姓名下单。

### 4.2 商户管理员

管理商品分类；管理商品名称、价格、图片、描述、餐段可售、每日投放份数和上下架状态；查看订单列表与详情；推进订单状态；发起退款；查看营收与销量数据；设置营业时间、餐段、截单时间、取餐地点和公告；管理后台子账号。

### 4.3 取餐核销员

查看待取餐订单；扫码核销；手动输入取餐号核销；查看订单口味与备注避免错餐。

限制：不应拥有商品价格、财务数据、退款、账号权限等能力。

### 4.4 平台/超级管理员

管理商户基础信息；配置支付参数与小程序发布配置；查看运行日志与异常记录；管理后台账号与权限；处理特殊订单与数据修正。

首期只服务单一餐饮企业，平台能力可弱化到运维后台或配置项中。

## 5. 用户端功能

### 5.1 首页

首页需要让用户在三秒内理解"现在能不能点、点什么、什么时候取"。

功能要求：

- 展示门店名称、地址、当前餐段与截单时间。
- **展示营业状态**：营业中 / 休息中 / 已截单（D16）。
- **展示门店公告**：取餐地点、今日提示、临时停供等，内容来自商户后台的门店公告字段（D17）。
- 营销 Banner 轮播，点击跳转对应菜品或菜单。
- 服务宫格：到店点单、预约点餐、我的订单、取餐码、会员中心、**外卖配送（置灰，标注"暂未开放"）**（D18）。
- 今日招牌横滑卡：展示带"今日推荐""热销"标签且未下架的菜品。
- **下单入口 gating**（D15）：当营业状态为休息中或已截单、或当前处于餐段空档期时，即时下单入口禁用并给出具体原因与替代动作（见 §5.5）。

### 5.2 菜品列表

- 按分类展示菜品，分类锚点导航支持点击定位与滚动反向高亮。
- **只展示当前餐段可售的菜品**（见 §6.3 餐段可售字段）。
- 展示图片、名称、价格、简介、月售、标签。
- 展示售罄、已下架、不可购买状态。
- 支持加入购物车、查看详情。
- **支持按菜品名称搜索**。

菜品状态说明：

| 状态 | 用户端表现 |
| --- | --- |
| 上架且今日剩余 > 0 | 可见且可购买 |
| 售罄（手动标记或今日剩余归零） | 可见、图片带蒙层、按钮禁用 |
| 下架 | 用户端不展示，后台保留 |
| 不在当前餐段 | 用户端不展示 |

### 5.3 菜品详情

- 顶部图廊：最多 3 张，手动滑动、不自动播放、不循环，右下角"2 / 3"计数；单图时不启用滑动、不显示计数；点击进入全屏预览。无图时按品类渐变 + 宋体首字占位。
- 展示名称、价格、月售、标签、描述。
- 展示规格信息与过敏原提示。
- 展示售罄或不可购买状态。
- 支持选择数量、填写口味与备注后加入购物车。

### 5.4 购物车与菜品级偏好

**口味与备注挂在菜品级**（D25）。每个菜品在加购时打开偏好弹层，填写：

- 数量；
- 口味多选：少饭 / 加饭 / 少盐 / 加辣 / 酱汁分装 / 免葱蒜 / 打包分装 / 多双餐具；
- 该菜品的备注文本。

购物车要求：

- 展示已选菜品、数量、单价、小计、已填的口味与备注。
- 支持修改数量、重新编辑偏好、删除商品、清空购物车。
- 自动计算总价。
- 售罄或下架商品需提示用户重新选择。
- 提交订单前再次校验价格、库存、餐段与营业状态。

> 订单不再有整单级的口味与备注字段。窗口看到的是"哪道菜要怎么做"，而不是一条需要人工拆解的整单备注。

### 5.5 确认订单页

- **取餐方式二选一**：
  - **尽快取餐**（即时单）：下单后立即制作，展示预计可取时间。
  - **预约取餐**（预约单）：选择日期（今天 / 明天 / 后天）与取餐时段，时段按餐段分组。
- **餐段空档期行为**（D11）：当前不在任何餐段的接单时间内时，"尽快取餐"禁用并提示（例："午餐已截单，可预约晚餐"），引导用户切换到预约；菜单仍可浏览。
- 展示取餐窗口（一期单点，见 §6.6）。
- 展示商品明细，逐项显示口味与备注，可就地重新编辑。
- 展示优惠明细（二期能力，见 §5.10）。
- 填写联系人与手机号。
- 展示应付金额，提交订单。

### 5.6 支付

首期方案：微信支付直连餐饮企业商户号。

1. 用户提交订单，系统创建待支付订单（**此时不占库存**）。
2. 用户发起微信支付。
3. **支付成功即扣减库存**（D5）；若此时今日剩余已不足，支付被拦截并提示重选。
4. 即时单进入「待制作」，预约单进入「已预约」。
5. 资金直接进入餐饮企业微信商户号。

### 5.7 订单列表

- 按状态筛选：全部 / 待支付 / 已预约 / 待取餐 / 已完成 / 已取消（含已退款）。
- 展示订单号、取餐号、金额、下单时间、取餐方式与状态。
- 预约单额外展示预约取餐时间。
- 待支付订单提供"去支付"入口，跳转的是**该笔订单的支付**，不是重新下单。

### 5.8 订单详情

- 展示取餐号（大号）与取餐二维码。
- 展示订单状态、订单号、菜品明细（含每道菜的口味与备注）。
- 展示实付金额与支付状态。
- 展示取餐地点、预计或预约取餐时间、联系人。
- 支持复制取餐号。
- **预约单在取餐前 30 分钟之前可自助取消**，取消后款项原路退回（D12）；进入 30 分钟窗口后不再提供取消入口，需联系商户。

### 5.9 通知提醒

首期支持微信订阅消息。可提醒事件：下单成功、支付成功、可取餐、订单完成、退款结果、临时停餐或菜品变更。

### 5.10 会员权益与优惠券（二期能力 · 不在一期合同范围）

身份识别：用户授权手机号，服务端用 `getPhoneNumber` 返回的 code 换取明文手机号后与商户名单比对，命中即判定等级。名单是会员的唯一来源，无"申请入会"入口。

我的优惠券页：展示会员姓名、等级、常驻折扣与可用券数；券分可用 / 已用完 / 已过期三态；券由商户按等级发放后自动进入卡包，用户无领取动作。

确认订单页优惠明细：依次展示商品小计、等级折扣、优惠券三行；默认自动选中优惠力度最大的可用券；不可用券不隐藏，置底并给出具体原因。

## 6. 商户后台功能

小程序商户端与 PC 网页后台共用同一套数据与规则，差异只在操作形态（见 §6.16）。

### 6.1 登录与权限

- 后台账号密码登录。
- 角色权限：商户管理员、核销员、平台管理员。
- 账号启用、禁用、改密码。
- 关键操作记录操作日志。

### 6.2 商品分类管理（D22）

- 新增、编辑、**删除**分类；删除前校验旗下菜品，需先迁移或拦截。
- **排序用上移 / 下移按钮**，不做拖拽。
- 设置分类启用 / 停用，停用后用户端隐藏该分类及其菜品。
- **改动落库**，且菜品编辑页的分类选项**读取真实分类数据**，不使用写死常量。

### 6.3 商品管理

- 新增、编辑商品：名称、分类、价格、图片、描述、排序。
- **餐段可售**：全天 / 仅午餐 / 仅晚餐，三选一（D10）。菜单按当前餐段过滤展示。
- 设置上下架、手动售罄。
- 设置每日投放份数（见 §6.5）。
- **支持按名称搜索**（D20）。
- 支持按分类、状态筛选。
- 图片要求见 §6.14。

### 6.4 价格与规格

- 单品固定价格。
- 商品价格变更后，新订单使用新价格，历史订单保留原成交价。
- 首期不做多规格差价；规格信息作为展示字段。

### 6.5 库存与售罄（本版核心机制）

手动接单取消后，"今天还能不能卖"完全由库存与售罄承担。商户的决策前置到每天设份数这一步，出餐环节只剩执行。

**两个量，不要混用：**

| 量 | 含义 | 谁维护 |
| --- | --- | --- |
| **每日投放份数** | 这道菜每天做多少份 | 商户配置，明天沿用 |
| **今日剩余** | 今天还能卖多少份 | 系统计算，只读展示 |

**规则：**

1. 商户在后台维护的是**每日投放份数**；界面同时显示**今日剩余**（D2）。
2. **每日 00:00 重置**：今日剩余 = 每日投放份数。投放份数沿用前一日设定，除非商户手动修改（D3）。
3. 商户手动标记的**「售罄」在次日 00:00 随重置自动解除**（D4）。
4. **支付成功才扣减**；待支付订单不锁量（D5）。因此最后一份菜可能被多人同时下到确认页，**支付时必须二次校验并拦截后付方**。
5. **预约单不预扣**目标日库存；在**取餐当天**先计入当日计数，剩余份数才卖给即时单（D13）。
6. **今日剩余归零 → 自动置售罄**，与商户手动售罄是同一终态：用户端可见、带蒙层、不可下单。
7. **取消或退款成功 → 自动返还**一份，重新可售（D6）。
8. 支持**不限量**：饮料等品类可不设份数，卖完由商户手动点售罄（D7）。
9. 今日剩余 ≤ 8 视为**库存告急**，在商户端标红提示补货。

> 全天可售的菜品共享同一个每日份数——本来就是同一锅。若某道菜需要午晚分开管控，把它拆成两个菜品并分别设为"仅午餐""仅晚餐"。

### 6.6 营业设置与餐段

**餐段（D8）**：一期为**午餐**与**晚餐**两段，不支持早餐。餐段是一等公民，决定菜单展示、预约时段分组、截单时间和即时下单可用性。

每个餐段需配置三个参数：

| 参数 | 说明 |
| --- | --- |
| 开始接单时间 | 该餐段开放即时下单与预约下单的起点 |
| 截单时间 | 到点停止接单，**固定时刻**，不随取餐时间滚动（D9） |
| 取餐时段 | 该餐段可选的预约取餐时间槽位 |

**截单规则（D9）**：按餐段固定截单。上一版前端使用的"距取餐时刻 ≥40 分钟"滚动提前量规则**废弃**，两套规则不并存。

**餐段空档期（D11）**：两个餐段之间（例：午餐已截单、晚餐未开始接单）不可即时下单，菜单可浏览，引导转预约。

**营业状态**：营业中 / 休息中 / 已截单，商户可手动切换，覆盖营业时间规则。休息中与已截单时用户端下单入口禁用。

**取餐地点（D24）**：一期为**单点**。多取餐点选择不在一期范围，前端预置的多点演示数据一并拆除。

**门店公告**：多行文本，展示在用户端首页（D17）。

### 6.7 订单管理

- 订单列表按状态泳道展示：**已预约 / 待制作 / 待取餐 / 已完成 / 已取消 / 已退款 / 全部**。
- **搜索栏**：按取餐号、订单号、手机号搜索（D19）。
- 按下单时间筛选。
- 查看订单详情，含每道菜的口味与备注（金色高亮，制作提醒）。
- 推进订单状态（见 §7.1）。
- 支持取消订单、发起退款、导出订单。

### 6.8 核销与退款

**核销**：

- 扫码核销订单二维码；支持手动输入取餐号。
- 核销前展示订单内容，避免错餐。
- 已核销订单不可重复核销，重复扫码提示"订单已完成"。
- 已取消、已退款订单不能核销。
- 核销记录保存核销人、核销时间、核销方式。

**退款（D14）**：

- 商户后台订单详情内置**「退款」按钮**，调用微信支付退款接口。
- 退款成功 → 订单置**「已退款」**终态，库存自动返还。
- 退款失败 → 报错并保留原状态，不引入"退款中"中间态。
- 退款必须关联原订单，金额不超过实付金额；首期只做全额退款。
- 退款记录退款单号、金额、操作人、时间。

### 6.9 数据看板

**指标（D21）**：

- 当日营收、当日订单、当月营收、当月订单。
- 单品销量排行，**数据来自真实订单**，不使用写死常量。
- 待办：待制作数、待取超时数、库存告急数。

统计口径：营收以支付成功订单为准，退款订单从营收中扣除；单品销量以已支付或已完成订单明细为准。

> 访问量与点击量不在本版范围，系统不建设埋点体系。

### 6.10 财务与对账

微信支付直连方案：

- 后台展示订单支付金额、支付时间、微信交易号。
- 支持按日期导出订单明细。
- 支持对账时核对微信支付账单。
- 退款需要记录退款单号、退款金额、退款状态与操作人（与 §6.8 同源，不重复维护）。

> 交班对账为规划中能力，当前仅在商户中心保留入口占位。

### 6.11 会员等级管理（二期能力 · 不在一期合同范围）

档位可自由增删、改名、排序；等级有序，一人一档。每档配置一个常驻折扣率，对该等级全部会员的每一单生效。等级由商户手动指定，不按消费自动升降级。删除档位强制走迁移弹层，并自动从券的适用等级中摘除；券因此没有任何适用等级时自动停用。至少保留一个等级。

### 6.12 会员名单管理（二期能力 · 不在一期合同范围）

字段：手机号（唯一识别键，必填）、姓名（必填）、会员等级（必填）、单位/部门/工号（选填）、备注（选填）、状态（默认启用）、加入时间（自动）、已绑定（只读）、累计消费与单量（只读）。

录入方式：手动逐条添加；CSV 批量导入。小程序端需先把文件发到微信聊天再用 `wx.chooseMessageFile` 选择；PC 后台可直接选文件。Excel 默认另存的 CSV 为 GBK 编码，导入页做显式检测并提示"另存为 CSV UTF-8"。导入前必须预览：新增 N 条、更新 M 条、异常 K 条，异常项可展开查看行号与原因。去重规则为按手机号覆盖更新，保留加入时间、累计消费与微信绑定关系。

### 6.13 优惠券配置（二期能力 · 不在一期合同范围）

券按等级自动生效，无领取动作，不设发放总量，成本控制依靠有效期与每人可用次数。

字段：券名称、类型（满减 / 折扣）、面额、封顶金额（折扣券必填）、使用门槛、适用等级（多选，至少 1 档）、适用商品范围（全场 / 指定分类 / 指定菜品）、有效期、每人可用次数、状态。

范围联动：选中分类为动态包含，后续新增到该分类的菜品自动纳入；菜品被删除时自动从券的范围中摘除，摘空则该券自动停用。

### 6.14 菜品图片

- 每个菜品最多 3 张图片，第一张为封面。
- 菜单列表、购物车、订单、后台列表一律只用封面，不引入额外的封面字段。
- 商户可删除任意图片，非首张图片可一键「设为封面」并移到第一位。
- 不做拖拽排序：小程序需借助 `movable-view` 实现，成本远高于价值。
- 图片经上传接口存入对象存储后写入菜品记录，不落本机存储。

### 6.15 开屏图层（D23）

- 商户上传一张透明 PNG，在等比缩放的手机预览上拖拽定位、滑杆调整大小。
- 保存后展示在品牌选择页与身份选择页。
- **图片上传至对象存储，配置存服务端，向所有用户下发**。不使用 `wx.setStorageSync` 或本机文件——商户端与用户端是不同的人、不同的设备，本机存储在架构上不成立。

### 6.16 两个商户端形态的分工

| | 小程序商户端 | PC 网页后台 |
| --- | --- | --- |
| 定位 | 现场高频、单手操作 | 批量、配置、查询 |
| 强项 | 扫码核销、出餐推进、临时改售罄 | 菜品与分类批量维护、订单查询与退款、营业设置、CSV 导入 |
| 营业设置 | 状态切换 | 完整可编辑表单（营业时间、截单、取餐点、公告） |

两端共用同一套数据与规则，任一端的修改对另一端立即可见。

## 7. 订单履约流程

### 7.1 即时单流程

1. 用户浏览菜品并加入购物车，逐菜填写口味与备注。
2. 用户在确认订单页选择"尽快取餐"，填写联系人与手机号。
3. 系统校验营业状态、餐段、商品状态、价格和今日剩余。
4. 用户完成微信支付，**支付成功扣减库存**。
5. 订单**直接进入「待制作」**（D1，无接单步骤）。
6. 商户端新单提醒 + 工作台待办计数，后厨按序制作。
7. 商户点「备好」→ 订单进入「待取餐」。
8. 用户到窗口出示取餐号或二维码。
9. 核销员扫码或输入取餐号，订单置「已完成」。

> 取消手动接单的理由：用户已在线支付成功、菜品在售即等于承诺供应、自提无配送时效压力，商户在此处没有真实的拒单决策。"确认已看到订单"的诉求由新单提醒与待办计数承担，而不是由一个每单都要点一次、高峰期必然被批量跳过的确认按钮承担。

### 7.2 预约单流程

1. 用户在确认订单页选择"预约取餐"，选择日期（今天 / 明天 / 后天）与取餐时段。
2. 支付成功后订单进入**「已预约」**，**不预扣**目标日库存。
3. 取餐当天，该预约单**计入当日库存计数**（D13）。
4. **取餐前 30 分钟**，订单**自动进入「待制作」**；同一时刻起用户不可自助取消（D12）。
5. 后续与即时单一致：备好 → 待取餐 → 核销 → 已完成。

### 7.3 订单编号规则

- 系统订单号：用于唯一识别与对账，例如 `SA + YYYYMMDD + 流水`。
- 取餐号：用于窗口叫号，即时单与预约单使用不同前缀以便现场区分。
- 二维码内容：使用订单核销 token，不直接暴露敏感用户信息。

要求：订单号必须唯一；取餐号在同一天、同一餐段内不可重复；已取消订单的取餐号不复用。

### 7.4 核销

- 用户订单详情页展示二维码与取餐号。
- 核销员扫码后展示订单号、取餐号、菜品明细与状态。
- 核销成功后订单变为已完成。
- 已完成、已取消、已退款订单不能再次核销。
- 手动核销需要记录操作人和时间。

### 7.5 取消订单

| 场景 | 规则 |
| --- | --- |
| 未支付订单 | 用户可直接取消，或超时自动关闭 |
| 已支付即时单 | 不提供用户自助取消，联系商户处理 |
| 已支付预约单，距取餐 > 30 分钟 | **用户可自助取消**，款项原路退回，库存返还（D12） |
| 已支付预约单，距取餐 ≤ 30 分钟 | 已进入制作，不可自助取消，联系商户处理 |
| 已完成订单 | 不可取消 |

### 7.6 退款

- 退款由商户在后台发起（§6.8）。
- 退款成功 → 订单置「已退款」，**库存自动返还**（D6）。
- 退款金额不超过实付金额，首期只做全额退款。
- 退款失败保留失败原因，方便人工处理。

## 8. 版本拆分

### 8.1 一期交付

用户端：微信登录；首页（含营业状态、公告、gating）；菜品列表与搜索；菜品详情图廊；购物车与菜品级偏好；即时单与预约单；微信支付；订单列表与详情；取餐号与二维码。

商户端（小程序 + PC）：登录与角色；分类管理（落库、删除、联动）；菜品管理（搜索、餐段可售、每日投放份数、多图）；库存与售罄机制；营业设置与餐段配置；订单管理（泳道、搜索、推进）；扫码与手动核销；退款；数据看板；开屏图层。

系统能力：订单编号；库存每日重置定时任务；预约单排产定时任务；权限控制；操作日志；支付与退款状态记录；异常订单记录；数据备份。

### 8.2 后续增强

- 员工身份绑定与访客下单限制。
- 部分退款与退款审核流。
- 订单导出与更完整的经营报表。
- 微信订阅消息全量事件。
- 后台子账号权限细分。
- 打印机与后厨屏对接。

### 8.3 明确不做

外卖配送与配送地址、评价系统、排队叫号屏、多门店与多档口、发票、企业月结、第三方 ERP 对接、按消费自动升降级、商品券（免费换购）、定向发券给指定个人、时段预约名额。

### 8.4 二期能力：会员等级与优惠券

合同 `online-ordering-system-contract-final.md` 第 31、108、321、420 条已将"会员体系、优惠券、积分、储值卡、预付卡"排除在第一期交付范围之外。本次交付的定位是**方案与界面提案**：界面、算价引擎、前后端接口契约已完成；服务端实现待签补充协议后随一期后端统一开发。对客户展示时必须标注"二期能力 · 不在一期合同范围"。

## 9. 非功能要求

### 9.1 稳定性

- 关键链路（浏览、下单、支付回调、库存扣减、核销、退款）优先保证稳定。
- 支付回调需幂等，避免重复写入支付状态与重复扣减库存。
- 核销操作需幂等，避免重复核销。
- **库存扣减必须在服务端串行化**，防止最后一份被并发超卖。
- 每日 00:00 重置与预约排产为定时任务，需具备重试与补偿；任务漏跑不得导致当日不可售。
- 系统异常时给用户明确提示，不展示技术错误。

### 9.2 容量预估

已知人数上限约 500 人。同时在线 100–200 人；短时集中下单 5–10 分钟内 100–300 单；日订单量 500–1000 单；商品数量 100–300 个。

### 9.3 安全与权限

- 用户只能查看自己的订单。
- 核销员不可改商品、价格，不可退款。
- 商户管理员只能管理本商户数据。
- 后台敏感操作（改价、退款、删菜品、删分类）记录日志。
- 支付参数、密钥、证书不可暴露给前端。
- 二维码核销 token 需签名或随机，避免被猜测。

### 9.4 数据备份

订单、支付、退款、核销数据定期备份；商品与配置变更保留操作记录；重要数据软删除；支持按日期导出订单和销售数据。

### 9.5 异常处理

常见异常：支付成功但订单未更新；支付回调重复到达；下单时今日剩余已归零；商户临时下架商品；二维码重复扫码；提交按钮重复点击；退款失败；定时任务漏跑。

处理要求：支付状态以服务端和微信支付结果为准；提交订单按钮防重复提交；后台可筛选异常订单；异常保留日志。

### 9.6 可维护性

- 商品、订单、库存、支付、统计模块边界清晰。
- 订单状态流转规则唯一且明确。
- 统计口径写在后台说明中。
- 餐段时间、截单时间、库存重置时点等配置项优先后台可配。

## 10. UI 与体验要求

### 10.1 视觉风格

主色商务蓝，辅助色绿色用于成功、可购买、已完成等正向状态。风格稳重、清晰、低噪音。精确色值与尺寸规范见 §15.2。

### 10.2 用户端体验原则

- 用户 3 步内完成核心操作：选菜、确认、下单。
- 菜品状态必须清楚：可买、售罄、已截单、不在当前餐段。
- 不可下单时必须给出**原因和替代动作**，不能只是禁用。
- 取餐号和二维码要足够醒目。
- 外卖入口必须明确标注暂未开放。

### 10.3 商户端体验原则

- 上下架、售罄、改份数要一步到位。
- 订单列表适合窗口高频查看，出餐推进每单只有一个主按钮。
- 核销页面步骤最少。
- 看板优先展示经营方每天最关心的数据。

## 11. 数据统计口径

后台统计：每日订单数、每日营收、每月订单数、每月营收、单品销量、单品销售额、支付成功率、取消与退款数量。

口径说明：

- 财务数据以支付成功和退款结果为准。
- 单品销量以已支付或已完成订单明细为准。
- 退款订单从营收中扣除。

> 本版不建设访问量与点击量埋点，看板不提供相关指标。

## 12. 关键业务规则

- 下单以后端实时价格为准，前端展示价格只作参考。
- 订单提交后，明细中的商品名称、价格、数量固化，后续改价不影响历史订单。
- 已售罄或已下架商品不能下单。
- 不在当前餐段的商品不展示、不能下单。
- **库存在支付成功时扣减，不在提交订单时扣减**；支付时必须二次校验今日剩余。
- 取消或退款成功后库存自动返还。
- 已完成订单不能重复核销；已退款订单不能核销。
- 支付成功但前端未跳转时，用户再次进入订单页应能看到正确状态。
- 商户修改营业状态、餐段、售罄后，用户端提交订单时必须重新校验。

### 12.1 会员与优惠券算价规则（二期能力 · 不在一期合同范围）

算价链固定为：**原价小计 → 等级折扣 → 减券 → 应付**。

1. 一单只能使用一张券；券与等级折扣叠加，不择优。
2. 券的门槛判定与减免作用均锚定"可用商品小计"，且作用在等级折扣之后的金额上。
3. 折扣券必须填写封顶金额，减免不超过可用商品小计。
4. 默认自动选中减免金额最大的可用券；已选券因购物车变化而不可用时自动回落。
5. 用户可显式选择"不使用优惠券"。
6. 券按"有效期内每人可用次数"计次，支付成功即计入。
7. 金额一律用"分"做整数运算，仅在展示时转元。
8. 名单是会员的唯一来源，不在名单中一律原价且无券可用。

## 14. 验收标准

一期验收至少满足：

- 用户可在小程序完成浏览、加购（含菜品级口味与备注）、提交即时单与预约单、微信支付。
- 用户可在订单详情看到取餐号和二维码；预约单可在取餐前 30 分钟之前自助取消。
- 餐段切换正确：菜单按餐段过滤，截单后即时下单入口禁用并给出替代动作。
- 库存机制正确：支付成功扣减、归零自动售罄、次日 00:00 重置并沿用投放份数、手动售罄次日自动恢复、取消与退款自动返还、预约单在取餐当天计入。
- 商户端可维护菜品（含餐段可售、投放份数、多图）、分类（落库、删除、联动）、营业设置。
- 商户端可查看并搜索订单、推进出餐、扫码与手动核销、发起退款并置「已退款」。
- 看板展示当日与当月营收及订单，单品销量来自真实订单。
- 开屏图层由服务端下发，换设备后仍可见。
- 关键操作有日志，异常订单可追踪。

## 15.7 订单状态机

**目标态（本版决策）**

```
即时单：待支付 ──支付──▶ 待制作 ──备好──▶ 待取餐 ──核销──▶ 已完成
预约单：待支付 ──支付──▶ 已预约 ──取餐前30分──▶ 待制作 ──备好──▶ 待取餐 ──核销──▶ 已完成
旁路：  待支付 ──超时/取消──▶ 已取消
       任意已支付态 ──商户退款成功──▶ 已退款
```

**当前实现**（`apps/wechat-miniprogram/utils/util.js`）

```js
const NEXT = { 待制作: '待取餐', 待取餐: '已完成' };
const ACT  = { 待制作: '备好', 待取餐: '核销', 已完成: '查看', 已取消: '查看' };
```

差异（待改造）：`已预约 → 待制作` 的自动排产未实现；`已退款` 终态未实现。

- 商户端每个订单卡只暴露**一个主行动按钮**，文案随状态变化：`备好 → 核销 → 查看`。
- **核销**是「待取餐 → 已完成」的唯一路径，核销成功后工作台营收与订单数实时更新。
- 推进操作给 Toast 反馈，**支持「撤销」**（回退到上一状态）。

## 15.11 边界与异常

| 场景 | 期望行为 |
| --- | --- |
| 已截单 / 休息中 | 用户端下单入口禁用并提示；菜单仅浏览 |
| 餐段空档期 | 「尽快取餐」禁用并提示可预约下一餐段 |
| 今日剩余为 0 / 手动售罄 | 菜品按钮禁用 + 蒙层；已加购需在支付前校验并提示 |
| 菜品不在当前餐段 | 用户端不展示；商户端可见 |
| 菜品下架 | 用户端不展示；商户端可见可重新上架 |
| 待支付超时 | 自动转「已取消」，不涉及库存（未支付本就未扣） |
| 支付时今日剩余不足 | 支付被拦截，提示重选，不生成取餐号 |
| 预约单距取餐 ≤ 30 分钟 | 取消入口消失，订单已自动进入待制作 |
| 取消或退款成功 | 库存自动 +1 返还 |
| 每日 00:00 | 今日剩余重置为投放份数，手动售罄解除 |
| 取餐码核销重复 | 已完成单再次扫码提示「已核销」，不重复计数 |
| 已退款订单扫码 | 提示订单已退款，拒绝核销 |
| 网络 / 支付失败 | 停留确认页，可重试，不生成取餐号 |
| 空购物车 | 「去结算」禁用 |
| 无待取订单点首页取餐码 | Toast 提示无待取餐订单 |
| 非会员进入确认页（二期） | 优惠卡显示「非会员 · 原价」，不显示选券入口 |
| 已选券因购物车变化失效（二期） | 自动回落到当前最优可用券 |
| 优惠额度超过应付（二期） | 券减免封顶在应付金额，实付最低为 0 |
| CSV 为 GBK 编码（二期） | 中止并提示「另存为 CSV UTF-8」 |
