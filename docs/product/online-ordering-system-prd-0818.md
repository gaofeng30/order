## 1. 项目背景

本项目为单门店餐饮经营主体提供微信小程序在线点单、微信支付、到店自提，以及配套商户后台。客户是经营、收款、退款、隐私和发布责任主体；开发方负责开发、配置、联调、提审协助、技术排障和运维支持。

客户已认可 P0 原型的视觉与主要交互方向。P0 允许 mock 数据、内存状态、假支付和简化状态机；这些只证明页面蓝本，不构成生产数据、权限、支付或状态契约。

## 2. 产品目标

一期目标是交付一条可验收的单门店到店自提闭环：

浏览与结算身份识别 → 服务端商品价格与按日库存 → 15 分钟支付软预占 → 微信支付 → 排产、制作与备好 → 单取餐点核销 → 完成或原路全额退款 → 后台查询与经营数据。

一期必须满足：

- 员工与访客均可浏览、下单和支付；支持**即时取餐**与**预约取餐**两种方式。
- 员工由启用名单识别，按会员等级享常驻折扣，并可使用与等级绑定的优惠券。
- 库存、价格、身份、订单、支付、退款和核销均以后端为唯一事实源。
- 商户使用店管 / 后厨 / 核销 / 财务只读四角色处理商品、履约、核销、退款和只读财务。
- 外部账号、资质和生产配置按 §13 的 Gate 在对应阶段完成，不阻塞本地产品与技术 OpenSpec。

## 3. 一期范围与文档依据

### 3.1 一期包含范围

- 单门店、单取餐点、到店自提。
- **即时取餐与预约取餐双模式**；预约可选今天、明天、后天。
- 微信小程序用户端、小程序商户端、PC 网页商户后台。
- 品牌选择首屏（绥安食品 / 绥安洗衣 / 绥安洗车，后两个标注即将上线）。
- 员工与访客；手机号启用名单识别员工。
- **会员等级与优惠券**（受 §0.3 C1 阻塞）。
- 商品分类、商品、图片（最多 3 张）、上下架、售罄、餐段可售、价格。
- 按营业日期计数的每日投放份数库存。
- 午餐与晚餐两餐段，每餐段独立截单时间。
- 购物车、订单、微信支付、15 分钟软预占与超时释放。
- 排产、制作、备好、扫码或手工核销。
- 用户规则内取消、商户处理和原路全额退款。
- 基础看板、支付退款只读查询和关键操作审计。
- 开屏装饰图层（服务端下发）。

### 3.2 一期排除范围

一期不包含积分、储值、部分退款、配送、多门店、多档口、多商户、POS、打印机、叫号屏、企业月结、发票及第三方 ERP / 财务 / 食堂系统对接。

排除项不得以「预留后启用」或兼容分支进入一期产品契约；需要时必须独立立项并取得新的范围授权。

**唯一例外**：外卖配送在用户端保留一处不可点击的置灰提示「暂未开放」，用于预期管理。该提示不构成任何产品契约、接口或数据结构（B6）。

> 会员等级与优惠券原属排除范围，本文档提议移入一期，见 §0.2 B5 与 §0.3 C1。补充协议签署前，本节仍以排除口径对客户表述。

### 3.3 文档优先级和合同证据边界

正式研发按以下唯一顺序裁决：

1. 真实适用合同与客户正式确认记录。
2. 现行基线 `online-ordering-system-prd.md` §1–§14。
3. 本文档 §1–§14（在 §0.2 七处修改被接受后升格为第 2 顺位）。
4. 本文档 §15、小程序源码和 PC 原型。
5. mock 数据、客户端内存状态和原型简化状态机仅用于演示，不是生产契约。

仓库范围内未发现已签署证据，现实签署状态未知。该表述只说明仓库证据边界，不判断现实中合同已签署或未签署。

## 4. 用户与后台角色

### 4.1 员工与访客

- 用户无需登录或手机号即可浏览门店、分类、商品和公开营业信息。
- **首次结算必须建立微信会话、完成手机号授权并提供姓名**；缺少任一项不得结算。
- 服务端标准化手机号后匹配当前启用名单：命中为员工并取得对应会员等级，未命中或记录停用为访客。
- 客户端不得让用户自行选择员工身份；手工输入手机号不得替代可信手机号授权。
- 订单创建时固化员工/访客身份、内部用户引用、等级快照和名单版本快照。
- 页面和日志只展示必要的脱敏信息，不公开名单或完整手机号。
- 访客按原价结算，无券可用。

### 4.2 店管

管理商品、分类、名单、会员等级、优惠券、价格、营业与预约设置、全部订单、原路全额退款和基础看板，并查看关键操作审计。

### 4.3 后厨

只可查看履约所需的订单和必要联系人信息，并执行排产确认、制作和备好；不得修改商品价格、名单、权限或退款。

### 4.4 核销

只可查看待取餐订单的最少必要信息，并执行二维码或手工取餐号核销；不得排产、改价或退款。

### 4.5 财务只读

只能查看支付、退款、交易结算和导出结果，不得执行任何业务写操作。

四角色及资源权限必须由服务端执行。普通用户不得自行进入商户端或选择后台角色；开发人员不默认持有常驻业务角色，生产排障只能使用客户明确授权、限时且有审计的访问。

## 5. 用户端功能

### 5.1 首页

- 展示门店、地址、当前餐段、截单时间、分类与商品入口。
- **展示营业状态**：营业中 / 休息中 / 已截单。
- **展示门店公告**，内容来自商户后台公告字段。
- 营销 Banner 轮播；今日招牌横滑卡。
- 服务宫格：到店点单、预约点餐、我的订单、取餐码、会员中心、**外卖配送（置灰，标注暂未开放，见 §3.2 例外）**。
- **下单入口 gating**：营业状态为休息中或已截单、或处于餐段空档期时，即时下单入口禁用并给出原因与替代动作。

### 5.2 菜单

- 商品数据、价格、库存和营业状态由后端返回；客户端不得用 mock 或缓存覆盖后端事实。
- **只展示当前餐段可售的商品**。
- 展示图片、名称、价格、简介、月售、标签。
- 下架商品不展示；售罄商品可展示但不可加入购物车。
- **支持按名称搜索**。

### 5.3 商品详情

- 顶部图廊最多 3 张，手动滑动、不自动播放、不循环，右下角计数；单图不启用滑动；点击全屏预览。
- 展示名称、说明、规格、口味选项、正常价与适用等级价、月售、标签、过敏原。
- 展示售罄或不可购买状态。
- 支持选择数量、填写口味与备注后加入购物车。

### 5.4 购物车与菜品级偏好

**口味与备注挂在菜品级**。每个商品加购时打开偏好弹层，填写数量、口味多选、该商品备注。

- 购物车保存用户选择，**不锁定价格或库存**；进入结算和提交订单时必须重新向后端校验。
- 数量为零的商品移除，空购物车不得进入结算。
- 售罄或下架商品需提示用户重新选择。

订单不设整单级口味与备注字段。

### 5.5 取餐方式

- **即时取餐**：下单后立即制作，展示预计可取时间。
- **预约取餐**：选择营业日期（今天 / 明天 / 后天）与固定取餐时段，时段按餐段分组。
- 门店时区固定 `Asia/Shanghai`。
- 每个固定取餐时段必须归属一个餐段并拥有独立截单时间。
- 用户可全天浏览，但只有目标时段尚未截单且商品可售时才能提交订单。
- **餐段空档期**：当前不在任何餐段接单时间内时，即时取餐禁用并提示（例：「午餐已截单，可预约晚餐」），引导转预约。
- 一期为单门店单取餐点，不提供多点选择或分单路由。

### 5.6 结算身份与算价

- 首次进入结算时执行 §4.1 的微信会话、手机号和姓名校验。
- 金额一律以**整数分**保存与计算，由服务端完成。
- **算价链固定为：原价小计 → 等级折扣 → 减券 → 应付。**
- 客户端提交的价格不可信；报价和订单明细固化正常价、等级折扣、券抵扣、成交价、身份及价格版本。
- 访客按原价结算，不享等级折扣，无券可用。

### 5.7 提交订单与微信支付

1. 服务端重新校验身份、商品状态、服务端价格、营业日期、餐段、时段截单和库存。
2. 校验通过后**原子创建 15 分钟库存软预占**和 `待支付` 订单。
3. 用户调用微信支付；前端成功回调只表示客户端流程结束，不作为支付成功事实。
4. 服务端根据微信支付结果确认支付；成功后软预占**原子转为实扣**，订单进入 `已支付待接单`。
5. 15 分钟内未确认支付成功时，订单进入 `已取消` 并释放完整软预占。
6. 迟到支付按 §7.4 处理，不得仅凭客户端跳转恢复订单。

### 5.8 订单列表与详情

- 用户只能查看自己的订单。
- 展示九态中的当前状态、取餐方式、服务日期与时段、取餐点、商品价格快照、优惠明细、实付金额、取餐号和可用操作。
- 只有 `待取餐` 订单展示有效核销二维码；二维码内容为服务端生成的不透明一次性 token。
- 页面状态以后端返回为准，不根据本地内存单独推进。
- 预约单在满足 §7.6 条件时提供取消入口。

### 5.9 通知提醒

支持微信订阅消息：下单成功、支付成功、可取餐、订单完成、退款结果、临时停餐或商品变更。

### 5.10 我的优惠券

- 展示会员姓名、等级、常驻折扣与当前可用券数；非会员展示访客态与说明。
- 券分可用 / 已用完 / 已过期三态，均展示券面、使用条件、适用范围、有效期。
- 券由商户按等级发放后自动进入卡包，用户**没有领取动作**。

## 6. 商户后台功能

小程序商户端与 PC 网页后台共用同一套数据与规则，差异只在操作形态（见 §6.16）。

### 6.1 登录与权限

后台所有页面和接口执行 §4 的四角色服务端鉴权。无角色用户不得进入后台；越权请求必须拒绝且不产生业务副作用。关键写操作记录操作者、时间、目标、前后状态、原因和幂等键。

### 6.2 商品分类管理

- 店管可新增、编辑、**删除**分类；删除前校验旗下商品，需先迁移或拦截。
- **排序用上移 / 下移按钮**，不做拖拽。
- 设置启用 / 停用，停用后用户端隐藏该分类及其商品。
- **改动落库**，且商品编辑页的分类选项**读取真实分类数据**，不使用写死常量。

### 6.3 商品管理

- 店管可新增、编辑、上下架、标记售罄商品，管理图片、说明、规格和口味选项。
- **餐段可售**：全天 / 仅午餐 / 仅晚餐，三选一。菜单按当前餐段过滤。
- 价格为必填整数分。
- 修改价格只影响新报价；既有订单使用下单时固化的价格快照。
- **支持按名称搜索**；支持按分类、状态筛选。
- 图片要求见 §6.14。

### 6.4 会员等级

> 受 §0.3 C1 阻塞。补充协议签署前不得实现。

- 档位可自由增删、改名、排序；等级有序，一人一档。
- 每档配置一个**常驻折扣率**，对该等级全部会员的每一单生效。
- 等级由店管在名单中手动指定，系统不按消费自动升降级。
- 删除档位强制走迁移流程：先展示该档会员数与受影响券清单，再指定会员迁移目标或降为非会员。
- 删除档位自动从所有券的适用等级中摘除；券因此没有任何适用等级时自动停用。
- 至少保留一个等级。

### 6.5 会员名单

名单是员工身份与会员等级的唯一来源，用户端没有申请入会入口。

字段：手机号（唯一识别键，必填）、姓名（必填）、会员等级（必填）、单位 / 部门 / 工号（选填）、备注（选填）、状态（默认启用）、加入时间（自动）、已绑定（只读）、累计消费与单量（只读）。

录入方式：手动逐条添加；CSV 批量导入。小程序端需先把文件发到微信聊天再用 `wx.chooseMessageFile` 选择；PC 后台可直接选文件。Excel 默认另存的 CSV 为 GBK 编码，导入页做显式检测并提示「另存为 CSV UTF-8」。导入前必须预览：新增 N 条、更新 M 条、异常 K 条，异常项可展开查看行号与原因。去重规则为按手机号覆盖更新，保留加入时间、累计消费与微信绑定关系。

停用保留记录但暂停全部权益，用于离职人员。

### 6.6 优惠券

> 受 §0.3 C1 阻塞。补充协议签署前不得实现。

券按等级自动生效，无领取动作，不设发放总量，成本控制依靠有效期与每人可用次数。

字段：券名称、类型（满减 / 折扣）、面额、封顶金额（折扣券必填）、使用门槛、适用等级（多选，至少 1 档）、适用商品范围（全场 / 指定分类 / 指定商品）、有效期、每人可用次数、状态。

范围联动：选中分类为动态包含，后续新增到该分类的商品自动纳入；商品被删除时自动从券的范围中摘除，摘空则该券自动停用。

### 6.7 库存

- 库存**配置**为每个商品一个「**每日投放份数**」；界面同时显示「今日剩余」。
- 库存**计数按营业日期各自独立**：今天、明天、后天各自拥有一份额度。
- **午餐与晚餐共享同一营业日期的额度**；菜单差异由商品「餐段可售」字段承担。只卖晚餐的商品天然只被晚餐消耗。
- 新建某营业日期的库存时，默认带出上一次的投放份数配置值，店管可改。
- 后端维护总量、软预占量、已售量和可售量，是唯一事实源。
- 订单提交只创建 15 分钟软预占，支付成功才转实扣；超时、取消和退款按 §7 释放或返还。
- 后端必须通过**原子条件更新避免超卖**；客户端展示值不能绕过服务端库存结果。
- 可售量归零时商品自动置售罄，与店管手动售罄为同一终态：用户端可见、带蒙层、不可下单。
- 支持**不限量**：饮料等品类可不设份数，卖完由店管手动置售罄。
- 可售量 ≤ 8 视为库存告急，在商户端标红提示补货。

### 6.8 营业与预约设置

- 门店时区固定 `Asia/Shanghai`。
- 一期为**午餐、晚餐两餐段**，不支持早餐。
- 店管为每个餐段配置三个参数：**开始接单时间、截单时间、固定取餐时段**。
- **截单为按餐段的固定时刻**，不随取餐时间滚动。
- 店管配置今天、明天、后天的可预约状态、特殊停餐日期、单取餐点名称、地址、说明和公告。
- 营业状态：营业中 / 休息中 / 已截单，店管可手动切换，覆盖营业时间规则。
- 实际时段、截单和取餐点内容属于 UAT 前配置，但不得改变「单取餐点、午晚固定餐段、即时单与预约单双模式」的模型。

### 6.9 订单履约

- 后厨查看 `已支付待接单` 和 `制作中` 订单。
- **即时单**支付成功后直接进入 `制作中`，不在 `已支付待接单` 停留。
- **预约单**在取餐前 30 分钟自动进入 `制作中`；后厨也可手动提前开做。
- 备好使订单进入 `待取餐`。
- 所有转换由服务端校验前置状态、角色和幂等键；**生产禁止撤销或回退**。
- 异常订单必须可由店管和授权技术人员按审计记录追踪，不得静默改状态。
- 商户端订单列表提供**按取餐号、订单号、手机号搜索**。

### 6.10 核销

- 核销二维码使用服务端生成的不透明一次性 token，仅对 `待取餐` 订单有效。
- 扫码和手工输入取餐号调用同一服务端原子核销能力。
- 核销成功使订单进入 `已完成`，并记录核销人、时间和方式。
- 重复核销返回第一次结果，不重复计算营收或订单量。
- 已取消、已退款、异常订单不得核销。

### 6.11 支付、退款与看板

- 店管可按 §7.7 发起原路全额退款；一期无部分退款。
- 财务只读可查看支付、退款、交易结算和导出，不得发起退款或修改订单。
- 看板只统计服务端已确认的数据，不由客户端 mock 累加。

### 6.12 财务与对账

- 后台展示订单支付金额、支付时间、微信交易号。
- 支持按日期导出订单明细。
- 支持对账时核对微信支付账单。
- 退款记录退款单号、退款金额、退款状态与操作人。

### 6.13 数据看板

- 指标：当日营收、当日订单、当月营收、当月订单、退款金额、商品销量排行。
- **商品销量排行来自真实订单数据**，不使用写死常量。
- 待办：待制作数、待取超时数、库存告急数。
- 已取消、退款中、已退款和异常订单按明确口径单独统计，不混入有效营收。

### 6.14 商品图片

- 每个商品最多 3 张图片，第一张为封面。
- 菜单列表、购物车、订单、后台列表一律只用封面。
- 可删除任意图片，非首张可一键「设为封面」并移到第一位。
- 不做拖拽排序。
- 图片经上传接口存入对象存储后写入商品记录，不落本机存储。

### 6.15 开屏图层

- 店管上传一张透明 PNG，在等比缩放的手机预览上拖拽定位、滑杆调整大小。
- 保存后展示在品牌选择页与身份选择页。
- **图片上传至对象存储，配置存服务端，向所有用户下发**；不使用本机存储。

### 6.16 两个商户端形态的分工

| | 小程序商户端 | PC 网页后台 |
| --- | --- | --- |
| 定位 | 现场高频、单手操作 | 批量、配置、查询 |
| 强项 | 扫码核销、出餐推进、临时改售罄 | 商品与分类批量维护、订单查询与退款、营业设置、CSV 导入 |
| 营业设置 | 状态切换 | 完整可编辑表单 |

## 7. 订单、库存、支付和履约规则

### 7.1 九态生产状态机

生产订单状态必须且只能为：

1. `待支付`
2. `已支付待接单`
3. `制作中`
4. `待取餐`
5. `已完成`
6. `已取消`
7. `退款中`
8. `已退款`
9. `异常`

标准履约链路：

```text
即时单：待支付 → 已支付待接单（瞬时）→ 制作中 → 待取餐 → 已完成
预约单：待支付 → 已支付待接单 → 制作中 → 待取餐 → 已完成
```

取消、退款和钱单/库存结果无法自动确定时分别进入对应状态。每次转换必须由服务端校验前置状态、资源权限和幂等键，并记录审计。相同幂等键重复请求返回第一次最终结果，不重复产生库存、支付、退款、营收或核销副作用。**生产禁止撤销或回退已完成的转换。**

### 7.2 软预占与正常支付

- 提交订单原子创建 15 分钟库存软预占和 `待支付` 订单。
- 软预占不计为已售库存或有效预约。
- 服务端确认微信支付成功后，软预占原子转为实扣，订单进入 `已支付待接单` 并成为有效订单。
- 15 分钟内未确认支付成功，订单进入 `已取消` 并完整释放软预占。
- 支付通知、超时释放和状态转换均须幂等。

### 7.3 排产

- **即时单**：支付成功确认后立即由服务端推进至 `制作中`，`已支付待接单` 为瞬时中间态。
- **预约单**：取餐前 30 分钟由服务端定时推进至 `制作中`；后厨可在此之前手动提前开做，手动操作记录操作者与时间。
- 定时推进任务须幂等，并具备重试与补偿；任务漏跑不得导致订单卡在 `已支付待接单`。

### 7.4 迟到支付

- 已超时订单收到可验证的迟到支付成功通知时，服务端先幂等确认支付事实，再按原营业日期与商品完整原子重占库存。
- 重占成功：转为实扣，订单进入 `已支付待接单`。
- 重占失败：不得形成有效订单，系统只发起一次原路全额退款并把订单置为 `异常`。
- 迟到支付自动退款成功后订单进入 `已退款`；退款未成功前保持可追踪的 `异常`。

### 7.5 商户履约与核销

- 排产：`已支付待接单 → 制作中`（触发条件见 §7.3）。
- 后厨备好：`制作中 → 待取餐`。
- 核销成功：`待取餐 → 已完成`。
- 任何角色不得跳过前置状态或使用客户端撤销回退生产状态。

### 7.6 用户取消

- `待支付`：用户可直接取消，订单进入 `已取消` 并释放软预占，不发起退款。
- **即时单**支付成功后立即进入制作，**不提供用户自助取消**，只能联系商户处理。
- **预约单**在 `已支付待接单`、尚未进入制作、且目标时段未到截单时间时：用户可自助取消，系统立即发起一次原路全额退款。
- 进入 `制作中` 或目标时段到达截单时间任一先发生后：用户自助取消关闭，只能联系商户处理。
- 其他状态不提供用户自助取消。

### 7.7 全额退款

- 一期只支持原路全额退款，任何部分退款请求必须拒绝且不创建退款记录。
- 除迟到支付重占失败的异常自动退款外，用户或店管发起退款后订单进入 `退款中`。
- 微信确认退款成功后订单进入 `已退款`；受理成功、客户端提示或调用成功均不等于退款完成。
- **进入制作前退款成功，返还对应营业日期的实扣库存。**
- **进入制作后由店管处理的退款不自动恢复可售库存**，需要店管按真实经营损耗调整后续投放份数。

### 7.8 订单编号

- 系统订单号用于唯一识别与对账。
- 取餐号用于窗口叫号，即时单与预约单使用不同前缀以便现场区分。
- 取餐号在同一营业日期、同一餐段内不可重复；已取消订单的取餐号不复用。

## 8. 版本范围

### 8.1 P0 可预览原型

P0 已完成视觉、页面覆盖和演示交互确认，允许 mock、内存状态、假支付、简化状态和撤销按钮。P0 的验收价值是界面与交互方向，不证明生产支付、权限、跨端同步或数据持久化。

### 8.2 一期 MVP 正式开发必做

- §3.1 全部包含范围。
- §4 的员工/访客识别和后台四角色。
- §5 的即时单与预约单闭环、服务端报价与算价链。
- §6 的商品、等级折扣、优惠券、库存、营业设置、履约、核销、退款和基础看板。
- §7 的九态、15 分钟软预占、微信支付、迟到支付、排产、取消和全额退款。
- §9 的稳定性、安全、审计和敏感数据边界。
- §13 对应阶段必须完成的外部 Gate 和 UAT 前配置。
- §14 全部验收标准。

### 8.3 后续独立能力

积分、储值、部分退款、配送、多门店、POS、打印机、叫号屏及其他 §3.2 排除项不属于一期。后续若需实施，必须分别获得范围授权、建立独立 OpenSpec，并不得改变已生成的一期订单快照。

## 9. 非功能要求

### 9.1 一致性与幂等

- 后端是身份、商品、价格、库存、订单、支付、退款和核销的唯一事实源。
- 创建订单、库存预占/实扣/释放/返还、支付回调、退款回调、状态推进、排产和核销均须幂等。
- 钱单或库存结果无法自动确定时进入 `异常`，保留原因和处理记录，不得猜测成功。
- 订单明细固化商品、价格、身份、等级、优惠、取餐方式和取餐点快照，后续配置变化不回算历史订单。

### 9.2 容量与可用性

- 支持 5–10 分钟集中 100–300 单、日 500–1000 单的已知规模。
- 下单、支付和核销路径使用原子操作与明确超时，不因统计任务阻塞核心交易。
- 空、加载、弱网、重复提交和外部调用失败必须提供可恢复结果；重试不得重复产生副作用。

### 9.3 权限与审计

- 用户只能访问自己的订单。
- 四角色资源权限由服务端执行，客户端菜单隐藏不能代替鉴权。
- 关键操作记录操作者、时间、对象、前后状态、原因和幂等键。
- 开发人员生产排障需要客户限时授权。

### 9.4 敏感数据

- 密钥、证书内容和服务端凭据不得进入客户端、PRD、OpenSpec、外部 Gate 台账或日志。
- 台账不得记录账号标识、真实手机号、名单或其他个人数据，只保存非敏感证据引用和状态。
- 手机号、姓名和订单个人信息按最小必要范围收集、展示和授权访问。

### 9.5 数据保护与异常恢复

- 核心数据需要备份与恢复演练方案。
- 支付、退款、异常订单和关键操作可查询、可审计、可人工处理。
- 数据恢复不得绕过九态、库存和支付事实约束。

## 10. UI 与体验要求

### 10.1 视觉蓝本

§15 的色彩、字体、间距、组件、页面布局和交互反馈作为一期视觉蓝本。任何视觉实现不得改变 §1–§14 的身份、价格、预约、状态、权限或支付结果。

### 10.2 用户端

- 浏览阶段不提前索取手机号。
- 结算页清晰展示取餐方式、营业日期、餐段、固定时段、截单、单取餐点、原价小计、等级折扣、券抵扣和应付金额。
- 支付中、支付结果确认中、库存变化、退款中和异常均有独立状态，不用「支付成功」动画替代服务端事实。
- **不可执行操作必须禁用并说明原因**，并在可能时给出替代动作。

### 10.3 商户后台

- 按四角色展示必要导航和字段；敏感信息按最小权限脱敏。
- 订单主操作与九态一致，不展示生产撤销。
- 核销、退款和异常处理必须先展示目标订单和结果，不以 Toast 作为唯一审计证据。

## 11. 数据统计

- 统计来源为服务端确认的订单、支付、退款和核销数据。
- 基础看板包含当日与当月有效营收、有效订单数、退款金额和商品销量。
- 已取消、退款中、已退款和异常订单必须按明确口径单独统计，不混入有效营收。
- 财务只读可查询和导出，任何统计页面不得修改交易事实。

> 一期不建设访问量与点击量埋点，看板不提供相关指标。

## 12. 正式业务不变量

1. 一期是单门店、单取餐点、到店自提，**即时单与预约单双模式并存**。
2. 预约可选今天、明天、后天；餐段仅午餐和晚餐；门店时区为 `Asia/Shanghai`。
3. 库存配置为每商品一个每日投放份数，**按营业日期各自独立计数**，午晚共享同日额度，菜单差异由「餐段可售」承担。
4. 下单原子软预占 15 分钟；服务端确认支付成功才实扣，超时释放。
5. 即时单支付成功即进 `制作中`；预约单取餐前 30 分钟自动进入，后厨可提前手动开做。
6. 迟到支付先完整重占，失败自动原路全额退款并进入 `异常`，退款成功转 `已退款`。
7. 公开订单状态只有九态，状态转换由服务端单向执行，生产禁止撤销。
8. 未支付可取消；预约单已支付未进制作且未截单可自助全退；即时单支付后不可自助取消。
9. 一期无部分退款，只有微信确认退款成功才是 `已退款`。进入制作前退款返还库存，进入制作后不自动返还。
10. 浏览免手机号；首次结算需微信会话、手机号和姓名；启用名单决定员工身份与会员等级。
11. 算价链固定为原价小计 → 等级折扣 → 减券 → 应付；一单一张券，券与等级折扣叠加；金额一律整数分。
12. 后台只有店管、后厨、核销、财务只读四角色，资源权限由服务端执行。
13. mock、客户端内存态、前端支付结果和 §15 简化状态都不是生产事实源。

### 12.1 会员与优惠券算价细则

> 受 §0.3 C1 阻塞。

1. 一单只能使用一张券；券与等级折扣**叠加**，不择优。
2. 券的门槛判定与减免作用均锚定「可用商品小计」，且作用在等级折扣**之后**的金额上。
3. 折扣券必须填写封顶金额，减免不超过可用商品小计。
4. 默认自动选中减免金额最大的可用券；已选券因购物车变化而不可用时自动回落到当前最优券。
5. 用户可显式选择「不使用优惠券」。
6. 券按「有效期内每人可用次数」计次，**支付成功即计入**。
7. 优惠总额被封顶在应付金额，实付最低为 0，不出现负数。
8. 名单是会员的唯一来源，不在名单中一律原价且无券可用。

## 14. 验收标准

- 用户能免手机号浏览，首次结算按服务端完成员工/访客识别与等级判定。
- 用户可选择即时取餐，或今天/明天/后天的固定时段预约，并看到单取餐点与逐餐段截单结果。
- 同一商品在不同营业日期库存独立计数；午晚共享同日额度；并发下单不超卖。
- 下单产生 15 分钟软预占；正常支付、超时释放和迟到支付三条路径均可复现。
- 即时单支付成功即进 `制作中`；预约单取餐前 30 分钟自动进入，后厨可手动提前。
- 九态和所有合法/非法转换可复现，生产不存在撤销入口。
- 用户取消、自动全额退款、商户处理、退款失败和库存返还符合 §7。
- 算价链按原价小计 → 等级折扣 → 减券 → 应付执行，金额为整数分，订单快照不随配置回算。
- 店管、后厨、核销、财务只读角色只能执行授权动作。
- 扫码和手工核销幂等，重复核销不重复统计。
- 首页展示营业状态与公告；休息中、已截单、餐段空档期时下单入口禁用并说明原因。
- 分类改动落库且与商品编辑联动；开屏图层由服务端下发，换设备仍可见。
- 外部 Gate 只在对应阶段生效；任何台账不含敏感数据。

## 15.1 产品概述

绥安食品到店自提点餐系统。**单一小程序内含两端**，冷启动经品牌选择页进入身份选择，由用户自选进入用户端或商户端；另有独立的 PC 网页商户后台。

## 15.7 订单状态机

**目标态：九态**（见 §7.1，采纳自现行基线）

```
即时单：待支付 ──支付──▶ 已支付待接单(瞬时) ──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
预约单：待支付 ──支付──▶ 已支付待接单 ──取餐前30分/后厨提前──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
旁路：  待支付 ──超时15分/取消──▶ 已取消（释放软预占）
       已支付各态 ──发起退款──▶ 退款中 ──微信确认──▶ 已退款
       钱单或库存结果无法自动确定 ──▶ 异常
```

**当前实现**（`apps/wechat-miniprogram/utils/util.js`）

```js
const NEXT = { 待制作: '待取餐', 待取餐: '已完成' };
const ACT  = { 待制作: '备好', 待取餐: '核销', 已完成: '查看', 已取消: '查看' };
```

**差异（待改造，工作量最大的一项）**：

- 前端为三态推进，目标为九态；`已支付待接单`、`退款中`、`已退款`、`异常` 四态完全不存在。
- 前端用「待制作」，目标态名为「制作中」。
- 预约单的自动排产未实现。
- 前端状态推进在本地内存完成；目标为**服务端单向驱动**，前端只展示后端返回的状态。
- **必须移除「撤销」**：现行基线 §7.1 明确「生产禁止撤销或回退已经完成的转换」，当前 `advanceOrder` 的 Toast 撤销是 P0 演示能力，不得进入生产。

- 商户端每个订单卡只暴露**一个主行动按钮**，文案随状态变化：`备好 → 核销 → 查看`。
- **核销**是「待取餐 → 已完成」的唯一路径。

## 15.11 边界与异常

| 场景 | 期望行为 |
| --- | --- |
| 已截单 / 休息中 | 用户端下单入口禁用并提示；菜单仅浏览 |
| 餐段空档期 | 「尽快取餐」禁用并提示可预约下一餐段 |
| 今日剩余为 0 / 手动售罄 | 菜品按钮禁用 + 蒙层；已加购需在支付前校验并提示 |
| 菜品不在当前餐段 | 用户端不展示；商户端可见 |
| 菜品下架 | 用户端不展示；商户端可见可重新上架 |
| 提交订单 | 原子创建 15 分钟软预占，订单置「待支付」；软预占不计已售 |
| 待支付超时 15 分钟 | 自动转「已取消」并完整释放软预占 |
| 支付成功 | 软预占原子转实扣，即时单直接进「制作中」，预约单进「已支付待接单」 |
| 迟到支付 | 先完整重占；成功转实扣，失败自动原路全额退款并置「异常」 |
| 提交时可售量不足 | 软预占创建失败，提示重选，不生成订单 |
| 预约单已进「制作中」或已过截单 | 取消入口消失，只能联系商户 |
| 进入制作前退款成功 | 返还对应营业日期的实扣库存 |
| 进入制作后退款成功 | **不自动返还**，由店管按经营损耗调整后续投放份数 |
| 排产定时任务漏跑 | 须重试与补偿，不得让订单卡在「已支付待接单」 |
| 取餐码核销重复 | 已完成单再次扫码提示「已核销」，不重复计数 |
| 已退款订单扫码 | 提示订单已退款，拒绝核销 |
| 网络 / 支付失败 | 停留确认页，可重试，不生成取餐号 |
| 空购物车 | 「去结算」禁用 |
| 无待取订单点首页取餐码 | Toast 提示无待取餐订单 |
| 非会员进入确认页 | 优惠卡显示「非会员 · 原价」，不显示选券入口 |
| 已选券因购物车变化失效 | 自动回落到当前最优可用券 |
| 券减免超过应付 | 券减免封顶在应付金额，实付最低为 0 |
| CSV 为 GBK 编码 | 中止并提示「另存为 CSV UTF-8」 |
| 菜品无图 | 按品类渐变 + 宋体首字占位，不开天窗 |
| 菜品仅 1 张图 | 详情页不显示计数、不启用滑动，仍可全屏预览 |

## 16.2 需修改现行生效基线的七处

`online-ordering-system-prd.md` 是团队正在依据其开发的文档。以下修改需先与其维护方对齐，不得单方面覆盖。

| # | 修改点 | 现行基线原文 | 本文档结论 | 复查要点 |
| --- | --- | --- | --- | --- |
| B1 | 即时单 | §5.3「不提供即时单或"尽快"模式」 | 即时单与预约单双模式并存 | 前端现状与本文档一致（首页宫格双入口），与基线不一致。复查一期是否真的要放弃即时单场景 |
| B2 | 可预约天数 | §5.3、§12.2「仅今天和明天」 | 今天、明天、后天 | 后天的库存需要能提前配置，见 B3 |
| B3 | 库存维度 | §6.3「营业日期 × 餐段 × 商品，午晚独立库存池」 | 每商品一个每日投放份数，按营业日期独立计数，**午晚共享同日额度** | 唯一实质差异是午晚不拆池。复查「午餐吃光晚餐无菜」是否可接受，或是否全靠「餐段可售」拆分商品来规避 |
| B4 | 排产触发 | §6.5、§7.4 后厨手动接单 | 即时单支付即制作；预约单取餐前 30 分钟自动，后厨可提前手动 | 复查后厨是否接受「订单自己进入制作中」，以及 30 分钟是否够备餐 |
| B5 | 会员等级 + 优惠券 | §3.2 排除；§5.4 用逐商品 `employee_price` | 移入一期，去掉 `employee_price` | 见 §16.1，硬阻塞 |
| B6 | 外卖占位 | §3.2「排除项不得以预留后启用或兼容分支进入一期产品契约」 | 保留一处纯 UI 置灰提示 | 复查该提示是否会被客户理解为一期含配送 |
| B7 | 餐段空档期 | 无即时单故无此概念 | 不可即时下单，引导转预约 | 随 B1 成立与否 |
