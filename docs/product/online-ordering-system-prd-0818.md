## 1. 项目背景

本项目为单门店餐饮经营主体提供微信小程序在线预约点单、微信支付、到店自提，以及配套商户后台。客户是经营、收款、退款、隐私和发布责任主体；开发方负责开发、配置、联调、提审协助、技术排障和运维支持。

客户已认可 P0 原型的视觉与主要交互方向。P0 允许 mock 数据、内存状态、假支付和简化状态机；这些只证明页面蓝本，不构成生产数据、权限、支付或状态契约。

## 2. 产品目标

一期目标是交付一条可验收的单门店预约自提闭环：

浏览 → 选取餐日期与时间 → 结算身份识别 → 微信支付成功后生成订单 → 取餐前 30 分钟自动开做 → 备好并推送提醒 → 单取餐点扫码或手工核销 → 完成，或原路全额退款。

一期必须满足：

- 员工与访客均可浏览、下单和支付；**只有预约取餐一种方式**。
- 员工由手机号白名单识别，命中后享**全局统一折扣率**，逐商品展示划线原价与员工价。
- 价格、身份、订单、支付、退款和核销均以后端为唯一事实源。
- 商户使用**主账号 / 子账号**两角色处理履约、核销、商品销售状态、配置、退款和财务。
- 外部账号、资质和生产配置按 §13 的 Gate 在对应阶段完成，不阻塞本地产品与技术 OpenSpec。

**一期明确不做**：数量库存与预占、即时取餐、接单、会员等级与优惠券、部分退款。相关风险见 §16。

## 3. 一期范围与文档依据

### 3.1 范围基线

以下为本版认定的一期范围。除注明外，均已由 2026-08-19 客户评审记录确认。

- 单门店、单取餐点、到店自提。
- **仅预约取餐**；可预约**今天、明天**两个营业日期。
- 微信小程序用户端、小程序商户端（精简）、PC 网页商户后台。
- 员工与访客；**手机号白名单**识别员工，命中后按**全局折扣率**结算。
- 商品分类、商品、图片（最多 3 张）、上下架、**按取餐日期的售罄开关**、餐段可售、价格。
- 午餐与晚餐两餐段，每餐段一个固定截单时刻；餐段内切分为**离散取餐时间点**。
- 购物车、订单、微信支付、支付对账兜底。
- 取餐前 30 分钟自动开做、备好、扫码或手工核销。
- 用户规则内取消、商户处理和原路全额退款。
- 两类微信订阅消息（待取餐提醒、退款结果）。
- 基础看板、财务对账查询与关键操作审计。
- 开屏装饰图层（服务端下发，展示在首页与身份选择页）。

## 4. 用户与后台角色

### 4.1 员工与访客

- 用户无需登录或手机号即可浏览门店、分类、商品和公开营业信息。**不得在启动时强制手机号授权。**
- **首次提交订单前必须建立微信会话并完成手机号授权**；未绑定不得进入支付。绑定完成后返回结算页继续。
- 服务端标准化手机号后匹配**员工折扣白名单**：命中且状态启用为员工，未命中或已停用为访客。
- **附加手机号**：用户可在个人中心手工填写第 2 个手机号用于员工匹配。**手工填写的号必须「手机号 + 姓名」同时命中同一条白名单记录才生效**；姓名做去空格与全半角归一后精确匹配。微信授权取得的主手机号已可信，命中即生效，姓名仅作记录。
- 客户端不得让用户自行选择员工身份。
- 订单创建时固化员工/访客身份、内部用户引用、折扣率快照和名单版本快照。
- 页面和日志只展示必要的脱敏信息，不公开名单或完整手机号。
- **访客按原价结算**，菜单不展示划线价。

> 附加手机号采用双要素而非短信验证，是明确的成本取舍：姓名属于弱秘密，同事之间可互相知晓。该残余风险已由客户接受，见 §16.1。

### 4.2 商户主账号

- **可配置多个**（运营上建议至少 2 个，避免单点）。
- 小程序端：子账号的全部能力。
- PC 后台：商品与分类配置、上下架、价格、**全局折扣率**、员工折扣白名单、商户账号名单、退款、财务与对账、营业设置、开屏图层、看板、支付待处理。

### 4.3 商户子账号

- 仅小程序端。能力限于：**查看订单、标记备好、扫码或手工核销、切换商品可售 / 售罄**。
- 不得进入 PC 后台；不得改价、上下架、退款、改配置或查看财务。

### 4.4 账号与登录

- 商户身份来源为 PC 后台维护的**商户账号名单**（手机号 + 角色），与员工折扣白名单**分开管理**，两份名单互不影响。
- **小程序端**：启动时静默 `wx.login` 取 openid，服务端查该 openid 是否已绑定商户手机号。已绑定进身份选择页，未绑定直接进用户端首页。商户首次使用需在个人中心点「商户登录」，触发微信手机号授权并比对商户账号名单，命中则绑定 openid。
- **PC 后台**：**微信扫码登录**。页面出码，用微信扫描后服务端取得手机号，比对同一份商户账号名单；仅主账号可登录。不建设独立密码体系。
- **账号字段**：可填写的只有手机号、姓名、角色三项；状态（默认启用）、微信绑定标记、创建时间由系统维护。编辑账号只覆盖这三项，不重置微信绑定与创建时间。
- **角色的可用范围**：主账号可登录 PC 后台并拥有全部权限；子账号只能用小程序商户端的订单、核销、菜品三个页面，不能登录 PC 后台。
- **最后一个主账号不可失效**：当某主账号是当前唯一启用的主账号时，删除它、停用它、把它降级为子账号这三条路径全部拒绝，拒绝由服务端裁决而非仅靠前端隐藏按钮。否则会出现无人能登录 PC 后台的死锁，且解锁需要人工改库。要执行上述任一操作，先添加并启用另一个主账号。
- **停用与删除**：停用保留记录与历史，随时可恢复；删除不可恢复，且会解绑该账号已绑定的微信。删除需二次确认，确认文案须写明两者区别。
- 两个角色的资源权限必须由服务端执行。普通用户不得进入商户端；客户端菜单隐藏不能代替鉴权。开发人员不默认持有常驻业务角色，生产排障只能使用客户明确授权、限时且有审计的访问。

## 5. 用户端功能

### 5.1 首页

- 展示门店名、地址、当前营业状态（营业中 / 休息中 / 已截单）与最近可预约信息。
- **展示门店公告**，内容来自商户后台公告字段。
- **开屏装饰图层**：进入首页时按服务端下发的位置与尺寸叠加一张透明 PNG，**1.5 秒后或点击任意处淡出**。
- **进行中订单提示条**：存在 `已预约` / `制作中` / `待取餐` 订单时，页面顶部常驻一条「你有 N 单进行中 · 今天 12:00 取餐」，点击直达取餐码页；订单进入 `待取餐` 后文案变为「**已备好，可取餐**」并高亮。
- 入口：**预约点餐 / 我的订单 / 取餐码**，共三个。
- **不含**：营销 Banner、推荐商品、今日招牌、入群模块、会员中心、外卖配送、洗衣洗车入口。

### 5.2 菜单

- 商品数据、价格、销售状态和营业状态由后端返回；客户端不得用 mock 或缓存覆盖后端事实。
- **顶部取餐时间条**：显示当前选择的取餐日期与时间（例「今天 12:00 取餐 ▾」），点击展开选择弹层（见 §5.5）。进入菜单时按 §5.5 的默认规则自动选定，不阻断用户直接看菜。
- **只展示所选取餐时间所属餐段可售的商品**（商品「餐段可售」为全天 / 仅午餐 / 仅晚餐）。
- 展示图片、名称、价格、简介。员工已识别时同时展示**划线原价与员工价**。
- 商品按商户后台设置的顺序展示，用户端不提供排序选择。
- 下架商品不展示；**当日售罄**商品可展示但带蒙层、不可加入购物车。
- **支持按名称搜索**，支持按分类锚点浏览。
- **不展示**：月售、标签、推荐或热销标识。

### 5.3 商品详情

- 顶部图廊最多 3 张，手动滑动、不自动播放、不循环，右下角计数；单图不启用滑动；点击全屏预览。
- 展示名称、说明、规格、口味选项、价格（员工态另展示划线原价与员工价）。
- 展示售罄或不可购买状态。
- 支持选择数量、填写口味与该商品备注后加入购物车。
- **不展示**：月售、标签、过敏原。

### 5.4 购物车与备注

**口味只在菜品级。** 每个商品加购时打开偏好弹层，填写数量、口味多选、该商品备注。

- 购物车保存用户选择，**不锁定价格或销售状态**；进入结算和提交订单时必须重新向后端校验。变价或已售罄时提示用户确认后再继续。
- 数量为零的商品移除，空购物车不得进入结算。
- **结算页提供整单备注**，与菜品级备注并存。订单不设整单级口味字段。

### 5.5 取餐日期与时间

- 门店时区固定 `Asia/Shanghai`。一期只有**预约取餐**，没有即时取餐。
- 可预约营业日期为**今天、明天**两天。
- 每个餐段有一个**固定截单时刻**（午餐、晚餐各一），该餐段内所有取餐时间共用同一截单时刻，不随取餐时间滚动。
- 餐段内切分为**离散取餐时间点**，默认 30 分钟粒度，商户可配。取餐时间是**约定时刻，不是必须到场的窗口**——商品备好后推送提醒，用户凭提醒随时来取。
- **选择弹层**：日期两段（今天 / 明天）＋ 时间列表。时间列表**按餐段分组**（午餐 / 晚餐）。
  - 已截单的餐段**整组折叠**，标题右侧标注「已截单 · hh:mm 截止」，不逐条渲染灰项。
  - 当天两个餐段均已截单时，「今天」整体置灰并标注「今日已截单」。
- **默认选中规则**：当前时刻之后第一个未截单的取餐时间点。当天全部截单则落到明天的第一个时间点。
- 用户可全天浏览，但只有目标取餐时间所属餐段尚未截单、且商品当日可售时才能提交订单。
- 一期为单门店单取餐点，不提供多点选择或分单路由。

> 客户确认的配置为：午餐截单 11:30、取餐 11:30–13:30；晚餐截单 17:00、取餐 17:00–19:00。截单时刻与首个取餐时间重合，意味着临近截单下的单几乎没有备餐缓冲，且会按 §7.4 在支付成功时立即进入 `制作中`。客户已确认可接受；截单时刻为商户后台可配项，UAT 前可自行调整。

### 5.6 结算身份与算价

- 首次进入结算时执行 §4.1 的微信会话与手机号授权校验。
- 金额一律以**整数分**保存与计算，由服务端完成。
- **算价链固定为：原价小计 → 员工折扣 → 应付。**
- **折扣逐商品计算**：每个商品的单价 × 全局折扣率，先四舍五入到分，再乘数量求和。保证菜单与详情页展示的员工价**等于**结算明细中的成交价。
- 客户端提交的价格不可信；报价和订单明细固化原价、折扣率、折后价、身份及价格版本。
- 访客按原价结算，不享折扣。
- 未绑定手机号前，菜单与详情页**一律展示原价、不展示划线**；绑定并命中白名单后才切换为划线展示。不做「先按员工价展示、结算时打回原价」。

### 5.7 提交订单与微信支付

1. 服务端重新校验身份、商品上下架与当日售罄、服务端价格、取餐日期，以及**目标取餐时间所属餐段是否仍在截单前**。
2. 校验不通过时**拦截支付**：售罄或变价按 §5.4 提示确认；已截单则提示「午餐已截单」并把用户送回时间选择，**购物车内容保留**。
3. 校验通过后创建**内部预支付记录**（含 `out_trade_no`）。该记录**不是订单**：不进订单列表、不占取餐号、用户不可见。
4. 用户调起微信支付；前端成功回调只表示客户端流程结束，不作为支付成功事实。
5. **服务端确认微信支付成功后才生成订单**，分配取餐号，订单进入 `已预约`；若此时距取餐时间已不足 30 分钟，直接进入 `制作中`。
6. 用户取消支付或支付失败**不生成订单**，预支付记录作废。
7. 支付结果未确认期间，用户端只显示临时加载提示，**不生成订单、不展示异常态**。兜底见 §7.3。

### 5.8 订单列表与详情

- 用户只能查看自己的订单。
- 展示当前状态、取餐日期与时间、取餐点、商品价格快照、折扣明细、实付金额、取餐号和可用操作。
- **只有 `待取餐` 订单展示核销二维码**；`已预约` 与 `制作中` 只展示取餐号、取餐时间与当前状态。二维码内容为服务端生成的不透明一次性 token。
- 未订阅取餐提醒时，取餐码页展示「**开启取餐提醒**」按钮，点击重新触发订阅授权。
- 页面状态以后端返回为准，不根据本地内存单独推进。
- 满足 §7.6 条件时提供取消入口。
- 状态筛选段：全部 / 已预约 / 制作中 / 待取餐 / 已完成 / 已退款。**不含**待支付、已取消、异常。

### 5.9 个人中心

- 身份卡：头像、昵称、脱敏手机号；员工态展示折扣胶囊，访客态展示「访客 · 原价」。
- **绑定手机号**入口（未绑定时）与**附加手机号**填写入口（手机号 + 姓名）。
- 我的订单、联系客服。
- **商户登录**入口：点击触发微信手机号授权，命中商户账号名单则绑定并跳转身份选择页，未命中提示无权限。
- **切换身份**入口：仅对已绑定商户手机号的用户展示，点击回身份选择页；普通用户不展示。
- **不含**：我的优惠券、会员中心、外卖配送。

### 5.10 通知提醒

一期只提供**两类**微信订阅消息，由用户主动订阅：

| 模板 | 订阅时机 | 说明 |
| --- | --- | --- |
| **待取餐提醒** | **支付成功页**自动请求一次订阅授权 | 用户动机最强的时刻 |
| **退款结果** | **用户点「取消订单」的确认弹窗内**一并请求 | 绝大多数订单不退款，不在支付时预先消耗授权额度 |

- 微信**长期订阅**只对特定类目开放，餐饮不在其中，因此本项目按**一次性订阅**设计：每次授权只能下发一条，需每单重新授权（用户勾选「总是保持以上选择」后不再弹窗）。该结论须在申请模板时按当时的官方类目规则复核，见 §13.2。
- 用户拒绝订阅时，以 §5.1 的首页进行中订单提示条与 §5.8 的订单状态展示作为兜底，并在取餐码页提供补订阅入口。
- **下单成功、支付成功、订单完成不发送订阅消息**；临时停餐或商品变更不做群发。

## 6. 商户后台功能

小程序商户端与 PC 网页后台共用同一套数据与规则。**小程序端只承担现场高频动作，其余全部在 PC 后台**（见 §6.10）。

### 6.1 登录与权限

后台所有页面和接口执行 §4 的主 / 子账号服务端鉴权。无角色用户不得进入后台；越权请求必须拒绝且不产生业务副作用。关键写操作记录操作者、时间、目标、前后状态、原因和幂等键。

### 6.2 商品分类管理（PC 后台）

- 主账号可新增、编辑、**删除**分类；删除前校验旗下商品，需先迁移或拦截。
- **排序用上移 / 下移按钮**，不做拖拽。
- 设置启用 / 停用，停用后用户端隐藏该分类及其商品。
- **改动落库**，且商品编辑页的分类选项**读取真实分类数据**，不使用写死常量。

### 6.3 商品管理（PC 后台）

- 主账号可新增、编辑、上下架商品。
- **商品编辑表单字段固定为五项**：菜品图片（最多 3 张）、菜品名称（必填）、售价（必填）、分类（必填）、餐段可售（必填），外加选填的描述。批量导入模板的列 MUST 与该字段集合一一对应，见 §6.13。
- **餐段可售**：全天 / 午餐 / 晚餐，三选一，必填。菜单按用户所选取餐时间的餐段过滤。
  > 已知偏差：2026-08-19 评审 §11 要求「每个商品可配置自己的口味选项」，当前实现为一份全局口味表，所有商品共用，商品编辑表单不提供逐商品配置。规格字段同样只存在于数据中，不在表单内维护。经 2026-08-21 确认，一期不做逐商品的口味与规格配置。
- 价格为必填整数分。修改价格只影响新报价；既有订单使用下单时固化的价格快照。
- **支持按名称搜索**；支持按分类、状态筛选。
- 图片要求见 §6.8。
- **无库存字段**；**无标签、无过敏原、无月售**。

### 6.4 员工折扣与白名单（PC 后台）

- **全局折扣率**：一个数值，对所有命中白名单的用户、所有商品统一生效。主账号可随时修改，只影响新报价。**一期不做等级、不做优惠券、不做逐商品员工价、不做「不参与折扣」商品开关。**
- **员工折扣白名单只有两个可填字段**：手机号（唯一识别键，必填）、姓名（必填，用于 §4.1 的附加手机号双要素）。不设单位、部门、工号与备注——白名单的唯一职责是判定「这个手机号是不是员工」，其余信息属人事系统，一期不在此维护。
- 另有三类非填写字段：**状态**（启用 / 停用，新增时默认启用，由页面上的开关切换，不进入导入模板）、**加入时间**（自动）、**已绑定 / 累计消费 / 累计单量**（只读，由系统统计）。
- 录入方式：手动逐条添加；`.xlsx` 批量导入，见 §6.13.3。去重规则为按手机号覆盖更新，保留加入时间、累计消费与微信绑定关系。
- 停用保留记录但暂停折扣，用于离职人员。
- 用户端没有申请入会入口。

### 6.5 商品销售状态（两端）

- 商品有两个独立维度：**上下架**（长期，仅 PC 后台）与**售罄**（当日，两端均可切）。
- **售罄按取餐日期生效，只影响当天**：商户在营业日 D 标记售罄，只屏蔽 D 当天的下单，**不影响 D+1 的预约**；次日自然清零，无需手工恢复。
- 售罄可**自由开关**：午餐卖完标售罄，晚餐补了货再切回可售。
- 用户端表现：可见、带蒙层、不可下单。
- 小程序商户端菜品页**只提供可售 / 售罄切换**，不提供编辑、上下架或新增。

> 一期没有数量库存，因此**没有任何自动的超卖保护**。某商品的预约量是否超出当餐产能，系统不做判断也不做提示；商户只能在现场发现不够时手工标售罄，已收进来的单需人工联系退款。该取舍已由客户确认，见 §16.1。

### 6.6 履约与核销（小程序商户端 + PC 后台）

- 商户订单列表按状态泳道展示：`已预约` / `制作中` / `待取餐` / `已完成` / `已退款`。
- **标记备好**：`制作中 → 待取餐`。主账号与子账号均可执行。
- **核销**：`待取餐 → 已完成`，是该转换的唯一路径。
  - 核销二维码使用服务端生成的不透明一次性 token，**在订单进入 `待取餐` 时生成**，绑定该订单，**不设时间过期**，核销成功后立即失效。
  - 扫码在**手机上**进行（小程序商户端）。扫码失败时可**手工输入 4 位取餐号**核销，两条路径调用同一服务端原子核销能力。
  - **手工输入只匹配当前营业日期的 `待取餐` 订单**。跨营业日未取的订单不能用取餐号核销，需在订单列表按日期筛出后对该条直接操作（核销或发起退款）。
  - 重复核销返回第一次结果，不重复计算营收或订单量。
  - 已退款订单不得核销。
- 所有转换由服务端校验前置状态、角色和幂等键；**生产禁止撤销或回退**。
- 商户端订单列表提供**按取餐号、订单号、手机号搜索**。

### 6.7 订单查询与退款（PC 后台）

- 主账号可按状态、取餐日期、取餐号、订单号、手机号查询全部订单。
- **「未取餐」查询口径**：营业日结束后仍处于 `待取餐` 的订单，作为一个筛选条件提供，**不是订单状态**。主账号可对其发起退款或事后核销。
- 主账号可按 §7.7 发起原路全额退款；一期无部分退款。
- **支付待处理列表**：§7.3 对账兜底产生的「有支付无订单」条目，主账号在此处理。

### 6.8 商品图片（PC 后台）

- 每个商品最多 3 张图片，第一张为封面。**由商户自行拍照上传**。
- 菜单列表、购物车、订单、后台列表一律只用封面。
- 可删除任意图片，非首张可一键「设为封面」并移到第一位。不做拖拽排序。
- 图片经上传接口存入对象存储后写入商品记录，不落本机存储。

### 6.9 营业设置与开屏图层（PC 后台）

**营业设置**

- 门店时区固定 `Asia/Shanghai`。一期为**午餐、晚餐两餐段**，不支持早餐。
- 每个餐段配置：**截单时刻、取餐时间范围、取餐时间粒度**（默认 30 分钟）。
- 配置今天、明天的可预约状态、特殊停餐日期、单取餐点名称、地址、说明和公告。
- 营业状态：营业中 / 休息中 / 已截单，主账号可手动切换，覆盖营业时间规则。
- 实际时刻与取餐点内容属于 UAT 前配置，但不得改变「单取餐点、午晚两餐段、仅预约取餐、可预约今天与明天」的模型。

**开屏图层**

- 主账号上传一张透明 PNG，在等比缩放的手机预览上拖拽定位、滑杆调整大小。
- 保存后展示在**用户端首页**（浮层，1.5 秒或点击后淡出）与**身份选择页**。
- **图片上传至对象存储，配置存服务端，向所有用户下发**；不使用本机存储。

### 6.10 两个商户端形态的分工

| | 小程序商户端（4 屏） | PC 网页后台（12 页） |
| --- | --- | --- |
| 使用者 | 主账号、子账号 | 仅主账号 |
| 定位 | 现场高频、单手操作 | 配置、批量、查询 |
| 能力 | 看单、标记备好、扫码与手工核销、切换可售/售罄、切换营业状态 | 商品与分类维护、价格、折扣率、名单、退款、财务、营业设置、开屏图层、看板 |
| 底部导航 | **订单 / 核销 / 菜品**，共三格 | 侧边导航 |
| 返回身份选择 | 订单页右上角入口 | 不适用 |

> 「切换营业状态」放在小程序商户端订单页顶部，理由是现场临时休息必须能用手机操作。评审记录未明确该项归属，见 §16.3。

### 6.11 财务与对账（PC 后台）

- 展示订单支付金额、支付时间、微信交易号。
- 支持按日期导出订单明细。
- 支持对账时核对微信支付账单。
- 退款记录退款单号、退款金额、退款状态与操作人。

### 6.12 数据看板（PC 后台）

- 指标：当日营收、当日订单、当月营收、当月订单、退款金额、商品销量排行。
- **商品销量排行来自真实订单数据**，不使用写死常量。
- 待办：**待制作数**。（`待取超时数` 与 `库存告急数` 随 D6、D2 删除。）
- `退款中` 与 `已退款` 订单按明确口径单独统计，不混入有效营收。

### 6.13 批量导入（PC 后台）

> **范围来源**：2026-08-19 客户评审记录未涉及批量导入；§6.4 原有的 CSV 导入表述继承自已删除的会员名单。本节由**项目负责人于 2026-08-21 确认纳入一期范围**。整份评审记录仍待客户书面签认，见 §16.4 C1。

一期提供两个独立的批量导入页面：**菜品批量导入**与**员工白名单批量导入**。两者共用同一套上传、解析、预览与提交流程，但模板、去重规则与校验各自独立。

#### 6.13.1 通用流程

- 文件格式 MUST 为 `.xlsx`。**不接受 CSV**：让商户自行另存为 CSV UTF-8 是已知的高失败率操作，一期改为直接接收 Excel 原文件。
- 解析 MUST 在服务端完成。客户端只负责选择文件、上传、渲染预览与提交确认，MUST NOT 在页面内解析或校验。
  > **P0 原型例外**：后端导入接口就位前，允许在 PC 后台的接口契约层（`apps/web-admin/data/api.js`）内实现一份本地 `.xlsx` 解析，用于验证流程、模板与校验规则。该实现**不构成生产契约**，与 §8.1 对 P0 mock 的定性一致；页面 MUST 只调用契约方法，MUST NOT 自行解析。后端就位时只替换契约层实现，页面代码不动。
- 流程固定为三步：**选择文件 → 服务端解析并返回预览 → 商户确认后提交入库**。预览与提交是两次独立请求；未提交前 MUST NOT 写入任何数据。
- 预览 MUST 给出三个计数：**新增 N 条 / 更新 M 条 / 异常 K 条**。异常项 MUST 可展开，逐条给出**行号**与**具体原因**。
- 存在异常行时 MUST 允许商户选择「跳过异常行提交」或「取消并修正后重传」，MUST NOT 因少量异常整批拒绝。
- 提交 MUST 幂等：同一预览令牌重复提交只生效一次。
- 首行 MUST 为表头，列按表头名称匹配，MUST NOT 依赖列顺序。表头缺少必填列时整份文件判定为异常并中止。
- 每份文件 MUST 限制最大行数，超出时中止并提示分批导入。

#### 6.13.2 菜品批量导入

**模板列**（与 §6.3 的表单字段一一对应）：

| 列名 | 必填 | 说明 |
| --- | :---: | --- |
| 菜品名称 | ✅ | 去首尾空格后非空 |
| 售价 | ✅ | 大于 0 的数值，单位元，入库转整数分 |
| 分类 | ✅ | 去首尾空格后精确匹配已有分类；**不存在则自动新建** |
| 餐段可售 | ✅ | 全天 / 午餐 / 晚餐，三选一 |
| 描述 | | 选填 |

- **图片 MUST NOT 进入模板。** 导入成功的商品先以占位图上架，商户随后在菜品管理中逐个补图。导入页 MUST 明确提示这一点。
- **去重规则：只新增，不更新。** 菜品名称在库中已存在时，该行 MUST 标记为异常并跳过，MUST NOT 覆盖既有商品。理由是菜品没有天然唯一键，覆盖语义不明确，且一次误传旧表就能把全部价格改回去且无法撤销。批量改价 MUST 继续使用菜品管理页既有的批量调价功能。
- **分类自动新建**：名称去首尾空格后精确匹配，命中则复用，未命中则新建，排序追加到末尾且默认启用。同一份文件中出现多次的同名新分类 MUST 只新建一次。预览 MUST 单独列出本次将新建的分类名称。
- 导入的商品 MUST 默认为可售状态。

#### 6.13.3 员工白名单批量导入

**模板只有两列**，与 §6.4 的两个可填字段一一对应：

| 列名 | 必填 | 说明 |
| --- | :---: | --- |
| 姓名 | ✅ | 去首尾空格后非空。§4.1 附加手机号双要素的第二要素 |
| 手机号 | ✅ | 唯一识别键，标准化后校验格式 |

- **模板 MUST NOT 包含其他任何列。** 状态、加入时间、已绑定、累计消费与累计单量均非填写字段：状态由页面开关切换且新增时默认启用，其余由系统生成。表头出现未知列时 MUST 忽略该列并在预览中提示，MUST NOT 因此判定整份文件异常。
- **去重规则：按手机号覆盖更新。** 手机号是唯一识别键，覆盖语义明确。更新时 MUST 保留加入时间、状态、累计消费、累计单量与微信绑定关系——导入 MUST NOT 把已停用的记录重新启用。
- 同一份文件中手机号重复时 MUST 判定为异常，MUST NOT 静默取最后一条。

#### 6.13.4 不做批量导入的对象

**商户账号名单不提供批量导入**（§4.4）。主账号与子账号数量极少，手工逐条添加即可，且该名单直接决定谁能进入商户端与 PC 后台，批量写入的误操作后果远大于收益。


## 7. 订单、支付和履约规则

### 7.1 六态状态机

生产订单状态必须且只能为：

1. `已预约`
2. `制作中`
3. `待取餐`
4. `已完成`
5. `退款中`
6. `已退款`

```text
主链路：（微信确认支付成功）──▶ 已预约 ──取餐前 30 分钟自动──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
旁路：  已预约 ──用户自助取消 / 主账号取消──▶ 退款中 ──微信确认退款成功──▶ 已退款
        制作中 / 待取餐 / 已完成 ──主账号发起退款──▶ 退款中 ──▶ 已退款
```

- **不存在 `待支付`**：支付成功前没有订单。
- **不存在 `已支付待接单`**：没有接单动作，支付成功直接进 `已预约`。
- **不存在 `已取消`**：支付前取消不产生订单；已支付订单被取消直接进 `退款中`。
- **不存在 `异常`**：退款结果无法确定时订单**停在 `退款中`**，后台挂待处理标记，最终按微信真实退款结果更新。用户端不展示异常态。
- 每次转换必须由服务端校验前置状态、资源权限和幂等键，并记录审计。相同幂等键重复请求返回第一次最终结果，不重复产生支付、退款、营收或核销副作用。**生产禁止撤销或回退已完成的转换。**

### 7.2 下单与支付

- 一期只实现正常支付流程。**不做迟到支付、不做库存重占、不做自动退款、不设异常订单流程。**
- 流程见 §5.7。关键约束：
  - 调起微信支付前的**内部预支付记录不是订单**，不进任何订单列表、不占取餐号、用户不可见。
  - **只有服务端确认微信支付成功才生成订单**并分配取餐号。
  - 生成订单时再次固化商品、价格、折扣率、身份、取餐日期与时间、取餐点快照。后续配置变化不回算历史订单。
  - 支付回调与订单生成必须幂等；同一 `out_trade_no` 重复通知不重复建单、不重复占号。

### 7.3 支付对账兜底

§7.2 不做迟到支付，但必须堵住「用户已付款、系统无订单」的资损口子：

- 定时任务扫描**已发起支付但未生成订单**且超过约定时长的预支付记录，调用微信支付**查询接口**核对真实支付结果。
- 查得**未支付**：作废该预支付记录，无后续动作。
- 查得**已支付**：幂等补建订单，分配取餐号，按 §7.4 判定进入 `已预约` 或 `制作中`。
- 补建失败（例如商品已下架、取餐时间已过、数据校验不通过）：**转入 PC 后台「支付待处理」列表**，由主账号人工处理（发起退款或人工建单）。
- 该链路对用户端不可见，不引入 `异常` 状态。用户在补建成功后于订单列表看到该单。

### 7.4 排产

- **取餐时间前 30 分钟**由服务端定时推进 `已预约 → 制作中`。
- 支付成功时若距取餐时间**已不足 30 分钟**，订单在生成时直接进入 `制作中`。
- **一期不提供商户手动提前开做**，也没有接单动作。
- 定时推进任务须幂等，并具备重试与补偿；任务漏跑不得导致订单卡在 `已预约`。

### 7.5 商户履约与核销

- 备好：`制作中 → 待取餐`，同时下发「待取餐提醒」订阅消息（用户已订阅时）。
- 核销成功：`待取餐 → 已完成`。规则见 §6.6。
- 一期**不设 `待取超时`**。备好后订单保持 `待取餐`，直至核销完成或发起退款。营业日结束后未核销的订单通过 §6.7 的「未取餐」口径查询。
- 任何角色不得跳过前置状态或使用客户端撤销回退生产状态。

### 7.6 用户取消

- `已预约` 且**距取餐时间大于 30 分钟**时：用户可自助取消，系统立即发起一次原路全额退款，订单进入 `退款中`。
- 进入 `制作中` 后（即距取餐不足 30 分钟，或支付时已不足 30 分钟）：**自助取消关闭**，只能联系商户处理。
- 其他状态不提供用户自助取消。
- 取消确认弹窗内一并请求「退款结果」订阅授权（§5.10）。

### 7.7 全额退款

- 一期只支持**原路全额退款**，任何部分退款请求必须拒绝且不创建退款记录。
- 用户自助取消或主账号发起退款后，订单进入 `退款中`。
- 微信确认退款成功后订单进入 `已退款`；受理成功、客户端提示或调用成功均不等于退款完成。
- **退款结果无法确定或退款失败**：订单**保持 `退款中`**，PC 后台挂待处理标记提醒主账号处理，最终按微信真实退款结果更新。不设 `异常` 状态。
- 一期没有库存，**不存在库存返还**。产能损耗由商户自行承担。

### 7.8 订单编号与取餐号

- 系统订单号用于唯一识别与对账。
- **取餐号为 4 位数字**，**按取餐日期**从 `0001` 顺序累计。即时单已删除，不再有前缀区分。
- 取餐号在订单生成时分配。**同一订单重复处理时始终返回原取餐号，不重复占号。**
- 取餐号在同一取餐日期内唯一。因不存在 `已取消` 状态，不涉及取消单号复用问题。
- 跨营业日的取餐号可能重复，因此手工核销必须限定当前营业日期，见 §6.6。

## 9. 非功能要求

### 9.1 一致性与幂等

- 后端是身份、商品、价格、销售状态、订单、支付、退款和核销的唯一事实源。
- 创建订单、支付回调、退款回调、状态推进、排产和核销均须幂等。
- 订单明细固化商品、价格、身份、折扣率、取餐日期与时间和取餐点快照，后续配置变化不回算历史订单。
- 支付结果无法自动确定时，走 §7.3 的对账兜底，不猜测成功、不生成订单、不引入异常态。

### 9.2 容量与可用性

- 支持 5–10 分钟集中 100–300 单、日 500–1000 单的已知规模。取餐号为 4 位，单日上限 9999 单，满足该规模。
- 下单、支付和核销路径使用原子操作与明确超时，不因统计任务阻塞核心交易。
- 空、加载、弱网、重复提交和外部调用失败必须提供可恢复结果；重试不得重复产生副作用。

### 9.3 权限与审计

- 用户只能访问自己的订单。
- 主 / 子账号资源权限由服务端执行，客户端菜单隐藏不能代替鉴权。
- 关键操作记录操作者、时间、对象、前后状态、原因和幂等键。
- 开发人员生产排障需要客户限时授权。

### 9.4 敏感数据

- 密钥、证书内容和服务端凭据不得进入客户端、PRD、OpenSpec、外部 Gate 台账或日志。
- 台账不得记录账号标识、真实手机号、名单或其他个人数据，只保存非敏感证据引用和状态。
- 手机号、姓名和订单个人信息按最小必要范围收集、展示和授权访问。

### 9.5 数据保护与异常恢复

- 核心数据需要备份与恢复演练方案。
- 支付、退款、待处理条目和关键操作可查询、可审计、可人工处理。
- 数据恢复不得绕过六态与支付事实约束。

## 10. UI 与体验要求

### 10.1 视觉蓝本

§15 的色彩、字体、间距、组件和交互反馈作为一期视觉蓝本。任何视觉实现不得改变 §1–§14 的身份、价格、预约、状态、权限或支付结果。

### 10.2 用户端

- 浏览阶段不提前索取手机号，**启动时不得弹出手机号授权**。
- 结算页清晰展示取餐日期、取餐时间、单取餐点、原价小计、员工折扣和应付金额。
- 支付中、支付结果确认中、退款中均有独立状态，不用「支付成功」动画替代服务端事实。支付结果未确认时只显示临时加载提示。
- **不可执行操作必须禁用并说明原因**，并在可能时给出替代动作（已截单餐段折叠并标注截止时刻、售罄商品蒙层、空购物车禁用结算）。
- 取餐时间是约定时刻不是到场窗口，文案须表述为「预计 hh:mm 备好，备好后通知你」，避免用户误以为必须准时到场。

### 10.3 商户后台

- 按主 / 子账号展示必要导航和字段；敏感信息按最小权限脱敏。
- 订单主操作与六态一致，不展示生产撤销。
- 核销、退款和待处理条目必须先展示目标订单和结果，不以 Toast 作为唯一审计证据。
- 小程序端底部导航固定为**订单 / 核销 / 菜品**三格。

## 11. 数据统计

- 统计来源为服务端确认的订单、支付、退款和核销数据。
- 基础看板包含当日与当月有效营收、有效订单数、退款金额和商品销量。
- `退款中`、`已退款` 订单必须按明确口径单独统计，不混入有效营收。
- **「未取餐」为查询口径**（营业日结束后仍处于 `待取餐`），单独可查，不计入已完成订单数。
- 财务只读查询与导出由主账号执行，任何统计页面不得修改交易事实。

> 一期不建设访问量与点击量埋点，看板不提供相关指标。

## 12. 正式业务不变量

1. 一期是单门店、单取餐点、到店自提，**只有预约取餐一种方式**。
2. 可预约今天与明天；餐段仅午餐和晚餐；门店时区为 `Asia/Shanghai`。
3. **一期没有数量库存、没有软预占、没有自动扣减**。商品只有上下架与**按取餐日期的当日售罄**两个维度。
4. 每个餐段一个固定截单时刻，餐段内所有取餐时间共用；取餐时间为离散时间点，是约定时刻不是到场窗口。
5. **只有服务端确认微信支付成功才生成订单**；支付取消或失败不生成订单。调起支付前的预支付记录不是订单。
6. 「有支付无订单」由 §7.3 对账兜底处理，补建或转人工，**不引入异常状态**。
7. 公开订单状态只有**六态**：`已预约` / `制作中` / `待取餐` / `已完成` / `退款中` / `已退款`。状态转换由服务端单向执行，生产禁止撤销。
8. 取餐时间前 30 分钟自动进 `制作中`；**没有接单，也不提供手动提前开做**。
9. `已预约` 且距取餐大于 30 分钟可自助取消；进入 `制作中` 后不可自助取消。
10. 一期无部分退款，只有微信确认退款成功才是 `已退款`；退款结果不确定时停在 `退款中` 并挂后台待处理标记。**没有库存返还。**
11. 浏览免手机号；首次提交订单前必须微信授权手机号；**员工折扣白名单**决定员工身份。手工填写的附加手机号需「手机号 + 姓名」双要素命中。
12. 算价链固定为**原价小计 → 员工折扣 → 应付**；折扣为**全局单一折扣率**、**逐商品**先舍入到分再乘数量；金额一律整数分。**没有等级、没有优惠券。**
13. 商户只有**主账号与子账号**两个角色；主账号可多个，子账号仅限小程序端四项现场动作；资源权限由服务端执行。
14. 取餐号为 4 位数字，**按取餐日期**从 `0001` 累计，同一订单幂等返回原号；手工核销限当前营业日期。
15. 一期只有**两类订阅消息**：待取餐提醒、退款结果，均由用户主动订阅。
16. mock、客户端内存态、前端支付结果和 §15 简化状态都不是生产事实源。

## 14. 验收标准

- 用户能免手机号浏览；**启动时不弹手机号授权**；首次提交订单前完成微信手机号授权并由服务端判定员工 / 访客。
- 手工填写的附加手机号，仅在「手机号 + 姓名」同时命中白名单时才取得员工身份；只命中手机号不生效。
- 用户可选择今天或明天的取餐时间点，已截单餐段整组折叠并标注截止时刻，当日全截时「今天」置灰且默认落到明天。
- 菜单按所选取餐时间的餐段过滤；未绑定手机号时只展示原价，绑定并命中后展示划线原价与员工价。
- 菜单与详情页展示的员工价，**逐项等于**结算明细中的成交价；金额为整数分。
- 支付取消或失败**不生成订单**；只有微信确认支付成功才生成订单并分配取餐号。
- **支付对账兜底可复现**：模拟回调丢失，定时任务能查得已支付并补建订单；补建失败时进入「支付待处理」列表。
- 提交订单时若目标餐段已截单，支付被拦截，用户被送回时间选择，购物车保留。
- 取餐时间前 30 分钟自动进 `制作中`；支付时已不足 30 分钟的订单生成即为 `制作中` 且无自助取消入口。
- 六态与所有合法 / 非法转换可复现；**生产不存在撤销入口**；用户端不出现待支付、已取消、异常。
- 二维码只在 `待取餐` 出现，核销后立即失效；扫码与手工输入幂等，重复核销不重复统计。
- **手工输入取餐号只匹配当前营业日期**；构造跨日同号场景不产生误核销。
- 商户标记售罄只影响当天，次日预约不受影响，且次日自动恢复可售。
- 用户自助取消、主账号退款、退款失败保持 `退款中` 并挂后台待处理标记，符合 §7.7。
- 订阅消息只有两类，分别在支付成功页与取消确认弹窗请求；拒绝订阅后首页提示条与取餐码页补订阅入口可用。
- 主 / 子账号只能执行授权动作；子账号无法进入 PC 后台；PC 后台微信扫码登录仅主账号可通过。
- 分类改动落库且与商品编辑联动；开屏图层由服务端下发，换设备仍可见，且在首页浮层与身份选择页均生效。
- 「未取餐」查询口径可用，且不计入已完成订单数与有效营收。
- 外部 Gate 只在对应阶段生效；任何台账不含敏感数据。

## 15.1 产品概述

绥安食品到店自提预约点餐系统。**单一小程序内含两端**：普通用户冷启动直接进用户端首页；已绑定商户手机号的 openid 冷启动进身份选择页，可选进入用户端或商户端。另有独立的 PC 网页商户后台。

关键业务约束：仅到店自提、仅预约取餐；取餐凭证为 4 位取餐号 + 二维码；有营业状态（营业中 / 休息中 / 已截单）与按餐段的固定截单时刻。

## 15.7 订单状态机改造

**目标态：六态**（见 §7.1）

```
（微信确认支付成功）──▶ 已预约 ──取餐前 30 分钟──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
已预约 ──取消──▶ 退款中 ──微信确认──▶ 已退款
制作中 / 待取餐 / 已完成 ──主账号退款──▶ 退款中 ──▶ 已退款
```

**当前实现**（`apps/wechat-miniprogram/utils/util.js`）

```js
const NEXT = { 待制作: '待取餐', 待取餐: '已完成' };
const ACT  = { 待制作: '备好', 待取餐: '核销', 已完成: '查看', 已取消: '查看' };
```

**改造要点：**

- 前端「待制作」改名为「**制作中**」；补 `已预约`、`退款中`、`已退款` 三态；**不需要**九态中的 `待支付` / `已支付待接单` / `已取消` / `异常`。
- 补取餐前 30 分钟的自动排产（由服务端定时任务驱动，前端只展示）。
- 前端状态推进改为**服务端单向驱动**，前端只展示后端返回的状态，不在本地内存推进。
- **必须移除「撤销」**：`advanceOrder` 的 Toast 撤销是 P0 演示能力，§7.1 禁止生产撤销或回退。
- 商户端每个订单卡仍只暴露**一个主行动按钮**：`备好 → 核销 → 查看`。
- 核销是 `待取餐 → 已完成` 的唯一路径。

## 15.8 边界与异常（改造后）

| 场景 | 期望行为 |
| --- | --- |
| 已截单 / 休息中 | 用户端下单入口禁用并提示；菜单仅浏览 |
| 目标餐段已截单 | 时间选择弹层中该餐段整组折叠并标注截止时刻；当日全截时「今天」置灰、默认落明天 |
| 当日售罄 / 已下架 | 售罄：可见 + 蒙层 + 禁用；下架：用户端不展示。已加购的需在结算与提交时校验并提示 |
| 菜品不在所选取餐时间的餐段 | 用户端不展示；商户端可见 |
| 提交订单时目标餐段已截单 | 拦截支付，提示已截单，送回时间选择，**购物车保留** |
| 提交订单时变价或售罄 | 提示用户确认后再继续；用户不确认则不进入支付 |
| 用户取消支付 / 支付失败 | **不生成订单**，预支付记录作废，停留确认页可重试 |
| 支付结果未确认 | 用户端只显示临时加载提示，**不生成订单、不展示异常态** |
| 有支付无订单 | §7.3 对账兜底：查得已支付则补建订单；补建失败进「支付待处理」由主账号处理 |
| 支付成功时距取餐不足 30 分钟 | 订单生成即为 `制作中`，无自助取消入口 |
| 排产定时任务漏跑 | 须重试与补偿，不得让订单卡在 `已预约` |
| 用户在距取餐 > 30 分钟时取消 | 进 `退款中`，弹窗内请求退款结果订阅 |
| 用户在距取餐 ≤ 30 分钟时尝试取消 | 取消入口不展示；文案提示联系商户 |
| 退款受理成功但结果未确认 | 订单保持 `退款中`，后台挂待处理标记，不进 `已退款`、不进异常态 |
| 二维码在 `已预约` / `制作中` | 不渲染；只显示取餐号、取餐时间与状态 |
| 重复核销 | 已完成单再次扫码提示「已核销」，不重复计数 |
| 已退款订单扫码 | 提示订单已退款，拒绝核销 |
| 手工输入取餐号，跨日同号 | 只匹配**当前营业日期**的 `待取餐` 订单；昨日未取单需在订单列表按日期筛出后处理 |
| 营业日结束仍 `待取餐` | 保持该状态，不自动流转；通过「未取餐」筛选查询，主账号可退款或事后核销 |
| 商户标记售罄 | 只影响当天，次日预约不受影响，次日自动恢复可售 |
| 用户拒绝订阅 | 首页进行中订单条 + 取餐码页「开启取餐提醒」补订阅入口 |
| 未绑定手机号点结算 | 引导至个人中心完成微信手机号授权，绑定后**返回结算页继续**，购物车保留 |
| 附加手机号只命中手机号、姓名不符 | 不授予员工身份，提示核对姓名 |
| 访客进入确认页 | 优惠卡显示「访客 · 原价」，不显示折扣行 |
| 空购物车 | 「去结算」禁用 |
| 无待取订单点首页取餐码 | Toast 提示无待取餐订单 |
| 上传非 `.xlsx` 文件 | 中止并提示只接受 `.xlsx`，不做格式猜测 |
| 表头缺少必填列 | 整份文件判定为异常并中止，不进入逐行解析 |
| 导入文件超出最大行数 | 中止并提示分批导入 |
| 菜品导入命中同名商品 | 该行标记异常并跳过，不覆盖既有商品 |
| 菜品导入的分类不存在 | 自动新建，排序追加末尾且默认启用；预览单独列出新建的分类 |
| 员工导入同一文件内手机号重复 | 判定为异常，不静默取最后一条 |
| 预览后重复提交同一令牌 | 只生效一次 |
| 菜品无图 | 按品类渐变 + 宋体首字占位，不开天窗 |
| 菜品仅 1 张图 | 详情页不显示计数、不启用滑动，仍可全屏预览 |
