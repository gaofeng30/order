# 在线点单系统 PRD

> 版本：一期正式研发产品基线
> 状态：本地技术基线；外部依赖按 §13 分阶段验收
> 文档结构：§1–§14 定义正式生产行为；§15 保留 P0 视觉与交互蓝本，冲突时不得覆盖 §1–§14。

## 1. 项目背景

本项目为单门店餐饮经营主体提供微信小程序在线点单、微信支付、固定时段预约自提，以及配套商户 Web 后台。客户是经营、收款、退款、隐私和发布责任主体；开发方负责开发、配置、联调、提审协助、技术排障和运维支持。

客户已经认可 P0 原型的视觉和主要交互方向。P0 允许使用 mock 数据、独立内存状态、假支付和简化状态机；这些内容仅证明页面蓝本，不构成生产数据、权限、支付或状态契约。

## 2. 产品目标

一期唯一目标是交付一条可验收的单门店到店预约自提闭环：用户浏览与结算身份识别 → 服务端商品价格和按餐段每日库存 → 15 分钟支付软预占 → 微信支付 → 商户接单、制作和备好 → 单取餐点核销 → 完成或原路全额退款 → 基础后台查询和经营数据。

一期必须满足：

- 员工和访客均可浏览、预约和支付。
- 员工由启用员工名单识别，可使用逐商品固定员工价。
- 库存、价格、身份、订单、支付、退款和核销均以后端为唯一事实源。
- 商户使用明确的四角色权限处理商品、履约、核销、退款和只读财务。
- 外部账号、资质和生产配置按 §13 的 Gate 在对应阶段完成，不阻塞本地产品与技术 OpenSpec。

## 3. 一期范围与文档依据

### 3.1 一期包含范围

- 单门店、单取餐点、到店预约自提。
- 微信小程序用户端和商户 Web 基础后台。
- 员工与访客；手机号启用名单识别员工。
- 商品分类、商品、图片、上下架、售罄、正常价和逐商品固定员工价。
- `营业日期 × 餐段 × 商品`的每日库存。
- 仅今天、明天的午餐和晚餐固定取餐时段，每个时段独立截单。
- 购物车、订单、微信支付、15 分钟软预占和超时释放。
- 商户接单、制作、备好、扫码或手工核销。
- 用户规则内取消、商户处理和原路全额退款。
- 基础看板、支付退款只读查询和关键操作审计。

### 3.2 一期排除范围

一期不包含会员等级、优惠券、积分、储值、部分退款、配送、多门店、多档口、多商户、POS、打印机、叫号屏、企业月结、发票及第三方 ERP/财务/食堂系统对接。排除项不得以“预留后启用”或兼容分支进入一期产品契约；需要时必须独立立项并取得新的范围授权。

逐商品固定员工价是一期简单定价规则，不属于会员等级、优惠券或积分体系。

### 3.3 文档优先级和合同证据边界

正式研发按以下唯一顺序裁决：

1. 真实适用合同与客户正式确认记录。
2. 本 PRD §1–§14。
3. 本 PRD §15、小程序源码和 PC 原型。
4. mock 数据、客户端内存状态和原型简化状态机仅用于演示，不是生产契约。

仓库范围内未发现已签署证据，现实签署状态未知。该表述只说明仓库证据边界，不判断现实中合同已签署或未签署；合同适用性属于商业与上线外部依赖，不阻塞本地技术 OpenSpec 的规划、严格校验和提交。

## 4. 用户与后台角色

### 4.1 员工与访客

- 用户无需登录或手机号即可浏览门店、分类、商品和公开营业信息。
- 首次结算必须建立微信会话、完成手机号授权并提供姓名；缺少任一项不得结算。
- 服务端标准化手机号后匹配当前启用员工名单：命中为员工，未命中或名单记录停用为访客。
- 客户端不得让用户自行选择员工身份；手工输入手机号不得替代可信手机号授权。
- 订单创建时固化员工/访客身份、内部用户引用和员工名单版本快照。
- 页面和日志只展示必要的脱敏信息，不公开员工名单或完整手机号。

### 4.2 店管

店管可管理商品、分类、员工名单、正常价、`employee_price`、营业预约设置、全部订单、原路全额退款和基础看板，并查看关键操作审计。

### 4.3 后厨

后厨只可查看履约所需的订单和必要联系人信息，并执行接单、制作和备好；不得修改商品价格、员工名单、权限或退款。

### 4.4 核销

核销角色只可查看待取餐订单的最少必要信息，并执行二维码或手工取餐号核销；不得接单、改价或退款。

### 4.5 财务只读

财务只读角色只能查看支付、退款、交易结算和导出结果，不得执行任何业务写操作。

四角色及资源权限必须由服务端执行。普通用户不得自行进入商户端或选择后台角色；开发人员不默认持有常驻业务角色，生产排障只能使用客户明确授权、限时且有审计的访问。

## 5. 用户端功能

### 5.1 首页与菜单

- 全天展示门店、公告、取餐点、分类、商品、图片、正常价、员工登录后的适用价格、售罄和上下架结果。
- 商品数据、价格、库存和营业状态由后端返回；客户端不得用 mock 或缓存覆盖后端事实。
- 下架商品不展示；售罄商品可展示但不可加入购物车。

### 5.2 商品详情与购物车

- 商品详情展示名称、图片、说明、规格、口味选项、价格和可售状态。
- 购物车保存用户选择，不锁定价格或库存；进入结算和提交订单时必须重新向后端校验。
- 数量为零的商品从购物车移除，空购物车不得进入结算。

### 5.3 预约选择

- 一期所有订单必须选择固定取餐时段，不提供即时单或“尽快”模式。
- 门店时区固定为 `Asia/Shanghai`。
- 可选营业日期仅为门店当地日期的今天和明天；餐段仅为午餐和晚餐。
- 每个固定取餐时段必须归属一个餐段并拥有独立截单时间。
- 用户可全天浏览，但只有目标时段尚未截单且商品可售时才能提交订单。
- 一期为单门店单取餐点，不提供多点选择或分单路由。

### 5.4 结算身份与价格

- 首次进入结算时执行 §4.1 的微信会话、手机号和姓名校验。
- 商品正常价和可选 `employee_price` 均以整数分保存，由服务端计算。
- 员工购买配置了 `employee_price` 的商品时使用员工价；未配置员工价的商品和所有访客使用正常价。
- 客户端提交的价格不可信；报价和订单明细固化正常价、适用员工价、成交价、身份及价格版本。
- 一期不计算百分比折扣，不叠加会员等级、优惠券、积分或储值权益。

### 5.5 提交订单与微信支付

1. 服务端重新校验身份、商品状态、服务端价格、营业日期、餐段、时段截单和库存。
2. 校验通过后原子创建 15 分钟库存软预占和`待支付`订单。
3. 用户调用微信支付；前端成功回调只表示客户端流程结束，不作为支付成功事实。
4. 服务端根据微信支付结果确认支付；支付成功后把软预占原子转为实扣和有效预约，订单进入`已支付待接单`。
5. 15 分钟内未确认支付成功时，订单进入`已取消`并释放完整软预占。
6. 迟到支付按 §7.3 处理，不得仅凭客户端跳转恢复订单。

### 5.6 订单列表与详情

- 用户只能查看自己的订单。
- 列表和详情显示九态中的当前状态、服务日期、餐段、时段、取餐点、商品价格快照、实付金额、取餐号和可用操作。
- 只有`待取餐`订单展示有效核销二维码；二维码内容不得直接暴露敏感信息。
- 页面状态必须以后端返回为准，不根据本地内存单独推进。

## 6. 商户后台功能

### 6.1 登录与权限

后台所有页面和接口执行 §4 的四角色服务端鉴权。无角色用户不得进入后台；越权请求必须拒绝且不产生业务副作用。关键写操作记录操作者、时间、目标、前后状态、原因和幂等键。

### 6.2 商品分类与商品

- 店管可新增、编辑、排序和停用分类。
- 店管可新增、编辑、上下架和标记售罄商品，管理图片、说明、规格和口味选项。
- 商品正常价为必填整数分；`employee_price`为可选整数分。
- 修改价格只影响新报价；既有订单使用下单时固化的价格快照。

### 6.3 库存

- 库存唯一键为`营业日期 × 餐段 × 商品`。
- 午餐和晚餐使用独立库存池；同一餐段内所有固定取餐时段共享该餐段商品库存，不增加时段库存维度。
- 后端维护总量、软预占量、已售量和可售量，是唯一事实源。
- 订单提交只创建 15 分钟软预占，支付成功才转为实扣；超时、取消和退款按 §7 的唯一规则释放或返还。
- 后端必须通过原子条件更新避免超卖；客户端展示值不能绕过服务端库存结果。

### 6.4 营业与预约设置

- 门店时区固定 `Asia/Shanghai`。
- 店管配置午餐、晚餐各自的固定取餐时段和每个时段独立截单时间。
- 店管配置当天和明天的可预约状态、特殊停餐日期、单取餐点名称、地址、说明和公告。
- 实际时段、截单和取餐点内容属于 UAT 前配置，但不得改变“今天/明天、午/晚固定时段、无即时单、单取餐点”的模型。

### 6.5 订单履约

- 后厨查看`已支付待接单`和`制作中`订单，并依次执行接单和备好。
- 接单使订单进入`制作中`；备好使订单进入`待取餐`。
- 所有转换由服务端校验前置状态、角色和幂等键；生产禁止撤销或回退。
- 异常订单必须可由店管和授权技术人员按审计记录追踪，不得静默改状态。

### 6.6 核销

- 核销二维码使用服务端生成的不透明一次性 token，仅对`待取餐`订单有效。
- 扫码和手工输入取餐号调用同一服务端原子核销能力。
- 核销成功使订单进入`已完成`，并记录核销人、时间和方式。
- 重复核销返回第一次结果，不重复计算营收或订单量。

### 6.7 支付、退款与看板

- 店管可按 §7.6 发起原路全额退款；一期无部分退款。
- 财务只读可查看支付、退款、交易结算和导出，不得发起退款或修改订单。
- 看板只统计服务端已确认的数据；今日营收、订单数和销量必须有明确统计口径，不由客户端 mock 累加。

## 7. 订单、库存、支付和履约规则

### 7.1 九态生产状态机

生产订单状态必须且只能为：

1. `待支付`
2. `已支付待接单`
3. `制作中`
4. `待取餐`
5. `已完成`
6. `已取消`
7. `退款中`
8. `已退款`
9. `异常`

标准履约链路为：

```text
待支付 → 已支付待接单 → 制作中 → 待取餐 → 已完成
```

取消、退款和钱单/库存结果无法自动确定时分别进入对应状态。每次转换必须由服务端校验前置状态、资源权限和幂等键，并记录审计。相同幂等键重复请求返回第一次最终结果，不重复产生库存、支付、退款、营收或核销副作用。生产禁止撤销或回退已经完成的转换。

### 7.2 软预占与正常支付

- 提交订单原子创建 15 分钟库存软预占和`待支付`订单。
- 软预占不计为已售库存或有效预约。
- 服务端确认微信支付成功后，软预占原子转为实扣，订单进入`已支付待接单`并成为有效预约。
- 15 分钟内未确认支付成功，订单进入`已取消`并完整释放软预占。
- 支付通知、超时释放和状态转换均须幂等。

### 7.3 迟到支付

- 已超时订单收到可验证的迟到支付成功通知时，服务端先幂等确认支付事实，再按原`营业日期 × 餐段 × 商品`完整原子重占库存。
- 重占成功：转为实扣和有效预约，订单进入`已支付待接单`。
- 重占失败：不得形成预约，系统只发起一次原路全额退款并把订单置为`异常`。
- 迟到支付自动退款成功后订单进入`已退款`；退款未成功前保持可追踪的`异常`。

### 7.4 商户履约与核销

- 后厨接单：`已支付待接单 → 制作中`。
- 后厨备好：`制作中 → 待取餐`。
- 核销成功：`待取餐 → 已完成`。
- 任何角色不得跳过前置状态或使用客户端“撤销”回退生产状态。

### 7.5 用户取消

- `待支付`：用户可直接取消，订单进入`已取消`并释放软预占，不发起退款。
- `已支付待接单`且商户未接单、目标时段未到截单时间：用户可自助取消，系统立即发起一次原路全额退款。
- 商户接单或目标时段到达截单时间任一先发生后：用户自助取消关闭，只能联系商户处理。
- 其他状态不提供用户自助取消。

### 7.6 全额退款

- 一期只支持原路全额退款，任何部分退款请求必须拒绝且不创建退款记录。
- 除迟到支付重占失败的异常自动退款外，用户或店管发起退款后订单进入`退款中`。
- 微信确认退款成功后订单进入`已退款`；受理成功、客户端提示或调用成功均不等于退款完成。
- 商户接单前退款成功，返还对应`营业日期 × 餐段 × 商品`实扣库存。
- 商户接单后由店管处理的退款不自动恢复可售库存，需要店管按真实经营损耗调整后续库存。

## 8. 版本范围

### 8.1 P0 可预览原型

P0 已完成视觉、页面覆盖和演示交互确认，允许 mock、独立内存状态、假支付、简化状态和撤销按钮。P0 的验收价值是界面与交互方向，不证明生产支付、权限、跨端同步或数据持久化。

### 8.2 一期 MVP 正式开发必做

- §3.1 全部包含范围。
- §4 的员工/访客识别和后台四角色。
- §5 的固定预约用户闭环和服务端报价。
- §6 的商品、`employee_price`、三维库存、营业设置、履约、核销、退款和基础看板。
- §7 的九态、15 分钟软预占、微信支付、迟到支付、取消和全额退款。
- §9 的稳定性、安全、审计和敏感数据边界。
- §13 对应阶段必须完成的外部 Gate 和 UAT 前配置。
- §14 全部验收与追踪矩阵。

### 8.3 后续独立能力

会员等级、优惠券、积分、储值、部分退款、配送、多门店、POS、打印机、叫号屏及其他 §3.2 排除项不属于一期。后续若需实施，必须分别获得范围授权、建立独立 OpenSpec，并不得改变已经生成的一期订单快照。

## 9. 非功能要求

### 9.1 一致性与幂等

- 后端是身份、商品、价格、库存、订单、支付、退款和核销的唯一事实源。
- 创建订单、库存预占/实扣/释放/返还、支付回调、退款回调、状态推进和核销均须幂等。
- 钱单或库存结果无法自动确定时进入`异常`，保留原因和处理记录，不得猜测成功。
- 订单明细固化商品、价格、身份、预约和取餐点快照，后续配置变化不回算历史订单。

### 9.2 容量与可用性

- 支持 5–10 分钟集中 100–300 单、日 500–1000 单的已知规模。
- 下单、支付和核销路径使用原子操作与明确超时，不因统计任务阻塞核心交易。
- 空、加载、弱网、重复提交和外部调用失败必须提供可恢复结果；重试不得重复产生副作用。

### 9.3 权限与审计

- 用户只能访问自己的订单。
- 四角色资源权限由服务端执行，客户端菜单隐藏不能代替鉴权。
- 关键操作记录操作者、时间、对象、前后状态、原因和幂等键。
- 开发人员生产排障需要客户限时授权；客户仍是管理员、经营和收款责任主体。

### 9.4 敏感数据

- 密钥、证书内容和服务端凭据不得进入客户端、PRD、OpenSpec、外部 Gate 台账或日志。
- 台账不得记录账号标识、真实手机号、员工名单或其他个人数据，只保存非敏感证据引用和状态。
- 手机号、姓名和订单个人信息按最小必要范围收集、展示和授权访问。

### 9.5 数据保护与异常恢复

- 核心数据需要备份与恢复演练方案。
- 支付、退款、异常订单和关键操作可查询、可审计、可人工处理。
- 数据恢复不得绕过九态、库存和支付事实约束。

## 10. UI 与体验要求

### 10.1 视觉蓝本

P0 §15 的色彩、字体、间距、组件、页面布局和交互反馈可作为一期视觉蓝本。任何视觉实现不得改变 §1–§14 的身份、价格、预约、状态、权限或支付结果。

### 10.2 用户端

- 浏览阶段不提前索取手机号。
- 结算页清晰展示日期、午/晚餐段、固定时段、截单、单取餐点、正常价/适用员工价和应付金额。
- 支付中、支付结果确认中、库存变化、退款中和异常均有独立状态，不用“支付成功”动画替代服务端事实。
- 不可执行操作必须禁用并说明原因。

### 10.3 商户后台

- 按四角色展示必要导航和字段；敏感信息按最小权限脱敏。
- 订单主操作与九态一致，不展示生产撤销。
- 核销、退款和异常处理必须先展示目标订单和结果，不以 Toast 作为唯一审计证据。

## 11. 数据统计

- 统计来源为服务端确认的订单、支付、退款和核销数据。
- 基础看板包含今日有效营收、有效订单数、退款金额和商品销量。
- 已取消、退款中、已退款和异常订单必须按明确口径单独统计，不混入有效营收。
- 财务只读可查询和导出，任何统计页面不得修改交易事实。

## 12. 正式业务不变量

1. 一期是单门店、单取餐点、固定预约自提，无即时单。
2. 预约仅今天和明天，餐段仅午餐和晚餐，门店时区为`Asia/Shanghai`。
3. 库存唯一键为`营业日期 × 餐段 × 商品`；午晚餐独立，同餐段时段共享。
4. 下单原子软预占 15 分钟；服务端确认支付成功才实扣和形成有效预约，超时释放。
5. 迟到支付先完整重占，失败自动原路全额退款并进入`异常`，退款成功转`已退款`。
6. 公开订单状态只有九态，状态转换由服务端单向执行，生产禁止撤销。
7. 未支付可取消；已支付未接单且未截单可自助全退；接单或截单后仅商户处理。
8. 一期无部分退款，只有微信确认退款成功才是`已退款`。
9. 浏览免手机号；首次结算需微信会话、手机号和姓名；启用员工名单决定员工身份。
10. `employee_price`是逐商品可选固定整数分；服务端算价并固化正常价、员工价和成交价。
11. 后台只有店管、后厨、核销、财务只读四角色，资源权限由服务端执行。
12. mock、客户端内存态、前端支付结果和 §15 简化状态都不是生产事实源。

## 15.1 产品概述（原型）

绥安食品到店自提点餐小程序。**单一小程序内含两端**，启动时由用户自选身份进入：

| 端 | 角色 | 核心任务 |
| --- | --- | --- |
| 用户端 | 顾客 | 浏览菜单 → 点单 → 在线支付 → 到店凭取餐码自提 |
| 商户端 | 店员 / 店长 | 接单 → 制作 → 扫码核销 → 菜品与经营管理 |

**关键业务约束**
- 仅支持**到店自提**，无配送（"外卖配送"为占位入口，标注未开放）。
- 取餐凭证为**取餐号 + 二维码**（如 `A126`），核销后订单完成。
- 有**截单时间**（默认 16:30）与营业状态（营业中 / 休息中 / 已截单），影响下单可用性。

## 15.7 订单状态机（原型核心逻辑）

> ⚠️ 与 §7.1 正式九态的差异：原型实现简化 6 态，且未含完整支付、退款与异常语义。本节只描述 P0 当前行为；生产状态、转换权限、幂等和禁止撤销规则以 §7 为准。

```
用户端：
  [下单未支付] 待支付 ──支付──▶ 待取餐(商户视角进入待接单)
  待支付 ──超时/取消──▶ 已取消

商户端履约推进（单向，每步一个主按钮）：
  待接单 ──接单──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
  任意活跃态 ──取消──▶ 已取消
```

- 商户端每个订单卡只暴露**一个主行动按钮**，文案随状态变化：`接单 → 备好 → 核销 → 查看`。
- **核销**（M04 / M03）是「待取餐 → 已完成」的唯一路径，核销成功后工作台营收/订单数实时 +1。
- 推进操作给 Toast 反馈，**支持「撤销」**（回退到上一状态）。
- 批量操作仅在「待接单」泳道开放（批量接单）。

- 单图时不启用滑动、不显示计数；无图时沿用按品类渐变 + 首字占位。
- 右下角「2 / 3」半透明计数胶囊（首页 Banner 已用圆点，此处用计数区分层级）。
- 点击任意图片调 `wx.previewImage` 进入全屏预览，可继续滑动与缩放。

## 15.9 商户端模块详述

### M01 工作台

### M02 订单管理
- 搜索栏（取餐号/订单号/手机号）+ 筛选。

### M03 订单详情（商户）

### M04 扫码核销
- 全屏深色取景框 + 扫描线动画。

  - 无效号 → Toast 报错。
  - 已完成 → 提示「已核销」。

  - 待取餐 → 展示订单匹配卡（取餐号 + 明细 + 联系人 + 实付）→ 「确认核销」→ 置已完成 + Toast（看板已更新）。

### M05 菜品管理

- **「上架新菜」入口条幅**（深蓝渐变按钮，搜索框下方）→ M06（新增模式 `id=null`）。

- 菜品卡：缩略图（售罄蒙层）+ 名称 + 可购/售罄/下架胶囊 + 价 + 库存（告急红）+ 月售；

- 底部「保存设置」。

> 以下 M10–M14 为二期能力，不在一期合同范围。

### M10 会员等级
- 顶部深色规则卡：等级由低到高、一人一档、折扣常驻、非名单用户按原价。
- 等级卡：序号圆 + 等级名 + 折扣胶囊 + 说明 + 「N 位会员 · M 张券适用」+ 右侧上移/下移按钮与编辑/删除。
- 底部虚线「新增等级」。
- **编辑弹层**：等级名称 / 折扣（填「几折」，实时回显，不打折填 10）/ 说明。
- **删除弹层**：先展示影响面（该档会员数、把它列为适用等级的券清单），再选会员去向（其他档位或「降为非会员」），选降为非会员时给出红色警示。确认后一次性完成迁移，并自动摘除券的该适用等级；券因此无任何适用等级时自动停用并在 Toast 中告知数量。

### M11 会员名单
- 搜索框（手机号或姓名，实时过滤）。
- 深色「批量导入名单」Banner（→M12）。
- 统计条：名单人数 / 已绑定微信 / 已停用 + 右侧「+」手动新增（→M13）。
- 等级筛选段（全部 + 各等级，带计数）。
- 会员卡：头像首字 + 姓名 + 等级胶囊 +（已停用胶囊）+ 脱敏手机号 + 单位·部门·工号 + 右侧累计消费/单量/绑定状态胶囊。
- 空状态区分「没有匹配的会员」与「该等级下暂无会员」。

### M12 名单导入
- **待选态**：深色「导入三步」卡（整理 → 另存 CSV UTF-8 → 发到微信聊天 → 从聊天选择），并显式警告 Excel 默认 CSV 为 GBK 会乱码；模板列卡（必填/选填标注、示例行、「复制表头」、当前可用等级名清单）。
- 底部按钮「从微信聊天选择 CSV 文件」→ `wx.chooseMessageFile`。
- **预览态**：文件名 + 重选；三色计数「新增 / 更新 / 异常」；异常明细可展开，逐行显示行号、原始内容与原因；待导入明细逐条列出「新增/更新」标签、姓名、脱敏手机号、等级与单位。
- 底部「导入 N 条」，异常行被跳过不影响其余行。

### M13 会员编辑
- 编辑态顶部只读档案（深色）：头像 + 姓名 + 加入时间 + 绑定状态胶囊；累计消费 / 累计单量 / 当前折扣三格；说明「累计数据由系统统计，等级不自动升降，需手动指定」。

### M14 优惠券列表
- 金色「新建优惠券」Banner（→M15）；下方规则条说明「无需领取、按等级自动生效、一单一张、可与等级折扣叠加」。

- 券票卡 + 拼接操作条：每人限用次数、编辑、删除、启用 Toggle（金色）。

### M15 优惠券编辑
- 顶部「用户端卡包中的样子」实时预览券票卡，随表单联动。
- 基础组：券名称 / 券类型(满减|折扣) / 面额（折扣券额外要求「最高优惠」必填，标红「必填」）/ 使用门槛。
- 适用等级组：多选 chips（带各档人数），说明「勾选后该等级会员在卡包中直接看到，无需领取」。
- 适用商品范围组：全场通用 / 指定分类 / 指定菜品三选一。
  - 指定分类：分类多选 chips + 说明「动态包含以后新增到该分类的菜品」。
  - 指定菜品：显示已选数量与名称，点击打开**菜品多选弹层**（按分类分组、每组可全选、缩略图 + 名称 + 价格 + 勾选圆点）。

- 有效期与限制组：开始/结束日期（原生 date picker）、每人可用次数、启用 Toggle。
- 底部说明卡解释为何不做发放总量。

## 15.10 边界与异常（原型）

| 场景 | 期望行为 |
| --- | --- |
| 已截单 / 休息中 | 用户端下单入口禁用并提示；菜单仅浏览 |
| 库存为 0 / 售罄 | 菜品按钮禁用 + 蒙层；已加购需校验并提示 |
| 菜品下架 (off) | 用户端不展示；商户端可见可重新上架 |
| 待支付超时 | 自动转「已取消」（后端定时；前端订单列表刷新反映） |
| 取餐码核销重复 | 已完成单再次扫码提示「已核销」，不重复计数 |
| 网络/支付失败 | 停留确认页，可重试，不生成取餐号 |
| 空购物车 | 「去结算」禁用 |
| 无待取订单点首页取餐码 | Toast 提示无待取餐订单 |
| **非会员进入确认页** | 优惠卡显示「非会员 · 原价」与入会说明，不显示选券入口 |
| **已选券因购物车变化而失效** | 自动回落到当前最优可用券，不报错、不留空 |
| **无任何可用券** | 优惠券行显示「暂无可用」；弹层中不可用券置底并逐条给出原因 |
| **优惠额度超过应付** | 券减免被封顶在应付金额，实付最低为 0，不出现负数 |
| **等级被删除后会员仍在名单** | 名单卡等级位显示「等级已删除」；删除流程本身强制迁移，正常不应出现 |
| **券的适用等级被删空** | 券自动置为停用，并在 Toast 中告知被停用的券数量 |
| **券的指定菜品被删空** | 同上，券自动停用，不留谁都用不了的僵尸券 |
| **CSV 为 GBK 编码** | 检测到替换字符即中止并提示「另存为 CSV UTF-8」，不导入乱码数据 |
| **CSV 识别不到必需列** | 中止并提示按模板列顺序整理 |
| **导入含异常行** | 异常行跳过，其余行仍可导入；异常明细可展开定位行号与原因 |
| **菜品无图** | 详情页与列表沿用按品类渐变 + 宋体首字占位，不开天窗 |
| **菜品仅 1 张图** | 详情页不显示计数、不启用滑动，但仍可点击进入全屏预览 |
