# 在线点单系统 PRD

> 文档构成：本文档由「业务/产品 PRD」（§1–§14）与「前端实现规格 as-built」（§15）合并而成。
> §1–§14 描述要做什么、范围、业务规则与版本拆分；§15 收纳绥安食品微信小程序 P0 原型的精确实现蓝本（色值/组件/路由/数据模型/逐屏细节）。
> 合并来源：`order-design-0610/wechat-miniprogram/绥安食品-前端开发PRD.md`（v1.0，2026-06-10），原文件保留作备份。

## 1. 项目背景

本系统用于企业承包政府或企业单位餐饮服务后的在线点单场景。用户通过微信小程序浏览菜品、加入购物车、提交订单，并在线下窗口自提。商户通过 Admin 后台维护菜品、价格、图片、上下架状态、订单履约和经营数据。

系统首期目标不是做完整外卖平台，而是先稳定解决“单位内部/访客点餐、自提、商户后台管理、基础经营统计”这几个核心问题。

## 2. 产品目标

- 降低用户排队和人工点单成本，让用户提前完成选餐和下单。
- 让商户可自主维护每日供应菜品、价格、图片、库存和上下架状态。
- 让取餐窗口可以通过订单号或二维码快速核销，减少错餐和漏单。
- 让经营方可以查看每日营收、访问、点击、下单和单品销售数据。
- 在 500 人以内使用规模下，优先保证稳定、清晰、易维护。

## 3. 已确认范围

- 首期入口：微信小程序。
- 用户范围：单位员工 + 外部访客。
- 履约方式：线下自提。
- 取餐凭证：订单号 + 订单二维码。
- 后台：商户 Admin 后台。
- 支付：首期按微信支付设计，资金进入餐饮企业的微信支付商户号。
- 外卖配送：首期不开发完整能力，只在 UI 中作为“待开发”入口预留。
- 视觉方向：商务蓝 + 绿色，强调稳定、可信、清晰。

## 3.1 当前最高优先级：P0 可预览交互原型

当前 P0 不是先把完整系统开发完，而是先做出一套可以给客户预览的整体页面交互，让客户快速看到系统长什么样、怎么点单、怎么取餐、后台怎么管理，再进入正式开发。

P0 原型目标：

- 先验证整体产品方向和客户感知。
- 先确认用户端核心页面是否清晰。
- 先确认后台管理范围是否符合商户日常工作。
- 先确认商务蓝 + 绿色的视觉基调是否适合政府/企业场景。
- 先把完整需求功能点沉淀出来，作为后续开发基调。

P0 原型性质：

- 可以使用静态数据或 mock 数据。
- 可以模拟登录、下单、支付成功、核销成功等状态。
- 不要求真实支付。
- 不要求真实后台数据库。
- 不要求真实微信发布上线。
- 必须能连贯演示用户从浏览菜品到生成取餐凭证的完整路径。

参考实现观察：

- `woniudiancang/bee` 这类餐饮点单小程序通常会覆盖自提/外卖、取餐码、扫码核销、订单中心、门店商品区分、销量展示等能力。
- `yangxiaohan168/orderFood-wxCloud` 这类云开发点餐项目常见页面包括点餐页、结算页、我的订单、个人中心、管理员菜品管理、订单管理、公告、店铺设置、桌码、打印机等。
- `cuiqyu/wxapplication` 这类开源微信点餐项目通常围绕菜品分类、菜品管理、订单管理、评价、微信支付、桌号管理组织后台。
- 腾讯云点餐小程序示例中，用户端常见流程是首页、菜单浏览、搜索、购物车、下单页、支付页、我的订单；后厨/后台侧关注新订单、订单状态、菜品和排号等。

对本项目的取舍：

- 保留“菜品分类、购物车、订单、取餐码、扫码核销、后台商品和订单管理”这些成熟点餐系统的核心交互。
- 暂不把堂食桌号、会员充值、余额支付、评价、排队等位、打印机作为 P0 必做。
- 外卖只做 UI 预留，避免客户误以为首期已支持配送。

## 3.2 P0 原型页面清单

### 用户端小程序页面

P0 需要优先做这些可预览页面：

- 启动/授权页：展示系统品牌、微信授权或手机号登录入口。
- 首页：展示食堂/餐饮企业名称、营业状态、取餐地点、公告、今日推荐、点单入口。
- 点单页：左侧分类、右侧菜品列表，支持加购、减购、售罄状态、热销标签。
- 菜品详情页：展示菜品图片、名称、价格、描述、规格/数量、加入购物车。
- 购物车弹层：展示已选菜品、数量、总价、清空购物车、去结算。
- 确认订单页：展示商品明细、取餐方式、取餐地点、联系人、手机号、备注、提交订单。
- 支付/提交结果页：模拟支付成功或提交成功。
- 订单详情页：突出展示取餐号、二维码、取餐地点、订单状态、菜品明细。
- 我的订单页：展示待支付、待取餐、已完成、已取消等状态。
- 我的页面：展示用户身份、订单入口、联系客服、外卖待开放入口。

### 商户 Admin 原型页面

P0 需要优先做这些可预览页面：

- 后台登录页。
- 数据看板页：今日营收、订单数、访问量、点击量、单品销量排行。
- 商品列表页：商品搜索、分类筛选、上架/下架、售罄、价格、库存。
- 商品编辑页：商品名称、分类、价格、图片、描述、库存、餐段、上下架状态。
- 分类管理页：分类新增、排序、启用/停用。
- 订单列表页：订单号、用户、金额、状态、下单时间、取餐号。
- 订单详情页：菜品明细、用户信息、备注、支付状态、核销状态。
- 核销页：扫码核销入口、手动输入取餐号、核销确认弹窗。
- 营业设置页：营业状态、营业时间、截单时间、取餐地点、公告。

### 二期能力页面（不在一期合同范围）

> 以下页面为「会员等级 + 会员名单 + 优惠券」能力，属于合同 `online-ordering-system-contract-final.md` 第 31、108 条明确排除的第一期交付范围。界面与接口契约先行落地，用于方案评审与报价谈判；实际上线需先签补充协议或需求变更单。

用户端新增 1 页：

- 我的优惠券页：会员身份与常驻折扣、可用/已用完/已过期三态券列表。

商户端新增 6 页：

- 会员等级页：档位增删改名、排序、常驻折扣率、删除时的会员迁移与券影响面确认。
- 会员名单页：搜索、按等级筛选、名单人数/已绑定/已停用统计、导入与新增入口。
- 会员编辑页：单条新增或修改，含只读档案（加入时间、累计消费、绑定状态）与权益停用开关。
- 名单导入页：从微信聊天选择 CSV、解析、新增/更新/异常三列预览、异常行定位。
- 优惠券列表页：按进行中/未开始/已过期/已停用分组，启停与删除。
- 优惠券编辑页：券类型、面额、门槛、适用等级多选、适用范围三选一（含菜品多选弹层）、有效期、每人可用次数，附用户端卡面实时预览。

同期改造既有 5 页：

- 菜品详情页：单图改为最多 3 张的手动轮播（不自动播放、不循环、右下角计数），点击进入全屏预览。
- 确认订单页：新增「商品小计 / 等级折扣 / 优惠券」优惠明细与选券弹层。
- 我的页面：展示会员等级与折扣，「会员权益（建设中）」占位改为「我的优惠券」实入口。
- 商品编辑页：保存真正落库，支持多图上传、删除、设为封面。
- 商户中心页：新增「会员与营销」分组，「营销活动（规划中）」占位改为优惠券实入口。

### P0 演示主链路

客户演示时建议按以下顺序走：

1. 用户进入小程序首页，看到今日食堂和营业状态。
2. 用户进入点单页，按分类浏览菜品。
3. 用户加入购物车，并在购物车中调整数量。
4. 用户进入确认订单页，填写联系人和备注。
5. 用户提交订单，模拟支付成功。
6. 系统展示取餐号和二维码。
7. 商户后台看到新订单。
8. 核销员通过订单号或二维码完成核销。
9. 后台数据看板出现订单和营收变化。

## 4. 角色与权限

### 4.1 普通用户

普通用户包括单位员工和外部访客。

主要能力：

- 使用微信授权登录或手机号登录。
- 浏览菜品、分类、价格、图片、售罄和上下架状态。
- 将菜品加入购物车。
- 提交订单。
- 查看订单号、二维码、订单状态和历史订单。
- 到线下窗口凭订单号或二维码自提。
- 在规则允许范围内取消订单或申请退款。

员工和访客的差异：

- 员工可选填或绑定手机号、姓名、部门、工号。
- 访客可用手机号、姓名或临时标识下单。
- 如果客户后续要求更严格的单位内控，可增加员工白名单、部门权限或访客审批。

### 4.2 商户管理员

商户管理员是餐饮企业侧的主要后台使用者。

主要能力：

- 管理商品分类。
- 管理商品名称、价格、图片、描述、规格、库存和上下架状态。
- 查看订单列表和订单详情。
- 修改订单状态。
- 查看每日营收、订单量、访问量、点击量、单品销量和销售额。
- 设置营业时间、餐段、取餐地点和公告。
- 管理后台子账号。

### 4.3 取餐核销员

取餐核销员通常是窗口工作人员。

主要能力：

- 查看待取餐订单。
- 通过扫码核销订单二维码。
- 手动输入订单号核销。
- 标记订单为已取餐。
- 查看订单备注，避免错餐。

限制：

- 不应拥有商品价格、财务数据、账号权限等后台管理能力。

### 4.4 平台/超级管理员

平台/超级管理员用于系统运维和全局管理。

主要能力：

- 管理商户基础信息。
- 配置支付参数、系统参数和小程序发布配置。
- 查看系统运行日志和异常记录。
- 管理所有后台账号和权限。
- 处理特殊订单问题和数据修正。

首期如果只服务单一餐饮企业，可弱化平台管理端，把平台能力放在运维后台或配置项中。

## 5. 用户端功能

### 5.1 首页

首页需要让用户快速理解“今天能点什么、什么时候取、在哪里取”。

功能要求：

- 展示门店/食堂名称。
- 展示营业状态：营业中、休息中、已截单。
- 展示当前餐段：早餐、午餐、晚餐或全天。
- 展示公告：取餐地点、今日提示、临时停供等。
- 展示菜品分类入口。
- 展示推荐菜品、热销菜品或今日套餐。
- 预留“外卖配送”入口，首期标记为“暂未开放”。

### 5.2 菜品列表

功能要求：

- 按分类展示菜品。
- 展示菜品图片、名称、价格、简介、销量或推荐标签。
- 展示售罄、已下架、不可购买状态。
- 支持加入购物车。
- 支持查看菜品详情。

菜品状态说明：

- 上架：用户可见且可购买。
- 售罄：用户可见但不可购买。
- 下架：用户端不可见，后台仍保留。
- 未到售卖时间：用户可见但不可购买，显示可购买时间。

### 5.3 菜品详情

功能要求：

- 展示高清图片。
- 展示名称、价格、描述、规格、口味、过敏原提示。
- 展示库存或售罄状态。
- 支持选择规格或数量。
- 支持加入购物车。

首期规格可以简化。如果菜品没有复杂规格，只保留数量选择即可。

### 5.4 购物车

功能要求：

- 展示已选菜品、数量、单价、小计。
- 支持修改数量。
- 支持删除商品。
- 自动计算总价。
- 售罄或下架商品需要提示用户重新选择。
- 提交订单前再次校验价格、库存、营业状态。

### 5.5 下单页

功能要求：

- 展示订单商品明细。
- 展示应付金额。
- 展示取餐方式：线下自提。
- 展示取餐地点。
- 展示预计取餐时间或餐段。
- 支持填写备注。
- 支持填写或确认联系人、手机号。
- 支持确认员工/访客身份信息。
- 支持提交订单。

### 5.6 支付/结算

首期方案：微信支付直连餐饮企业商户号。

流程：

1. 用户提交订单。
2. 系统创建待支付订单。
3. 用户发起微信支付。
4. 支付成功后订单变为待备餐或待取餐。
5. 资金直接进入餐饮企业微信商户号。

非首期方案：线下/内部结算。

仅在客户明确不接微信支付时才考虑：

- 单位内部统一结算。
- 只验证点单流程，不发生真实线上收款。

流程：

1. 用户提交订单。
2. 系统生成待取餐订单。
3. 后台记录订单金额。
4. 线下或内部系统完成结算。

### 5.7 订单列表

功能要求：

- 展示全部订单。
- 按状态筛选：待支付、待备餐、待取餐、已完成、已取消、退款中、已退款。
- 展示订单号、金额、下单时间、取餐状态。
- 支持进入订单详情。

### 5.8 订单详情

功能要求：

- 展示订单号。
- 展示取餐二维码。
- 展示订单状态。
- 展示菜品明细。
- 展示支付金额和支付状态。
- 展示取餐地点。
- 展示下单时间、支付时间、完成时间。
- 展示用户备注。
- 支持取消订单或申请退款，具体规则由商户配置。

### 5.9 通知提醒

首期建议支持微信订阅消息或小程序内消息。

可提醒事件：

- 下单成功。
- 支付成功。
- 商户接单。
- 可取餐。
- 订单完成。
- 退款结果。
- 临时停餐或菜品变更。

### 5.10 会员权益与优惠券（二期能力 · 不在一期合同范围）

身份识别：

- 用户在下单或进入会员页时通过 `getPhoneNumber` 授权手机号，服务端用返回的 code 换取明文手机号后与商户名单比对，命中即判定等级。前端拿不到明文手机号，此链路必须由服务端完成。
- 名单是会员的唯一来源，用户端没有「申请入会」入口；不在名单中的用户为访客，按原价结算且无券可用。
- 同一手机号可跨设备使用，不做 openid 绑定锁；换绑由商户在后台名单中处理。

我的优惠券页：

- 顶部展示会员姓名、等级、常驻折扣与当前可用券数；非会员展示访客态与说明。
- 券分为可用、已用完、已过期三态，均展示券面、使用条件、适用范围、有效期。
- 券由商户按等级发放后自动进入卡包，用户没有领取动作。

确认订单页的优惠明细：

- 依次展示商品小计、等级折扣、优惠券三行，底部展示应付金额与「已优惠」合计。
- 默认自动选中优惠力度最大的可用券，用户可在选券弹层中手动切换或选择不使用。
- 不可用的券不隐藏，置于弹层底部并给出具体原因：已过期、未开始、本期已用完、购物车无适用商品、还差多少金额可用。

## 6. 商户 Admin 后台功能

### 6.1 登录与权限

功能要求：

- 支持后台账号密码登录。
- 支持角色权限：商户管理员、核销员、平台管理员。
- 支持账号启用、禁用。
- 支持修改密码。
- 关键操作记录操作日志。

### 6.2 商品分类管理

功能要求：

- 新增、编辑、删除分类。
- 设置分类排序。
- 设置分类启用/停用。
- 示例分类：套餐、主食、热菜、饮品、小吃、早餐、午餐。

### 6.3 商品管理

功能要求：

- 新增商品。
- 编辑商品名称、分类、价格、图片、描述、排序。
- 设置商品上下架。
- 设置商品售罄。
- 设置每日库存。
- 设置餐段可售：早餐、午餐、晚餐。
- 支持商品搜索。
- 支持按分类、状态筛选。

图片要求：

- 支持上传商品图片。
- 支持后台裁剪或压缩。
- 可将“AI 优化菜品图片”作为运营辅助能力，不作为首期核心交易链路。

### 6.4 价格与规格

首期建议支持简单规格。

功能要求：

- 单品固定价格。
- 可选规格：大份、小份、加料等。
- 每个规格可配置单独价格。
- 商品价格变更后，新订单使用新价格，历史订单保留原成交价。

### 6.5 库存与售罄

功能要求：

- 支持每日库存。
- 支持无限库存。
- 支持手动标记售罄。
- 用户提交订单时扣减库存。
- 订单取消或退款成功后可按规则返还库存。
- 库存不足时禁止下单。

### 6.6 营业设置

功能要求：

- 设置营业日。
- 设置营业时间。
- 设置餐段。
- 设置截单时间。
- 设置取餐地点。
- 设置公告。
- 设置是否开放点单。

示例：

- 午餐点单时间：09:00-11:00。
- 午餐取餐时间：11:30-13:00。
- 截单后用户仍可浏览，但不能提交订单。

### 6.7 订单管理

功能要求：

- 查看订单列表。
- 按订单号、手机号、用户姓名搜索。
- 按订单状态筛选。
- 按下单时间筛选。
- 查看订单详情。
- 修改订单状态。
- 支持取消订单。
- 支持退款处理。
- 支持导出订单。

订单状态建议：

- 待支付。
- 已支付/待接单。
- 待备餐。
- 待取餐。
- 已完成。
- 已取消。
- 退款中。
- 已退款。
- 异常订单。

> 注意：P0 原型（§15.7 订单状态机）实现的是简化 6 态 `待支付 / 待接单 / 制作中 / 待取餐 / 已完成 / 已取消`，用「制作中」而非「待备餐」，且未含退款态。本节为业务目标态，正式开发以本节为准；原型差异详见 §15.7。

### 6.8 核销管理

功能要求：

- 支持扫码核销订单二维码。
- 支持手动输入订单号核销。
- 核销前展示订单内容，避免错餐。
- 已核销订单不可重复核销。
- 重复扫码时提示“订单已完成”。
- 核销记录保存核销人、核销时间、核销方式。

### 6.9 数据看板

基础指标：

- 今日营收。
- 今日订单数。
- 今日下单人数。
- 今日访问人数。
- 今日菜品点击量。
- 客单价。
- 单品销量排行。
- 单品销售额排行。
- 订单状态分布。

筛选维度：

- 日期。
- 餐段。
- 商品分类。
- 商品名称。

统计口径：

- 营收以支付成功订单为准。
- 退款订单从营收中扣除。
- 浏览和点击以用户端行为埋点为准。
- 单品销量以已支付或已完成订单明细为准，具体口径需在后台说明。

### 6.10 财务与对账

微信支付直连方案：

- 后台展示订单支付金额、支付时间、微信交易号。
- 支持按日期导出订单明细。
- 支持对账时核对微信支付账单。
- 退款需要记录退款单号、退款金额、退款状态。

线下/内部结算方案：

- 后台展示应收金额。
- 支持导出结算报表。
- 可标记已结算、未结算。

### 6.11 会员等级管理（二期能力 · 不在一期合同范围）

- 档位可自由增删、改名、排序；等级有序，由低到高，一位会员只属于一个等级。
- 每档配置一个常驻折扣率（1–10 折），对该等级下全部会员的每一单生效。
- 等级由商户在名单中手动指定，系统不按消费自动升降级。系统上线时没有历史交易数据，自动升级无法承载「老会员」这一概念。
- 删除档位时强制走迁移弹层：先展示该档会员数与受影响的券清单，再由商户指定会员迁移至其他档位或降为非会员，确认后一次性完成。
- 删除档位会自动从所有券的适用等级中摘除该档；某张券因此没有任何适用等级时自动置为停用并提示。
- 至少保留一个等级，不允许删空。

### 6.12 会员名单管理（二期能力 · 不在一期合同范围）

字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 手机号 | 是 | 唯一识别键，与微信授权手机号比对 |
| 姓名 | 是 | 商户识别用 |
| 会员等级 | 是 | 从当前档位中选择 |
| 单位 / 部门 / 工号 | 否 | 对应确认清单第 10 条「按需填写」 |
| 备注 | 否 | 内部备注，用户不可见 |
| 状态 | 自动默认启用 | 停用保留记录但暂停全部权益，用于离职人员 |
| 加入时间 | 自动 | 导入或新增时间 |
| 已绑定 | 自动只读 | 该手机号是否已有用户完成微信授权 |
| 累计消费 / 单量 | 自动只读 | 商户手动调级的依据 |

录入方式：

- 手动逐条添加或修改。
- CSV 批量导入。小程序读不到手机本地文件，唯一途径是 `wx.chooseMessageFile`，商户需先把文件发送到微信聊天再选择。
- Excel 默认另存的 CSV 为 GBK 编码，按 UTF-8 读取会整片乱码，导入页做显式检测并提示「另存为 CSV UTF-8」。
- 表头支持别名识别；无表头时按模板列顺序解析。
- 导入前必须经过预览：分列展示新增 N 条、更新 M 条、异常 K 条，异常项可展开查看行号与具体原因（手机号格式错、姓名为空、等级名不存在、表内手机号重复）。
- 去重规则为按手机号覆盖更新：覆盖姓名与等级，保留加入时间、累计消费与微信绑定关系。商户第二次导入通常就是为了批量调级。
- 电脑端网页后台导入列入后期演进，不在本次范围。

### 6.13 优惠券配置（二期能力 · 不在一期合同范围）

发放模型：

- 券按等级自动生效，商户勾选适用等级后该等级会员在卡包中直接可见可用，没有领取动作。
- 券是一条规则而非一张票，不为每个用户生成券实例，因此不设发放总量；成本控制依靠有效期与每人可用次数。
- 定向发放给指定个人列入后期演进，不在本次范围。

字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 券名称 | 必填 | 用户端卡面主标题 |
| 类型 | 满减 / 折扣 | 门槛设 0 即为无门槛代金券，代金券不单独建类型 |
| 面额 | 满减填减免金额；折扣填折扣率 | — |
| 封顶金额 | 折扣券必填 | 强校验，不提供「不封顶」选项，防止商户配出亏损券 |
| 使用门槛 | 满 X 元可用，可为 0 | — |
| 适用等级 | 多选，至少 1 档 | 决定券发给谁 |
| 适用商品范围 | 全场通用 / 指定分类 / 指定菜品 | 指定菜品经多选弹层选择，支持按分类全选 |
| 有效期 | 固定起止日期 | 无领取动作，「领后 N 天」无从算起 |
| 每人可用次数 | 有效期内 N 次，默认 1 | — |
| 状态 | 启用 / 停用 | 停用后立即从用户卡包移除 |

范围联动规则：

- 选中分类为动态包含：以后新增到该分类的菜品自动纳入适用范围，不是勾选那一刻的快照。
- 菜品被删除时自动从券的适用范围中摘除；摘空则该券自动停用。菜品仅下架时保留在范围内，下架商品本来就下不了单。
- 商品券（免费换购）不做：牵连库存、售罄与独立核销三条链路，成本远高于满减与折扣之和，且在食堂场景价值有限。

### 6.14 菜品图片（本次同步补齐）

- 每个菜品最多 3 张图片，第一张为封面。
- 菜单列表、购物车、订单、后台列表一律只用封面，不引入额外的封面字段。
- 商户可删除任意图片，非首张图片可一键「设为封面」并移到第一位。
- 不做拖拽排序：小程序需借助 `movable-view` 实现，成本远高于价值。
- 图片经上传接口返回可跨设备访问的地址后存入菜品记录，不落本机存储。

## 7. 订单履约流程

### 7.1 标准自提流程

1. 用户进入微信小程序。
2. 用户浏览菜品。
3. 用户加入购物车。
4. 用户确认取餐信息并提交订单。
5. 系统校验营业状态、商品状态、价格和库存。
6. 系统生成订单。
7. 用户完成微信支付。
8. 系统生成订单号和取餐二维码。
9. 商户后台看到订单。
10. 窗口按订单备餐。
11. 用户到窗口出示订单号或二维码。
12. 核销员扫码或输入订单号。
13. 系统标记订单已完成。

### 7.2 订单编号规则

订单需要同时有系统订单号和取餐号。

建议规则：

- 系统订单号：用于系统唯一识别和对账，例如 `YYYYMMDDHHmmss + 随机数`。
- 取餐号：用于窗口叫号和用户取餐，例如每日递增 `A001`、`A002`。
- 二维码内容：使用订单核销 token，不直接暴露敏感用户信息。

要求：

- 订单号必须唯一。
- 取餐号在同一天、同一门店或同一餐段内不可重复。
- 已取消订单的取餐号不复用。

### 7.3 二维码核销

功能要求：

- 用户订单详情页展示二维码。
- 核销员扫码后进入订单确认页。
- 核销前展示订单号、取餐号、菜品明细和订单状态。
- 核销成功后订单变为已完成。
- 已完成、已取消、已退款订单不能再次核销。

### 7.4 手动核销

功能要求：

- 核销员可输入订单号或取餐号。
- 系统查询订单并展示明细。
- 核销员确认后完成核销。
- 手动核销需要记录操作人和时间。

### 7.5 取消订单

建议规则：

- 未支付订单：用户可直接取消。
- 已支付但未备餐：用户可申请取消，由商户后台审核退款。
- 已备餐或待取餐：默认不允许用户自行取消，由商户后台处理。
- 已完成订单：不可取消。

首期采用保守规则：

- 未支付订单可取消。
- 已支付订单需要商户后台确认退款。

### 7.6 退款

功能要求：

- 退款必须关联原订单。
- 退款金额不能超过实付金额。
- 支持全额退款。
- 部分退款可作为 V1 增强。
- 退款状态包括：退款中、退款成功、退款失败。
- 退款成功后订单状态更新为已退款。
- 退款失败需要保留失败原因，方便人工处理。

## 9. 非功能要求

### 9.1 稳定性

要求：

- 关键链路包括浏览、下单、支付回调、核销，必须优先保证稳定。
- 支付回调需要幂等处理，避免重复支付状态写入。
- 核销操作需要幂等处理，避免重复核销。
- 下单时需要再次校验价格、库存和商品状态。
- 后台修改商品状态后，用户端需要及时感知。
- 系统异常时需要给用户明确提示，不展示技术错误。

### 9.2 容量预估

已知人数上限约 500 人。

建议按以下峰值设计：

- 同时在线用户：100-200 人。
- 短时间集中下单：5-10 分钟内 100-300 单。
- 日订单量：500-1000 单以内。
- 商品数量：100-300 个以内。

设计原则：

- 数据库字段和索引要支持订单号、用户、时间、状态查询。
- 订单和支付回调不能依赖前端状态。
- 统计数据可异步计算，不阻塞下单主流程。

### 9.3 安全与权限

要求：

- 用户只能查看自己的订单。
- 核销员只能查看和核销订单，不可改商品和价格。
- 商户管理员只能管理本商户数据。
- 平台管理员可管理全局配置。
- 后台敏感操作记录日志。
- 支付参数、密钥、证书不可暴露给前端。
- 二维码核销 token 需要有签名或随机性，避免被猜测。

### 9.4 数据备份

要求：

- 订单、支付、退款、核销数据需要定期备份。
- 商品和配置变更需要保留操作记录。
- 重要数据删除建议采用软删除。
- 支持按日期导出订单和销售数据。

### 9.5 异常处理

常见异常：

- 用户支付成功但订单未更新。
- 支付回调重复到达。
- 用户下单时商品已售罄。
- 商户临时下架商品。
- 二维码重复扫码。
- 网络异常导致提交按钮重复点击。
- 退款失败。

处理要求：

- 支付状态以服务端和微信支付结果为准。
- 提交订单按钮需要防重复提交。
- 后台需要有异常订单筛选。
- 异常订单需要保留日志，方便人工处理。

### 9.6 可维护性

要求：

- 商品、订单、用户、支付、统计模块边界清晰。
- 订单状态流转必须有明确规则。
- 统计口径需要写在后台说明中，避免经营数据争议。
- 配置项优先后台可配置，减少上线后改代码。

## 10. UI 与体验要求

### 10.1 视觉风格

- 主色：商务蓝。
- 辅助色：绿色，用于成功、可购买、已完成等正向状态。
- 风格：稳重、清晰、低噪音。
- 避免过度花哨，更适合政府/企业单位环境。

> 精确色值、字体、圆角、阴影与尺寸规范见 §15.2「设计基线」；语义色映射见 §15.4。

### 10.2 用户端体验原则

- 用户 3 步内能完成核心操作：选菜、确认、下单。
- 菜品状态必须清楚：可买、售罄、已截单、暂未开放。
- 订单号和二维码要足够醒目。
- 取餐地点和取餐时间要在订单详情中突出展示。
- 外卖入口如预留，必须明确标注暂未开放，避免误导。

### 10.3 后台体验原则

- 商品上下架、售罄、改价格要简单直接。
- 订单列表要适合窗口高频查看。
- 核销页面要少步骤，避免窗口排队。
- 数据看板优先展示经营方每天最关心的数据。

## 11. 埋点与数据统计

用户端埋点：

- 访问首页。
- 浏览分类。
- 点击菜品。
- 加入购物车。
- 提交订单。
- 支付成功。
- 查看订单详情。
- 出示二维码。

后台统计：

- 每日访问人数。
- 每日菜品点击量。
- 每日下单人数。
- 每日订单数。
- 每日营收。
- 单品销量。
- 单品销售额。
- 支付成功率。
- 取消/退款数量。

注意：

- 访问和点击数据用于运营参考，不应和财务数据混用。
- 财务数据必须以支付成功和退款结果为准。

## 12. 关键业务规则

- 下单时以后端实时价格为准，前端展示价格只作为用户参考。
- 用户提交订单后，订单明细中的商品名称、价格、数量需要固化，后续商品改价不影响历史订单。
- 已售罄或已下架商品不能继续下单。
- 已完成订单不能重复核销。
- 已退款订单不能核销。
- 支付成功但前端未跳转成功时，用户再次进入订单页应能看到正确状态。
- 商户后台修改营业状态后，用户端提交订单时必须重新校验。

### 12.1 会员与优惠券算价规则（二期能力 · 不在一期合同范围）

算价链固定为：**原价小计 → 等级折扣 → 减券 → 应付**。以下规则写死，不做可配置。

1. 一单只能使用一张券；券与等级折扣**叠加**，不择优。
2. 等级折扣是常驻权益，优惠券是限时营销工具，两者业务目的不同，不合并为一套机制。
3. 券的**门槛判定**与**减免作用**均锚定「可用商品小计」，且作用在等级折扣**之后**的金额上，保证优惠永不超过实付。
   - 例：券为「指定商品满 50 减 10」，购物车含适用商品 40 元 + 不适用商品 30 元，则按 40 元（再乘等级折扣率）判定门槛，不满足即不可用。
4. 折扣券必须填写封顶金额，且减免不超过可用商品小计。
5. 默认自动选中减免金额最大的可用券；用户手动选中的券因购物车变化而不可用时，自动回落到最优券。
6. 用户可显式选择「不使用优惠券」，此时仅享等级折扣。
7. 券按「有效期内每人可用次数」计次，支付成功即计入。
8. 金额一律用「分」做整数运算，仅在展示时转元，避免浮点误差。
9. 会员与非会员的边界：名单是会员的唯一来源，不在名单中一律原价且无券可用。

## 13. 需要和客户讨论的事项

以下内容建议单独拿出来和客户确认。表达时不要用太技术化的说法，重点让客户判断“实际业务怎么做”。

### 13.1 用户身份怎么识别

需要和客户确认：

- 员工点餐时，是否必须填写或绑定姓名、手机号、部门、工号。
- 是否需要提前导入员工名单，只有名单内的人才能下单。
- 外部访客是否可以直接点餐，还是需要员工代下单或提供手机号。
- 是否需要区分员工订单和访客订单，方便后续统计。

客户能理解的问法：

“我们要不要限制只有单位内部员工才能点？访客能不能点？如果要区分员工和访客，需要用户下单时填哪些信息？”

### 13.2 点餐时间和餐段规则

需要和客户确认：

- 是只支持当天实时点餐，还是支持提前预订。
- 是否要分早餐、午餐、晚餐。
- 每个餐段是否有开始点餐时间和截单时间。
- 截单后用户是否还能浏览菜单，但不能下单。
- 是否需要每天固定菜单，还是后台随时调整当天菜品。

客户能理解的问法：

“用户是当天想吃什么就下单，还是要提前预订？比如午餐是否 11 点前必须下单，超过时间就不能买？”

### 13.3 菜品库存和售罄规则

需要和客户确认：

- 每个菜品是否需要设置每日数量。
- 菜品卖完后，是自动显示售罄，还是由后台人工设置售罄。
- 用户取消订单或退款成功后，库存是否要自动加回来。
- 是否允许某些菜品不限量供应。

客户能理解的问法：

“每个菜每天是不是有固定份数？卖完后系统要不要自动显示售罄？如果用户退单，这份库存要不要重新放出来卖？”

### 13.4 退款规则

已确认方向：已支付订单退款由商户审核。

仍需和客户确认：

- 用户支付后，多久以内可以申请退款。
- 商户开始备餐后，是否还允许退款。
- 已经取餐的订单是否一律不允许退款。
- 退款由谁审核，是商户管理员、财务人员，还是指定负责人。

客户能理解的问法：

“用户付完钱后，如果不想要了，商户是否要人工确认才能退？如果已经开始做餐或已经取餐，还能不能退？”

### 13.5 门店、窗口和档口范围

当前建议：首期先按一个门店/一个食堂设计。

仍需和客户确认：

- 是否确实只有一个取餐地点。
- 是否有多个窗口，比如套餐窗口、面食窗口、饮品窗口。
- 不同窗口是否需要分别管理自己的菜品和订单。
- 后续是否可能扩展到多个食堂或多个办公区。

客户能理解的问法：

“这套系统第一期是不是只给一个食堂用？如果现场有多个窗口，订单要不要分到不同窗口处理？”

### 13.6 后台账号和角色

需要和客户确认：

- 谁负责上架菜品和改价格。
- 谁负责看订单。
- 谁负责窗口核销。
- 谁可以看营收和财务数据。
- 是否需要给不同人员不同权限。

客户能理解的问法：

“后台不是所有人都应该看到所有功能。比如窗口人员只需要核销订单，老板或负责人才能看营业额。客户这边实际会有哪些人使用后台？”

### 13.7 是否需要对接其他系统

需要和客户确认：

- 是否需要对接现有财务系统。
- 是否需要对接食堂原有收银系统。
- 是否需要导出订单给财务对账。
- 是否需要按部门、人员或访客类型出报表。

客户能理解的问法：

“订单和收款数据后续要不要给财务用？是后台导出 Excel 就够，还是必须接到客户已有系统里？”

## 14. 验收标准

P0 原型验收时至少满足：

- 可以完整演示用户端从首页、点单、购物车、确认订单到订单详情取餐码的路径。
- 可以完整演示后台从数据看板、商品管理、订单管理到核销的路径。
- 页面视觉符合商务蓝 + 绿色、稳定、清晰、政府/企业场景可信感。
- 菜品图片、分类、价格、售罄、上下架、订单状态等关键元素都有样例展示。
- 外卖入口有 UI 预留，但明确显示“待开放”或“暂未开放”。
- 支付、核销、数据看板可以用 mock 数据模拟，不要求真实交易。
- 客户评审后可以基于页面逐项确认：保留、调整、删除、后续开发。

MVP 验收时至少满足：

- 用户可以在微信小程序完成浏览、加入购物车、提交订单。
- 用户可以在订单详情看到订单号和二维码。
- 商户后台可以维护商品、价格、图片、上下架和售罄。
- 商户后台可以查看订单并完成扫码/手动核销。
- 系统可以正确处理订单状态变化。
- 数据看板可以展示今日营收、订单数、访问/点击和单品销量。
- 支付方案或内部结算方案有明确配置和流程。
- 关键操作有日志，异常订单可追踪。

## 15.1 产品概述（原型）

绥安食品到店自提点餐小程序。**单一小程序内含两端**，启动时由用户自选身份进入：

| 端 | 角色 | 核心任务 |
| --- | --- | --- |
| 用户端 | 顾客 | 浏览菜单 → 点单 → 在线支付 → 到店凭取餐码自提 |
| 商户端 | 店员 / 店长 | 接单 → 制作 → 扫码核销 → 菜品与经营管理 |

**关键业务约束**
- 仅支持**到店自提**，无配送（"外卖配送"为占位入口，标注未开放）。
- 取餐凭证为**取餐号 + 二维码**（如 `A126`），核销后订单完成。
- 有**截单时间**（默认 16:30）与营业状态（营业中 / 休息中 / 已截单），影响下单可用性。

## 15.7 订单状态机（原型核心逻辑）

> ⚠️ 与 §6.7 业务目标态的差异：原型实现简化 6 态，用「制作中」而非「待备餐」，且未含 `退款中/已退款/异常订单`。正式开发的目标态以 §6.7 为准；本节描述原型当前行为。

```
用户端：
  [下单未支付] 待支付 ──支付──▶ 待取餐(商户视角进入待接单)
  待支付 ──超时/取消──▶ 已取消

商户端履约推进（单向，每步一个主按钮）：
  待接单 ──接单──▶ 制作中 ──备好──▶ 待取餐 ──核销──▶ 已完成
  任意活跃态 ──取消──▶ 已取消
```

- 商户端每个订单卡只暴露**一个主行动按钮**，文案随状态变化：`接单 → 备好 → 核销 → 查看`。
- **核销**（M04 / M03）是「待取餐 → 已完成」的唯一路径，核销成功后工作台营收/订单数实时 +1。
- 推进操作给 Toast 反馈，**支持「撤销」**（回退到上一状态）。
- 批量操作仅在「待接单」泳道开放（批量接单）。

## 15.10 边界与异常（原型）

| 场景 | 期望行为 |
| --- | --- |
| 已截单 / 休息中 | 用户端下单入口禁用并提示；菜单仅浏览 |
| 库存为 0 / 售罄 | 菜品按钮禁用 + 蒙层；已加购需校验并提示 |
| 菜品下架 (off) | 用户端不展示；商户端可见可重新上架 |
| 待支付超时 | 自动转「已取消」（后端定时；前端订单列表刷新反映） |
| 取餐码核销重复 | 已完成单再次扫码提示「已核销」，不重复计数 |
| 网络/支付失败 | 停留确认页，可重试，不生成取餐号 |
| 空购物车 | 「去结算」禁用 |
| 无待取订单点首页取餐码 | Toast 提示无待取餐订单 |
| **非会员进入确认页** | 优惠卡显示「非会员 · 原价」与入会说明，不显示选券入口 |
| **已选券因购物车变化而失效** | 自动回落到当前最优可用券，不报错、不留空 |
| **无任何可用券** | 优惠券行显示「暂无可用」；弹层中不可用券置底并逐条给出原因 |
| **优惠额度超过应付** | 券减免被封顶在应付金额，实付最低为 0，不出现负数 |
| **等级被删除后会员仍在名单** | 名单卡等级位显示「等级已删除」；删除流程本身强制迁移，正常不应出现 |
| **券的适用等级被删空** | 券自动置为停用，并在 Toast 中告知被停用的券数量 |
| **券的指定菜品被删空** | 同上，券自动停用，不留谁都用不了的僵尸券 |
| **CSV 为 GBK 编码** | 检测到替换字符即中止并提示「另存为 CSV UTF-8」，不导入乱码数据 |
| **CSV 识别不到必需列** | 中止并提示按模板列顺序整理 |
| **导入含异常行** | 异常行跳过，其余行仍可导入；异常明细可展开定位行号与原因 |
| **菜品无图** | 详情页与列表沿用按品类渐变 + 宋体首字占位，不开天窗 |
| **菜品仅 1 张图** | 详情页不显示计数、不启用滑动，但仍可点击进入全屏预览 |
